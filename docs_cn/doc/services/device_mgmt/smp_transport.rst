.. _mcumgr_smp_transport_specification:

SMP 传输规范
###########################

本文档规定了实现服务器端和客户端 SMP 传输所需的信息。

.. _mcumgr_smp_transport_ble:

Bluetooth Low Energy (LE)
*************************

MCUmgr 客户端在实现 SMP 客户端时，需要使用以下 Bluetooth 特征值：

- **服务 UUID**：``8D53DC1D-1DB7-4CD3-868B-8A527460AA84``
- **特征值 UUID**：``DA2E7828-FBCE-4E01-AE9E-261174997C48``

所有 SMP 通信都使用单个 GATT 特征值。SMP 请求通过
GATT Write Without Response 命令发送，SMP 响应以
GATT Notification 的形式发送。

如果 SMP 请求或响应过大，无法装入单个 GATT 命令，
发送方会将其分片为多个数据包。请求或响应分片时
不引入额外的帧结构，载荷只是被拆分到多个数据包中。
由于 GATT 保证数据包按序送达，第一个分片中的 SMP 头部
包含足够的信息用于重组。

.. _mcumgr_smp_transport_uart:

UART/串口和控制台
***********************

Zephyr 的 MCUmgr 子系统所使用的 SMP 协议规范采用
基本的数据帧结构，以支持 UART 通道的复用。复用要求
每个帧以两字节标记开头，并以换行符结尾。
目前 MCUmgr 对帧大小施加 127 字节的限制，尽管
实际上并没有要求该限制的协议约束。
该限制包含前缀和换行符，因此实际允许的载荷
大小为 124 字节。

尽管 Zephyr 中不存在这样的传输，但完全可以实现
基于 UART 传输的 MCUmgr 客户端/服务器，该传输可以完全没有帧结构，
或者使用硬件串口控制，或者其他帧结构方式。

帧分片
=================

串口上的 SMP 协议被分片为 MTU 大小的帧；每个
帧由两字节起始标记、主体和结尾换行符
组成。

共有四种类型的帧：initial（初始）、partial（部分）、partial-final（部分-结束）
和 initial-final（初始-结束）；每种帧类型通过起始标记和/或
主体内容加以区分。

帧格式
-------------

Initial 帧之后必须跟随可选的 partial
帧序列，最后以 partial-final 帧结尾。
主体始终采用 Base64 编码，因此此处描述为
MTU - 3 的主体大小，实际上能够承载 N = (MTU - 3) / 4 * 3 字节
的原始数据。

Initial 帧的主体前面跟随两字节的总包长度，
按 Big Endian 编码，其值等于原始主体大小加上 2 字节
CRC16 的大小；这意味着 initial 帧允许的实际主体大小为 N - 2。

如果主体大小小于 N - 4，则可以在单个
帧中承载整个主体及其前面的长度和后面的 CRC，
这里称为 initial-final；关于 initial-final
帧的描述见下文。

Initial 帧格式：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | 0x06 0x09     | 2 字节        | 帧起始标记                 |
    +---------------+---------------+---------------------------+
    | <base64-i>    | 不超过      | Base64 编码的主体          |
    |               | MTU - 3 字节 |                           |
    +---------------+---------------+---------------------------+
    | 0x0a          | 1 字节        | 帧结束                     |
    +---------------+---------------+---------------------------+

``<base64-i>`` 是 Base64 编码的主体，格式为：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | total length  | 2 字节        | Big endian 16 位值，      |
    |               |               | 表示主体总长度 + 2 字节   |
    |               |               | CRC16 的大小；注意，      |
    |               |               | total length 字段本身的大小 |
    |               |               | 不计入总长度值。          |
    +---------------+---------------+---------------------------+
    | body          | 不超过      | 原始主体数据分片           |
    |               | MTU - 5       |                           |
    +---------------+---------------+---------------------------+

Initial-final 帧格式与 initial 帧格式相似，
但 ``<base64-i>`` 的定义不同。

Initial-final 帧的 ``<base64-i>`` 是 Base64 编码的数据，
形式为：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | total length  | 2 字节        | Big endian 16 位值，      |
    |               |               | 表示主体总长度 + 2 字节   |
    |               |               | CRC16 的大小；注意，      |
    |               |               | total length 字段本身的大小 |
    |               |               | 不计入总长度值。          |
    +---------------+---------------+---------------------------+
    | body          | 不超过      | 原始主体数据分片           |
    |               | MTU - 7       |                           |
    +---------------+---------------+---------------------------+
    | crc16         | 2 字节        | 整个包主体的 CRC16，      |
    |               |               | 前面的长度字段不计入。    |
    +---------------+---------------+---------------------------+

Partial 帧是前一个 initial 帧或其他 partial
帧的延续。Partial 帧的形式为：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | 0x04 0x14     | 2 字节        | 帧起始标记                 |
    +---------------+---------------+---------------------------+
    | <base64-i>    | 不超过      | Base64 编码的主体          |
    |               | MTU - 3 字节 |                           |
    +---------------+---------------+---------------------------+
    | 0x0a          | 1 字节        | 帧结束                     |
    +---------------+---------------+---------------------------+

Partial 帧的 ``<base64-i>`` 是数据的 Base64 编码，
形式为：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | body          | 不超过      | 原始主体数据分片           |
    |               | MTU - 3       |                           |
    +---------------+---------------+---------------------------+

Partial-final 帧的 ``<base64-i>`` 是数据的 Base64 编码，
形式为：

.. table::
    :align: center

    +---------------+---------------+---------------------------+
    | 内容           | 大小          | 描述                       |
    +===============+===============+===========================+
    | body          | 不超过      | 原始主体数据分片           |
    |               | MTU - 5       |                           |
    +---------------+---------------+---------------------------+
    | crc16         | 2 字节        | 整个包主体的 CRC16，      |
    |               |               | 前面的长度字段不计入。    |
    +---------------+---------------+---------------------------+


CRC 细节
-------------

Final 类型帧中包含的 CRC16 仅针对
原始数据计算，不包含包长度。
CRC16 多项式为 0x1021，初始值为 0。

.. _mcumgr_smp_transport_raw_uart:

Raw UART/串口（不使用控制台）
*********************************

在 Zephyr 中，UART 可用一种替代传输，它不像
SMP over console 传输那样使用 Base64，这允许更小的代码尺寸和更快的传输 - 但
不能用于在同一 UART 上有 shell 或日志输出的设备，
或连接到显示 ASCII 数据的终端，因为所有通信
都使用原始二进制 SMP 协议完成。

要使用此协议，请使用 :kconfig:option:`CONFIG_MCUMGR_TRANSPORT_RAW_UART`，它要求
以 raw 模式启用 MCUmgr UART 控制台驱动程序。

超时
=======

由于使用该传输时没有帧结构，UART 上可能会收到无效
数据，导致系统等待一个例如很长的包，而该包
永远不会到达。为防止这种情况，存在一个超时机制：如果
在特定时间范围内未收到完整包，则整个接收缓冲区被清空。
建议在 UART 端口上启用该选项；对于 USB CDC 之类的传输，
它是"虚拟"UART，数据在传递之前可以校验，因此
不需要该选项。该选项可通过
:kconfig:option:`CONFIG_MCUMGR_TRANSPORT_RAW_UART_INPUT_TIMEOUT` 启用，
其超时时间可通过 :kconfig:option:`CONFIG_MCUMGR_TRANSPORT_RAW_UART_INPUT_TIMEOUT_TIME_MS` 设置。
