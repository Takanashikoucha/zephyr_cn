传感器设备威胁模型
##########################

本文档描述了一种物联网传感器设备的威胁模型。
明确威胁模型有助于指导开发工作，也可用于帮助确定这些工作的优先级。

该设备包含某种传感器（例如温度或管道压力），
将该数据发送到运行微控制器的 SoC。该微控制器连接到云
服务，并将该传感器数据转发到该服务。云服务还可以
向设备发送配置数据以及软件更新镜像。总体框图可参见图 1：

.. figure:: media/sensor-model.svg

    图 1. 传感器总体框图

在该传感器设备中，传感器通过 SPI 总线与 SoC 连接，
SoC 具有一个网络接口，用于与云服务通信。这些接口的
具体细节可能以意想不到的方式影响威胁模型，需要
考虑其变体（例如，使用通过某种总线连接的独立
网络接口 SoC）。

该模型还侧重于通过 MQTT-over-TLS 协议进行通信，
因为这似乎被广泛使用 [1]_。

资产
======

威胁模型需要考虑的一个方面是设备运行中涉及的
资产。以下列表列举了该模型中包含的资产：

1. **引导加载程序（bootloader）**。这是包含在
   设备闪存中的小型代码/数据镜像，是第一个运行的代码。为了建立
   信任根，该镜像必须不可变。该模型假设
   SoC 提供保护闪存区域免受未来写入的机制，且该操作
   将在该镜像被编程到设备后尽早在生产中完成 [th-imboot]_。

2. **应用固件镜像**。该资产由微控制器运行的
   其余固件组成。之所以区分是因为该镜像部分需要
   随着安全漏洞的发现而定期更新。对该镜像
   更新的要求为：

   a. 该镜像仅可被授权镜像替换
      [th-authrepl]_。

   b. 当有授权替换镜像可用时，更新
      应及时进行 [th-timely-update]_。

   c. 镜像更新应被视为原子操作，即当
      镜像运行时，闪存中应包含完整的更新镜像
      或完整的旧镜像 [th-atomic-update]_。

3. **根证书列表**。为了认证云服务
   （服务器），物联网设备必须拥有一份允许对
   服务器上证书进行签名的根证书列表。对于基于
   云提供商的服务，该列表通常由服务
   提供商提供。由于根证书可能过期，
   甚至可能被撤销，该列表需要定期更新
   [th-root-certs]_、[th-root-check]_。

4. **客户端密钥**。为了向服务认证客户端，
   客户端必须拥有某种密钥。这通常是一个私
   钥，通常是 RSA 密钥或 EC 私钥。
   在与服务器建立通信时，设备将使用
   该密钥作为 TLS 建立过程的一部分，或用于
   签署通信中使用的消息。

   该密钥通常由服务提供商或运行在其他
   地方的软件生成，必须安全地安装到
   设备上。策略可能要求定期更换该密钥，
   这需要一种更新客户端密钥的方式。
   通常，服务允许两到三个活动密钥，
   以便在旧密钥仍在使用时更新得以
   继续。

   这些密钥必须受到防读取保护，且允许
   访问它们的代码量应为最小。[th-secret-storage]_

5. **当前日期/时间**。TLS 证书验证需要
   知道当前日期和时间，以判断当前时间是否
   在证书的有效时间范围内。此外，基于令牌
   的客户端认证通常要求客户端签署一条
   包含令牌有效时间窗口的消息。证书验证
   要求设备对日期和时间的认知在一天左右
   的范围内准确。令牌生成通常要求时间
   在 5-10 分钟范围内准确。

   可能通过查询外部时间服务器来近似
   安全时间。安全 NTP 可能超出
   物联网设备的能力。时间不准确的主要风险
   是拒绝服务（设备拒绝有效证书），
   以及生成时间无效的令牌。攻击者
   可能诱骗设备生成未来才有效的令牌，
   但攻击者还必须伪造服务器证书才能
   拦截该令牌。[th-time]_

6. **传感器数据**。从传感器本身接收并
   传输到服务的数据应未经修改或篡改地
   传输。

7. **设备配置**。各种配置数据，例如
   要连接的云服务的主机名、时间服务器的
   地址、传感器数据发送到服务的频率和
   参数，以及其他需要由设备保存的数据。
   这些配置数据需要随着配置的变化定期
   更新。更新应仅允许来自授权方。[th-conf]_

8. **日志**。为了协助分析安全问题，
   设备应记录与安全相关事件的信息。
   物联网设备通常存储有限，因此这些
   日志需要仔细筛选。也可能将这些
   日志事件发送到云服务，在资源更
   充裕的环境中存储。应记录的事件
   类型包括：

   a. **固件镜像更新**。系统应记录
      新镜像的下载，以及镜像成功更新
      的时间。

   b. **客户端密钥变更**。客户端密钥的
      变更和新密钥应被记录。

   c. **设备配置的变更**。

   [th-logs]_

通信
=============

除资产外，威胁模型还考虑数据或资产在
系统实体之间通信的位置。

1. **闪存内容**。闪存设备包含多个区域。
   闪存的内容可由 SoC 的 CPU 以编程方式
   修改。

   a. **引导加载程序**。如资产部分所述，
      引导加载程序是闪存设备中包含初始
      运行代码的一小段区域。该区域应在
      设备生命周期的早期写入，然后闪存设备
      应配置为永久禁止修改该区域。该
      配置还应防止通过外部接口（如
      JTAG 或 SWD 调试器）修改。

      引导加载程序负责验证应用镜像的
      签名，并在需要更新时从更新镜像
      更新应用镜像。

      引导加载程序应在安装更新镜像前
      验证其签名。

      引导加载程序应仅接受版本号比
      当前镜像新的更新镜像。

   b. **应用镜像**。应用镜像包含设备
      正常运行期间执行的代码。在运行
      该镜像前，引导加载程序应验证镜像的
      数字签名，以避免运行被篡改的镜像。
      闪存/系统应配置为在引导加载程序
      完成后，CPU 无法写入应用
      镜像。

   c. **更新镜像**。这是闪存中存放
      新版本应用镜像的区域。该镜像
      将在正常运行期间由应用下载并
      存储。完成后，应用可触发重启，
      引导加载程序即可安装新镜像。

   d. **密钥存储**。闪存中的一块区域将
      用于存储客户端密钥。该区域由
      应用镜像的子集读写。应用应配置为
      保护该区域免受不需要访问它的代码的
      读写，同时考虑应用代码中可能
      发现的漏洞。泄露密钥内容将
      允许攻击者伪造该设备。

      初始密钥应在设备配置活动（与
      设备正常运行不同的阶段）中放入
      设备。后续更新可在通过安全
      通道从服务接收的通信指导下进行。

   e. **配置存储**。应有一块区域用于
      存储其他配置信息。在资源受限的
      设备上，允许将其存储在与密钥
      存储相同的区域中，但这会增加
      可访问密钥存储区域的代码量，
      从而增加需要审查的代码量。

   f. **日志存储**。设备可能有闪存区域
      用于写入日志事件。

2. **传感器/执行器接口**。在该设计中，
   传感器或执行器通过 SPI 等总线与
   SoC 通信。硬件设计应使攻击者
   难以拦截该总线。所需技术取决于
   传感器数据的敏感性和用途，
   可从将传感器安装在与 MCU 相同的
   PCB 上到用环氧树脂封装整个设备不等。

3. **与云服务的通信**。设备与云服务
   之间的通信将通过公共互联网进行。
   因此，应假设攻击者可任意
   拦截该通道，例如返回伪造的
   DNS 结果或尝试对与云服务的
   通信实施中间人攻击。

   设备应对所有与云服务的通信使用
   TLS [th-all-tls]_。TLS 协议栈应配置为
   仅使用通常被认为安全的密码套件
   [2]_，包括前向保密。通信应
   由以下措施保障安全：

   a. **密码套件选择**。设备应仅允许
      使用通常公认的密码套件
      [th-tls-ciphers]_。

   b. **服务器证书验证**。服务器提供的
      证书应经过验证 [th-root-check]_。

      i.   **命名**。证书应命名
           云服务服务器所提供的主机和服务。
           :rfc:`6125` 描述了相关最佳实践。
           设备可要求证书比该 RFC
           中描述的更为严格，前提是
           服务可使用符合要求的证书。

      ii.  **路径验证**。设备应验证
           证书链从设备中包含的根证书
           到服务提供的证书具有有效的
           签名路径。
           :rfc:`4158` 一般性地描述了这一点。
           设备可要求更严格的路径，
           前提是服务器使用的证书
           符合该限制。

      iii. **有效期**。所有提供的
           证书的有效期应针对设备对
           当前时间的最佳认知进行检查。

   c. **客户端认证**。客户端应使用仅
      该特定设备知晓的密钥向服务
      认证自身。有多种选项，所用技术
      通常由所使用的特定服务提供商
      指定 [th-tls-client-auth]_。

      i.  **TLS 客户端证书**。TLS 协议允许
          客户端提供证书，并声明其
          知晓该证书所描述的密钥。
          通常，这些证书将存储在
          服务提供商处。这些证书可以
          是自签名的，也可以由 CA 签署。
          由于服务提供商维护有效证书
          （将其映射到设备身份）的列表，
          由 CA 签署这些证书不会增加
          任何额外安全性，但可能
          有助于这些证书的管理。

      ii. **基于令牌的认证**。客户端
          也可使用 MQTT CONNECT 数据包的
          *password* 字段进行认证。
          但密钥本身不得在该数据包中
          传输。相反，可使用基于
          令牌的协议，例如 :rfc:`7519` 的
          JSON Web Token（JWT）。
          这些令牌通常有较短的有效期
          （例如 1 小时），以防止被
          拦截后重用。在设备验证
          服务器身份之前，不应发送
          令牌。

   d. **随机/熵源**。加密通信需要
      生成安全伪随机数。设备应使用
      现代公认的加密随机比特生成器
      生成这些随机数。应使用在
      SoC 内以硬件实现的非确定性
      随机比特生成器（True RBG），
      或使用由 SoC 内熵源播种的
      确定性随机比特生成器（Pseudo RBG）。
      有关批准的 RBG 信息请参见 NIST SP 800-90A，
      有关测试设备熵源的信息请参见
      NIST SP 800-90B [th-entropy]_。

4. **与时间服务的通信**。理想情况下，
   设备应包含维护安全时间的硬件。
   然而，大多数在用的 SoC 不支持
   此功能，因此有必要查询
   外部时间服务。
   :rfc:`4330` 及所引用的 RFC 描述了
   简单网络时间协议（Simple Network Time
   Protocol），可用于从网络时间
   服务器查询当前时间。

5. **设备生命周期**。物联网设备将具有
   从生产到销毁和处置的生命周期。
   影响该生命周期安全的方面包括
   初始配置、正常运行、重新配置
   和销毁。

   a. **初始配置**。在初始配置阶段，
      需要编程引导加载程序、初始
      应用镜像、设备密钥和初始
      配置数据 [th-initial-provision]_。
      此外，应安装引导加载程序闪存
      保护。这些信息中，只有
      设备密钥需要逐设备不同。
      该密钥应安全保存，并在编程后
      在设备外的所有位置销毁
      [th-initial-secret]_。

   b. **正常运行**。正常运行包括
      本文档其余部分描述的行为。

   c. **重新配置**。有时需要重新
      配置设备，例如用于不同的应用。
      一种方式是保留相同的设备密钥，
      替换配置数据以及与该
      设备关联的云服务数据。也可以
      编程新的设备密钥，但如果这样做
      应安全地进行，并在编程到
      设备后在外部销毁新密钥
      [th-reprovision]_。

   d. **销毁**。为防止设备密钥被用于
      伪造设备，在退役时，特定
      设备的密钥应被使其失效
      [th-destruction]_。可能的
      方式包括：

      i.    硬件销毁设备。

      ii.   安全擦除包含密钥的
            闪存区域 [3]_。

      iii.  从服务中移除设备身份和
            证书。

其他考虑因素
====================

除上述内容外，联网设备通常还需要
一种方式来配置其连接到所放置的
网络环境。实现方式有很多种，
重要的是这些配置方式不得绕过
上述安全要求。

威胁
=======

.. [th-imboot] 必须使用不可变的引导加载程序启动。

.. [th-authrepl] 应用镜像仅可被授权镜像替换。

.. [th-timely-update]
   应用更新应及时进行。

.. [th-atomic-update]
   应用更新应为原子操作。

.. [th-root-certs]
   TLS 必须拥有一份受信任的根证书列表。

.. [th-root-check]
   TLS 必须验证来自服务器的根证书有效。

.. [th-secret-storage]
   必须有安全存储客户端密钥的机制。
   允许访问这些密钥的代码量应为最小。

.. [th-time]
   系统必须对当前日期/时间有
   适度准确的认知。

.. [th-conf]
   系统必须接收并保存配置数据。

.. [th-logs]
   系统必须记录安全相关事件，
   并将其存储在本地或发送到服务。

.. [th-all-tls]
   所有与云服务的通信应使用 TLS。

.. [th-tls-ciphers]
   TLS 应配置为仅允许通常公认的
   密码套件（包括前向保密）。

.. [th-tls-client-auth]
   设备应使用上述方法之一向
   云提供商认证自身。

.. [th-entropy]
   TLS 层应使用由 SoC 内熵源播种的
   现代公认加密随机比特生成器。

.. [th-initial-provision]
   设备在部署前必须加载逐设备的密钥。

.. [th-initial-secret]
   初始密钥应安全保存，并在设备
   配置后尽快在任何外部位置销毁。

.. [th-reprovision]
   设备重新配置应安全地进行。

.. [th-destruction]
   在退役时，设备密钥应被使其失效。
