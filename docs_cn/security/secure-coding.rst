安全编码
#############

传统上，基于微控制器的系统并未过多
强调安全。
它们通常被视为孤立的、
与世隔绝的，且不太脆弱，仅仅是因为
访问它们的难度。物联网改变了
这一点。现在，运行在小型微控制器上的代码通常可以
访问互联网，或至少访问其他设备（这些设备本身可能
有漏洞）。鉴于它们通常部署的规模，
不受控制的访问可能是灾难性的 [#attackf]_。

本文档描述了确保
在 Zephyr 项目中处理安全的需求和流程。所有提交的
代码都应遵守这些原则。

本文档的很大一部分来自 [CIIBPB]_。

**********************

本文档涵盖 `Zephyr 项目`_ 的指南，
从安全视角来看。其中包含的许多想法
取自其他开源努力。

安全编码
*************

将 Zephyr 这样的开放软件系统设计为安全的，需要
遵循一组定义的设计标准。在 [SALT75]_ 中，
定义了以下
广泛接受的保护机制原则，
以帮助防止安全违规并限制其影响：

- **开放设计**作为设计准则，纳入了这样的至理名言：
  保护机制在任何广泛使用的系统中
  都无法保密。相反于依赖秘密的、量身定制的
  安全措施，应使用公开接受的加密算法和
  成熟的加密库。

- **机制经济性**规定系统的底层设计
  应尽可能简单和精简。在
  Zephyr 项目的上下文中，这可以通过模块化代码
  [PAUL09]_ 和抽象 API 实现。

- **完全中介**要求对每个对象和每个进程的
  每次访问都必须先经过认证。应尽可能
  避免存储访问条件的机制。

- **故障安全默认值**定义访问默认受限，
  仅在系统保护方案定义的特定条件下
  才被允许，例如成功认证后。
  此外，服务的默认设置应选择
  以提供最大安全性的方式。这对应于
  "默认安全"范式 [MS12]_。

- **权限分离**是这样一项原则：
  在授予访问之前需要满足两个或更多
  条件。在 Zephyr 项目的上下文中，这可能包括分割密钥 [PAUL09]_。

- **最小权限**描述了一种访问模型，
  其中每个用户、
  程序和线程都应拥有
  执行其任务所需的最小权限子集。
  该正向安全模型旨在最小化系统的
  攻击面。

- **最小公共机制**规定，供
  多个用户或进程共用的机制，
  除非严格必需，否则不应共享。
  [SALT75]_ 中给出的例子是一个应
  实现为每个用户执行的共享库的函数，
  而非所有用户共享的监视过程。

- **心理可接受性**要求安全特性
  对开发者易于使用，以确保其使用
  及其应用的正确性。

除这些一般原则外，以下要点
特定于安全 RTOS 的开发：

- **互补安全/纵深防御**：不要依赖单一
  威胁缓解方法。在互补安全
  方法的情况下，威胁缓解的部分
  由底层平台执行。如果平台
  未提供此类机制，或不可信，
  应使用纵深防御 [MS12]_ 范式。

- **不常用服务默认关闭**：为减少
  系统对潜在攻击的暴露，
  如果功能或服务仅很少使用，
  则不应默认启用（[MS12]_ 给出了
  80% 的阈值）。对于 Zephyr 项目，这可以
  使用配置管理实现。每个功能
  和模块都应表示为配置选项，
  需要显式启用。然后，
  对特定用例不需要的所有功能、协议和驱动
  都可以禁用。如果启用了低级选项和 API
  但应用未使用，应通知用户。

- **变更管理**：为保证对
  系统变更的可追溯性，每个变更都应遵循
  指定流程，包括
  变更请求、影响分析、批准、实施和
  验证阶段。在每个阶段，应提供
  适当文档。所有提交都应关联到
  问题跟踪器中的 bug 报告或变更
  请求。没有有效引用的提交
  应被拒绝。

安全开发知识
****************************

安全设计者
===============

Zephyr 项目必须至少拥有一位知道
如何设计安全软件的主要开发者。

这需要理解以下设计原则，
包括 [SALT75]_ 中的 8 个原则：

- 机制经济性（尽可能保持设计
  简单和精简，例如通过采用
  大幅简化）

- 故障安全默认值（访问决策应默认
  拒绝，且项目的安装应
  默认安全）

- 完全中介（每个可能被限制的访问
  都必须检查权限且不可绕过）

.. todo: 更好地解释嵌入式设备的约束，以及
   我们通常做边缘检测，而非在每个函数处。
   或许将其与下文输入验证关联。

- 开放设计（安全机制不应依赖
  攻击者对其设计的无知，而应依赖
  更易保护和更改的信息，如密钥和密码）

- 权限分离（理想情况下，
  对重要对象的访问应
  依赖多个条件，因此击败一个保护
  系统不会启用完全访问。例如，
  多因素认证，如同时要求
  密码和硬件令牌，比单因素认证
  更强）

- 最小权限（进程应以
  必要的最小权限运行）

- 最小公共机制（设计应最小化
  多个用户共用的机制，
  以及所有用户依赖的机制，
  例如临时文件目录）

- 心理可接受性（人机界面必须
  为易用性设计——为
  "最小惊讶"设计会有所帮助）

- 有限攻击面（
  攻击者可尝试进入或提取数据的
  不同点的集合）

- 使用允许列表的输入验证（输入通常应
  在接收前检查以确定其是否有效；
  该验证应使用允许列表
  （仅接受已知良好值），
  而非阻止列表（尝试列出已知不良值））。

漏洞知识
=======================

项目中的"主要开发者"是指任何熟悉
项目代码库、能轻松对其进行变更，
且被项目大多数其他参与者
如此认可的人。主要开发者通常
在过去一年中做出若干贡献
（通过代码、文档或回答问题）。
如果开发者启动了项目
（且未在项目超过三年前离开）、
拥有接收私有漏洞报告渠道
信息（如果有的话）的选项、
能代表项目接受提交，
或执行项目软件的最终发布，
则通常被视为主要开发者。
如果只有一位开发者，该个人就是
主要开发者。

至少一位主要开发者**必须**知道
导致此类软件漏洞的常见错误类型，
以及对抗或缓解每种错误的
至少一种方法。

例子（取决于软件类型）包括 SQL
注入、操作系统注入、经典缓冲区溢出、
跨站脚本、缺失认证和
缺失授权。参见
`CWE/SANS top 25`_ 或 `OWASP Top 10`_ 获取
常用列表。

非营利组织 OpenSecurityTraining2 为 C/C++ 开发者
提供的免费课程可在 `OST2_1001`_ 获取。
它教授如何防止、检测和
缓解线性栈/堆缓冲区溢出、
非线性越界写入、
整数溢出及其他整数问题。
后续课程 `OST2_1002`_
涵盖未初始化数据访问、竞态条件、
释放后使用、类型混淆和
信息泄露漏洞。

Zephyr 安全小组委员会
============================

应有一个"Zephyr 安全小组委员会"，
负责执行本指南、监控评审，
以及改进这些指南。

该团队将根据 Zephyr 项目章程
建立。

代码评审
***********

Zephyr 项目应使用一个代码评审系统，
所有变更都必须经过该系统。每个变更都应
由至少一位不是变更作者的主要开发者
评审。该开发者应确定
该变更是否影响系统安全
（基于其对安全的一般理解），
如果是，应请求具有漏洞知识的开发者
或安全设计者也评审代码。
这些个人中的任何一人都应有能力
阻止该变更被合并到
主线代码中，直到安全问题得到解决。

问题与 Bug 跟踪
***********************

Zephyr 项目应有一个问题跟踪系统
（如 GitHub_），可用于
记录和跟踪在系统中发现的
缺陷。

.. _GitHub: https://www.github.com

由于安全问题通常是敏感的，
该问题跟踪系统应有一个
字段以指示安全问题。设置该
字段应导致问题仅对 Zephyr 安全
小组委员会可见。此外，应有一个
字段允许 Zephyr 安全小组委员会
添加将对给定问题具有
可见性的额外用户。

该禁运，或有限可见性，
应仅持续固定时长，
默认值为由项目决定的值。然而，
由于安全考虑通常
在 Zephyr 项目本身之外，
可能需要延长该禁运时间。
所需时间应清晰标注在
问题本身中。

Zephyr 安全小组委员会应
至少每月审查一次问题列表。
该审查应专注于
跟踪修复、确定是否需要
通知或让外部方参与，
以及确定何时解除问题的禁运。
禁运**不应**通过
自动化手段解除，但
评审团队应避免在解除
已解决问题上造成不必要的延迟。
