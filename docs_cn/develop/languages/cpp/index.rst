.. _language_cpp:

C++
语言
支持
####################

C++
是
一种
通用
面向
对象
编程
语言，
基于
C
语言。

启用
C++
支持
********************

Zephyr
支持
用
C
和
C++
两者
编写
的
应用。
不过，
要
在
应用
中
使用
C++
你
必须
通过
在
应用
配置
文件
中
选择
:kconfig:option:`CONFIG_CPP`
配置
Zephyr
包括
C++
支持。

要
启用
C++
支持，
编译器
工具链
必须
也
包括
一个
C++
编译器
且
包含
的
编译器
必须
被
Zephyr
构建
系统
支持。
:ref:`toolchain_zephyr_sdk`，
包括
GNU
C++
Compiler
（GCC
的
一部分），
被
Zephyr
支持，
这里
文档化
的
功能
和
其
可用性
假设
使用
Zephyr
SDK。

Zephyr
应用
的
默认
C++
标准
级别
（即
编译器
标志
传递
强制
的
语言）
是
C++11。
其他
标准
通过
kconfig
choice
可用，
例如
:kconfig:option:`CONFIG_STD_CPP98`。
Zephyr
中
受
支持
和
测试
的
最
旧
标准
是
C++98。

编译
源
文件
时，
构建
系统
基于
文件
的
后缀
（扩展名）
选择
C++
编译器。
用
**cpp**
或
**cxx**
后缀
标识
的
文件
用
C++
编译器
编译。
例如，
:file:`myCplusplusApp.cpp`
用
C++
编译。

C++
标准
要求
``main()``
函数
有
``int``
返回
类型。
你的
``main()``
必须
定义
为
``int
main(void)``
或
``int
main(int,
char
**)``。
要
使用
带
参数
的
main
必须
选择
``CONFIG_BOOTARGS``
选项。
Zephyr
忽略
main
的
返回
值。
不过，
应用
必须
返回
零
（0）。
所有
非
零
返回
值
保留。

.. note::
   不
   要
   对
   内核、
   驱动
   或
   系统
   初始化
   代码
   使用
   C++。

语言
功能
*****************

Zephyr
当前
只
提供
C++
功能
的
一个
子集。
以下
功能
*不*
受
支持：

* 静态
  全局
  对象
  销毁
* OS
  特定
  C++
  标准
  库
  类
  （例如
  ``std::thread``、
  ``std::mutex``）

尽管
不
是
穷举
列表，
以下
功能
的
支持
被
包括：

* 继承
* 虚
  函数
* 虚
  表
* 静态
  全局
  对象
  构造器
* 用
  **new**
  和
  **delete**
  操作符
  的
  动态
  对象
  管理
* 异常
* :abbr:`RTTI
  （运行
  时
  类型
  信息）`
* 标准
  模板
  库
  （STL）

静态
全局
对象
构造器
在
驱动
初始化
后
但
应用
:c:func:`main()`
函数
前
初始化。
因此，
C++
的
使用
被
限制
在
应用
代码。

要
利用
C++
异常，
必须
在
应用
配置
文件
中
选择
:kconfig:option:`CONFIG_CPP_EXCEPTIONS`。

Zephyr
最小
C++
库
**************************

Zephyr
最小
C++
库
（:file:`lib/cpp/minimal`）
提供
C++
标准
库
和
应用
二进制
接口
（ABI）
函数
的
最小
子集
以
启用
基本
C++
语言
支持。
这
包括：

* ``new``
  和
  ``delete``
  操作符
* 虚
  函数
  桩
  和
  vtables
* 全局
  构造器
  的
  静态
  全局
  初始化器

最小
C++
库
的
范围
严格
限制
在
提供
基本
C++
语言
支持，
它
不
实现
任何
`标准
模板
库
（STL）`_
类
和
函数。
因此，
它
只
适合
用于
实现
其
自己
（非
标准）
类
库
且
不
依赖
标准
模板
库
（STL）
组件
的
应用。

任何
使用
标准
模板
库
（STL）
组件
的
应用，
如
``std::string``
和
``std::vector``，
必须
启用
C++
标准
库
支持。

C++
标准
库
********************

`C++
标准
库`_
是
ISO
C++
标准
（``std``
命名空间）
一部分
的
类
和
函数
集合。

Zephyr
不
以
源
代码
形式
包括
任何
C++
标准
库
实现。
相反，
它
允许
配置
构建
系统
链接
到
C++
编译器
工具链
中
包含
的
预
构建
C++
标准
库。

要
启用
C++
标准
库，
从
应用
配置
文件
中
的
:kconfig:option:`CONFIG_LIBCPP_IMPLEMENTATION`
选择
一个
适用
的
工具链
特定
C++
标准
库
类型。

例如，
当
用
:ref:`toolchain_zephyr_sdk`
构建
时，
构建
系统
可以
被
配置
链接
到
GNU
C++
Library
（``libstdc++.a``），
这是
一个
功能
完整
的
C++
标准
库，
提供
ISO
C++
标准
要求
的
所有
功能
包括
标准
模板
库
（STL），
通过
在
应用
配置
文件
中
选择
:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`。

以下
C++
标准
库
被
Zephyr
支持：

* GNU
  C++
  Library
  （:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`）
* ARC
  MetaWare
  C++
  Library
  （:kconfig:option:`CONFIG_ARCMWDT_LIBCPP`）

需要
完整
C++
标准
库
功能
的
Zephyr
子系统
可以
从
其
config
选择
:kconfig:option:`CONFIG_REQUIRES_FULL_LIBCPP`，
它
自动
选择
一个
兼容
的
C++
标准
库
除非
特定
C++
标准
库
的
Kconfig
符号
被
选择。

头
文件
和
C
与
C++
之间
的
不
兼容
****************************************************

要
相互
交互，
C
和
C++
必须
通过
头
文件
共享
代码：
数据
结构、
宏、
静态
函数、
...
尽管
C
和
C++
有
大量
重叠，
它们
是
不同
的
语言
有
`已知
不
兼容
性`_。
C
不
只是
C++
子集。
标准
级别
（例如
"C++11"）
添加
另一
层
复杂
性，
因为
新
功能
通常
受
另一
语言
启发
并
从
其
复制
但
很多
年
后
且
有
微妙
差异。
使
事情
更
复杂
的
是，
编译器
通常
在
功能
被
标准化
前
提供
早期
原型。
标准
可以
有
被
不同
编译器
不同
解释
的
歧义。
编译器
可以
有
bug
且
这些
可能
需要
变通
方法。
为
了
帮助
这，
许多
项目
限制
自己
到
有限
数量
的
工具链。
Zephyr
不
这样。

这些
兼容
性
问题
对
头
文件
影响
不
成
比例
的
大。
不
只
因为
它们
必须
在
C
和
C++
之间
兼容，
还
因为
由于
*间接*
包含
和
实际
项目
典型
的
`缺乏
结构
和
头
文件
组织`_，
它们
最终
被
编译
在
惊人
高
数量
的
其他
源
文件
中。
因此，
头
文件
暴露
于
更
大
多样性
的
工具链
和
项目
配置。
添加
更多
约束，
Zephyr
项目
对
代码
风格、
编译器
警告、
静态
分析器
和
标准
符合性
（例如：
MISRA）
有
严格
的
策略。

综合
起来，
所有
这些
约束
可以
使
编写
头
文件
非常
有
挑战。
这
一
节
的
目的
是
文档化
某些
最佳
"头
文件
实践"
和
在
Zephyr
特定
上下文
中
学习
的
经验。
尽管
这里
的
许多
信息
不
是
Zephyr
特定
的，
这
一
节
不
是
C/C++
标准、
教科
书
和
其他
参考
知识
的
替代。

测试
-------

幸运
的
是，
Zephyr
项目
有
广泛
的
测试
和
CI
基础设施，
提供
覆盖
基线、
早期
捕获
问题、
强制
策略
并
在
某种
控制
下
保持
这种
组合
爆炸。
``tests/lib/cpp/cxx/``
在
这个
上下文
中
非常
有用，
因为
其
``testcase.yaml``
配置
让
``twister``
快速
迭代
一
范围
的
``-std``
参数：
``-std=c++98``、
``-std=c++11``
等。

记住
未
使用
的
宏
不
被
编译。

指定
初始化器
-----------------------

初始化
宏
在
头
文件
中
常见，
因为
它们
帮助
减少
样板
代码。
C99
添加
用
"指定"
成员
名
而非
*裸*
表达式
列表
初始化
``struct``
和
``union``
类型。
某些
GCC
版本
即使
在
其
C90
模式
下
也
支持
指定
初始化器。

当
在
简单
级别
使用
时，
指定
初始化器
更
少
容易
出错、
更
可
读
和
更
灵活。
另一
方面，
C99
允许
一个
惊人
大
且
宽松
的
可能性
集合：
指定
初始化器
可以
乱
序、
重复、
"嵌套"
（``.a.x
=``）、
各种
其他
大
括号
可以
省略、
指定
初始化器
和
不
可以
混合
等。

二十
年
后，
C++20
以
更
多
限制
的
方式
向
C++
添加
指定
初始化器；
部分
因为
C++
``struct``
实际
是
``class``。
如
C++
提案
编号
P0329
（与
C
对比）
或
任何
完整
C++
参考
中
描述
的，
混合
不
被
允许
且
初始化器
必须
按
顺序
（允许
间隙）。

有趣
的
是，
C++20
中
的
新
限制
可以
导致
``gcc
-std=c++20``
失败
编译
用
``gcc
-std=c++17``
成功
编译
的
代码。
例如，
``gcc
-std=c++17``
和
更
旧
的
允许
C
风格
的
初始化器
和
裸
表达式
混合。
这
用
``gcc
-std=c++20``
*相同
GCC
版本*
失败
编译。

推荐：
要
最大化
跨
不同
C
和
C++
工具链
和
标准
的
兼容
性，
Zephyr
头
文件
中
的
指定
初始化器
应该
遵循
所有
C++20
规则
和
限制。
非
指定、
pre-C99
初始化
提供
更
多
兼容
性
且
也
被
允许
但
指定
初始化
是
更
可
读
和
偏好
的
代码
风格。
在
任何
情况
下，
两种
风格
必须
永远
不
在
相同
初始化器
中
混合。

警告：
成功
编译
不
是
不
兼容
性
故事
的
结束。
例如，
初始化
表达式
的
*求值
顺序*
在
C99
中
未
指定！
它
是
C++20
中
（预期
的）
左
到
右
顺序。
其他
标准
修订
可能
变化。
怀疑
时，
不
依赖
求值
顺序
（这里
和
其他
地方）。

匿名
联合
----------------

匿名
联合
（a.k.a.
"unnamed"
联合）
似乎
从
C++
的
最
开始
就
是
其
一部分。
它们
直到
C11
才
被
正式
添加
到
C。
如
通常
的，
C
和
C++
之间
有
差异。
例如，
C
只
支持
匿名
联合
作为
外层
``struct``
或
``union``
的
成员，
空
列表
``{
}``
一直
在
C++
中
被
允许
但
它们
需要
C23
等。

当
初始化
匿名
成员
时，
表达式
可以
被
大
括号
包围
或
不。
它
可以
是
指定
的
或
裸
的。
为
最大
可
移植性，
当
初始化
*匿名
联合*：

- *不*
  用
  大
  括号
  包围
  *指定*
  初始化器。
  这
  被
  C++20
  及
  之后
  要求，
  它们
  将
  这种
  大
  括号
  视为
  将
  裸
  表达式
  与
  （其他）
  指定
  初始化器
  混合
  并
  失败
  编译。

- 用
  大
  括号
  包围
  *裸*
  表达式。
  这
  被
  C
  要求。
  也许
  因为
  C
  更
  宽松
  且
  允许
  许多
  初始化
  可能性
  和
  变体，
  因此
  可能
  需要
  这种
  大
  括号
  来
  消歧？
  注意
  C
  不
  允许
  在
  初始化
  表达式
  中
  省略
  大多数
  大
  括号
  -
  但
  不
  在
  这个
  特定
  情况
  下
  用
  裸
  表达式
  初始化
  匿名
  联合。

某些
pre-C11
GCC
版本
支持
某种
形式
的
匿名
联合。
它们
不幸
地
要求
用
大
括号
包围
其
指定
初始化器
与
这个
推荐
冲突。
这
可以
用
``#ifdef
__STDC_VERSION__``
解决，
如
Zephyr
commit
`c15f029a7108
<https://github.com/zephyrproject-rtos/zephyr/commit/c15f029a7108>`_
和
对应
的
代码
审查
中
演示
的。
