.. _language_cpp:

C++ 语言支持
####################

C++ 是一种基于 C 语言的通用面向对象编程语言。

启用 C++ 支持
********************

Zephyr 支持用 C 和 C++ 编写的应用。不过，要在应用中使用
C++，必须在应用配置文件中选择 :kconfig:option:`CONFIG_CPP`
来配置 Zephyr 包含 C++ 支持。

要启用 C++ 支持，编译器工具链还必须包含 C++ 编译器，
且该编译器必须受 Zephyr 构建系统支持。:ref:`toolchain_zephyr_sdk`
（包含 GNU C++ 编译器，它是 GCC 的一部分）受 Zephyr 支持；
本文档记录的功能及其可用性均假设使用 Zephyr SDK。

Zephyr 应用的默认 C++ 标准级别（即由编译器标志所强制的
语言标准）为 C++11。其他标准可通过 kconfig choice 选择，
例如 :kconfig:option:`CONFIG_STD_CPP98`。Zephyr 中受支持和
测试的最旧标准是 C++98。

编译源文件时，构建系统根据文件后缀（扩展名）选择
C++ 编译器。带有 **cpp** 或 **cxx** 后缀的文件使用
C++ 编译器编译。例如，:file:`myCplusplusApp.cpp`
使用 C++ 编译。

C++ 标准要求 ``main()`` 函数的返回类型为 ``int``。你的
``main()`` 必须定义为 ``int main(void)`` 或
``int main(int, char **)``。若要使用带参数的 main，
必须选择 ``CONFIG_BOOTARGS`` 选项。Zephyr 会忽略
main 的返回值，但应用必须返回零（0）。所有
非零返回值均被保留。

.. note::
    不要在内核、驱动或系统初始化代码中使用 C++。

语言功能
*****************

Zephyr 目前仅提供 C++ 功能的一个子集。
以下功能 *不* 受支持：

* 静态全局对象的析构
* 操作系统特定的 C++ 标准库类（例如 ``std::thread``、
  ``std::mutex``）

虽然这不是一个穷举列表，但以下功能已包含支持：

* 继承
* 虚函数
* 虚函数表
* 静态全局对象的构造
* 使用 **new** 和 **delete** 操作符进行
  动态对象管理
* 异常
* :abbr:`RTTI (运行时类型信息)`
* 标准模板库（STL）

静态全局对象的构造在驱动初始化之后、
应用 :c:func:`main()` 函数之前完成初始化。
因此，C++ 的使用仅限于应用代码。

若要使用 C++ 异常，必须在应用配置文件中
选择 :kconfig:option:`CONFIG_CPP_EXCEPTIONS`。

Zephyr 最小 C++ 库
**************************

Zephyr 最小 C++ 库（:file:`lib/cpp/minimal`）
提供 C++ 标准库和应用二进制接口（ABI）函数的
一个最小子集，以实现基本的 C++ 语言支持。
它包括：

* ``new`` 和 ``delete`` 操作符
* 虚函数桩和虚函数表
* 用于全局构造函数的静态全局初始化器

最小 C++ 库的范围严格限定于提供基本的
C++ 语言支持，它不实现任何
`Standard Template Library (STL)`_ 的
类和函数。因此，它仅适用于实现自己的
（非标准）类库且不依赖标准模板库（STL）
组件的应用。

任何使用标准模板库（STL）组件的应用，
例如 ``std::string`` 和 ``std::vector``，
都必须启用 C++ 标准库支持。

C++ 标准库
********************

`C++ Standard Library`_ 是 ISO C++ 标准
（``std`` 命名空间）的一部分，由一系列
类和函数组成。

Zephyr 的源代码中不包含任何 C++ 标准库实现。
相反，它允许配置构建系统链接到 C++ 编译器工具链中自带的预构建 C++ 标准库。

要启用 C++ 标准库，请在应用配置文件中
从 :kconfig:option:`CONFIG_LIBCPP_IMPLEMENTATION`
选择一个适用的、与工具链对应的 C++ 标准库类型。

例如，使用 :ref:`toolchain_zephyr_sdk` 构建时，
可以在应用配置文件中选择
:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`，
将构建系统配置为链接 GNU C++ 库
（``libstdc++.a``）。这是一个功能完整的
C++ 标准库，提供 ISO C++ 标准要求
的所有功能，包括标准模板库（STL）。

Zephyr 支持以下 C++ 标准库：

* GNU C++ 库（:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`）
* ARC MetaWare C++ 库（:kconfig:option:`CONFIG_ARCMWDT_LIBCPP`）

需要完整 C++ 标准库功能的 Zephyr 子系统
可以在其配置中选择
:kconfig:option:`CONFIG_REQUIRES_FULL_LIBCPP`。
除非已选择某个特定 C++ 标准库的
Kconfig 符号，否则该选项会自动选择
一个兼容的 C++ 标准库。

头文件以及 C 与 C++ 之间的不兼容
****************************************************

为了相互交互，C 和 C++ 必须通过头文件共享
代码：数据结构、宏、静态函数等。尽管
C 和 C++ 有大量重叠，但它们是两种不同的
语言，存在 `known incompatibilities`_。
C 并不只是 C++ 的一个子集。标准级别
（例如 “C++11”）又增加了一层复杂性，
因为新功能常常受到另一种语言的启发
并从其复制而来，但往往多年之后才出现，
且带有细微差异。更复杂的是，编译器
通常会在功能标准化之前提前提供其原型；
标准本身可能存在歧义，被不同编译器
以不同方式解释；编译器也可能有缺陷，
需要变通处理。为了应对这些问题，
许多项目把自己限制在有限数量的工具链上，
而 Zephyr 并不这样做。

这些兼容性问题对头文件的影响尤其不成比例。
不仅因为它们必须在 C 和 C++ 之间保持兼容，
还因为由于 *间接* 包含，以及实际项目中
常见的 `lack of structure and headers organization`_，
它们最终会被大量其他源文件编译。
因此，头文件会暴露于更多样的
工具链和项目配置。再加上
Zephyr 项目对代码风格、编译器警告、
静态分析器和标准合规性（例如 MISRA）
有严格要求，问题更加复杂。

综合起来，所有这些约束都会使编写头文件
变得非常困难。本节旨在记录一些最佳的
“头文件实践”以及在 Zephyr 特定上下文中
总结出的经验。尽管这里的许多信息并非
Zephyr 特有，但本节不能替代对
C/C++ 标准、教科书和其他参考资料的了解。

测试
-------

幸运的是，Zephyr 项目拥有完善的测试和
CI 基础设施，能够提供覆盖率基线、尽早发现问题、强制执行策略，并在一定程度上控制这种组合爆炸。
``tests/lib/cpp/cxx/`` 在这方面非常有用，
因为其 ``testcase.yaml`` 配置可以让
``twister`` 快速遍历一系列 ``-std`` 参数：
``-std=c++98``、``-std=c++11`` 等。

请记住，未使用的宏不会被编译。

指定初始化器
-----------------------

初始化宏在头文件中很常见，因为它们
有助于减少样板代码。C99 允许通过
“指定”成员名而非一组 *裸* 表达式
来初始化 ``struct`` 和 ``union`` 类型。
某些 GCC 版本即使在 C90 模式下
也支持指定初始化器。

在简单层面使用时，指定初始化器
更不容易出错、更易读、更灵活。
另一方面，C99 允许了一个出人意料地
庞大且宽松的可能性集合：指定初始化器
可以乱序、重复、“嵌套”（``.a.x =``），
可以省略各种其他大括号，可以混合使用指定初始化器和裸表达式，等等。

二十年后，C++20 以更为严格的方式
将指定初始化器引入 C++，部分原因是
C++ 中的 ``struct`` 实际上就是 ``class``。
如 C++ 提案 P0329（该提案与 C 进行了
对比）或任何完整的 C++ 参考中所述，
不允许混合使用，且初始化器必须按顺序排列（允许跳过某些成员）。

有趣的是，C++20 中的新限制可能导致
``gcc -std=c++20`` 无法编译用
``gcc -std=c++17`` 成功编译的代码。
例如，``gcc -std=c++17`` 及更早版本
允许 C 风格的初始化器与裸表达式混合。
这在使用 ``gcc -std=c++20`` *相同
GCC 版本* 时无法编译。

建议：为了最大化不同 C 和 C++ 工具链及标准之间的兼容性，Zephyr 头文件中的指定初始化器应遵循所有 C++20 规则和限制。非指定的、C99 之前的初始化方式兼容性更好，也是允许的，但指定初始化是更易读、更推荐的代码风格。无论如何，两种风格永远不应在同一个初始化器中混合使用。

警告：成功编译并不意味着不兼容性问题的结束。例如，初始化表达式的 *求值顺序* 在 C99 中是未定义的！在 C++20 中，它是（预期的）从左到右顺序。其他标准修订版本可能有所不同。如有疑问，不要依赖求值顺序（无论在这里还是其他地方）。

匿名联合
----------------

匿名联合（又称“未命名”联合）似乎
从 C++ 诞生之初就是其一部分。
直到 C11，它们才被正式加入 C 语言。
一如既往，C 和 C++ 之间存在差异。
例如，C 仅支持将匿名联合作为
外层 ``struct`` 或 ``union`` 的成员；
空列表 ``{ }`` 在 C++ 中一直允许，
但在 C 中需要 C23 才支持，等等。

初始化匿名成员时，表达式可以加括号也可以不加，可以是指定初始化器也可以是裸表达式。为了最大可移植性，初始化 *匿名联合* 时：

- *不要* 用大括号包围 *指定* 初始化器。
  这是 C++20 及以上版本的要求，因为它们
  会将这种大括号视为将裸表达式与（其他）指定初始化器混合，从而导致编译失败。

- *要* 用大括号包围 *裸* 表达式。
  这是 C 语言的要求。也许是因为 C 语言更宽松，允许许多初始化可能性和变体，因此可能需要这些大括号来消除歧义？注意 C 语言虽然允许在初始化表达式中省略大多数大括号，但在用裸表达式初始化匿名联合这一特定情况下不允许。

某些 C11 之前的 GCC 版本支持某种形式
的匿名联合。不幸的是，它们要求用大括号包围指定初始化器，这与上述建议相冲突。这可以通过
``#ifdef __STDC_VERSION__`` 解决，
如 Zephyr commit `c15f029a7108
<https://github.com/zephyrproject-rtos/zephyr/commit/c15f029a7108>`_
及其对应的代码审查中所示。
