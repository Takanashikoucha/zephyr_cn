厂商特定 API 放置策略
####################################

概览
*********

本策略定义了厂商特定硬件功能在 Zephyr 项目中必须如何贡献、组织以及对外暴露。
它确保 Zephyr 的公共 API 表面保持稳定，厂商扩展不会绕过标准 API 生命周期，
并且潜在的跨厂商功能有清晰的演进路径，最终可以发展为通用驱动类。

除非满足纳入 Zephyr 正式 API 生命周期（experimental → stable → deprecated）
所需的标准，否则厂商特定 API 不得暴露为公共 Zephyr 接口。
固有绑定到单个 SoC 或厂商的功能必须封装在厂商的 SoC 目录内。

本策略为贡献者和维护者提供了一致的决策模型。

指导原则
******************

- **公共 Zephyr API 不得包含厂商特定接口。**

  放置在 ``include/zephyr/`` 下的接口预期通过标准 API 生命周期演进。
  不能满足这一演进要求的厂商特定接口不得暴露为公共 Zephyr API。

- **优先选择通用方案而非厂商特定方案。**

  当硬件功能适用于多个厂商，或者未来可能适用于多个厂商时，
  应将其实现为现有驱动类的一部分，或作为新的跨厂商驱动类。

- **厂商特定功能必须封装。**

  厂商专用机制应位于厂商的平台命名空间（SoC、开发板等）内。

- **演进必须保持可能。**

  代码的放置方式不得阻止将来将厂商特定实现提升为可移植的 Zephyr 驱动类。

决策过程
****************

添加新的硬件功能或厂商特定行为时，贡献者必须按照以下顺序遵循决策树：

- **该功能是否在逻辑上扩展现有驱动类？**

  如果是，则扩展现有驱动类；不要创建厂商特定 API。

- **该功能是否可以成为跨厂商驱动类？**

  如果硬件概念并非明显只属于单个厂商，
  或者类似于可能出现在多个架构中的模式，
  则创建新的驱动类。

- **该功能是否明显是厂商特定的且不太可能通用化？**

  在这种情况下，将头文件和实现都放在以下位置：

  .. code-block:: none

     soc/<vendor>/..


  这确保了真正的封装、长期可维护性，
  以及在 SoC 被移除时的干净清理。

  厂商特定代码应在位于 ``soc/<vendor>/include`` 下的头文件中实现，
  代码放在 ``soc/<vendor>/common`` 或 ``soc/<vendor>/<series>`` 中。

  此类接口对厂商而言是私有的和/或内部的，用于支持其特定硬件，
  并且会受到审查，以避免创建特定于某个厂商的功能孤岛。

  使用这些接口的应用程序，鉴于它们是厂商内部和/或私有的，
  不应期望有任何关于生命周期或向后兼容性的保证。

允许位置摘要
*************************

1. 扩展现有驱动类

   - 位置：

     .. code-block:: none

        include/zephyr/drivers/<class>.h
        drivers/<class>/

   - 适用场景：

     功能适合或扩展现有驱动类。


2. 对现有驱动类的厂商特定扩展

   - 位置：

     .. code-block:: none

        include/zephyr/drivers/<class>/
        drivers/<class>/

   - 适用场景：

     功能是对现有驱动类的厂商特定扩展，
     但核心概念并非只属于单个厂商，
     且未来有可能被标准化。

3. 创建新驱动类（跨厂商）

   - 位置：

     .. code-block:: none

        include/zephyr/drivers/<class>.h
        drivers/<class>/

   - 适用场景：

     功能可以合理地适用于多个厂商，
     或者可以演进为通用抽象。

4. 厂商特定、SoC 本地代码（厂商独有功能的默认选择）

   - 位置：

     厂商特定代码应在位于 ``soc/<vendor>/include`` 下的头文件中实现，
     代码放在 ``soc/<vendor>/common`` 或 ``soc/<vendor>/<series>`` 中。

   - 适用场景：

     功能为某个厂商或 SoC 所独有，
     且不打算作为公共 API 暴露。
