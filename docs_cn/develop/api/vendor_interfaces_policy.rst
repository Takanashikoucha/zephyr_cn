厂商
特定
API
放置
策略
####################################

概览
*********

这个
策略
定义
厂商
特定
硬件
功能
必须
如何
贡献、
结构化
和
在
Zephyr
项目
内
暴露。
它
确保
Zephyr
的
公共
API
表面
保持
稳定，
厂商
扩展
不
绕过
标准
API
生命周期，
以及
潜在
的
跨
厂商
功能
有
清晰
的
路径
演进
为
通用
驱动
类。

除非
满足
纳入
Zephyr
正式
API
生命周期
（experimental
→
stable
→
deprecated）
所需
的
标准，
厂商
特定
API
不
应该
被
暴露
为
公共
Zephyr
接口。
固有
绑定
到
单个
SoC
或
厂商
的
功能
必须
保持
封装
在
厂商
的
SoC
目录
内。

这个
策略
为
贡献者
和
维护者
提供
一致
的
决策
模型。

指导
原则
******************

- **公共
  Zephyr
  API
  不
  应该
  包含
  厂商
  特定
  接口。**

  放在
  ``include/zephyr/``
  下
  的
  接口
  预期
  通过
  标准
  API
  生命周期
  演进。
  不
  能
  满足
  这个
  演进
  的
  厂商
  特定
  接口
  不
  应该
  被
  暴露
  为
  公共
  Zephyr
  API。

- **偏好
  通用
  方案
  而非
  厂商
  特定
  方案。**

  当
  硬件
  功能
  适用
  于
  多个
  厂商
  或
  未来
  可能
  适用
  时，
  它
  应该
  作为
  现有
  驱动
  类
  的
  部分
  或
  新
  的
  跨
  厂商
  驱动
  类
  实现。

- **厂商
  特定
  功能
  必须
  被
  封装。**

  厂商
  专用
  机制
  应该
  位于
  厂商
  的
  平台
  命名空间
  （SoC、
  开发板
  等）
  内。

- **演进
  必须
  保持
  可能。**

  放置
  不
  应该
  阻止
  后来
  将
  厂商
  特定
  实现
  提升
  为
  可
  移植
  Zephyr
  驱动
  类。

决策
过程
****************

添加
新
硬件
功能
或
厂商
特定
行为
时，
贡献者
必须
按
给定
顺序
遵循
下面
的
决策
树：

- **功能
  在
  逻辑
  上
  扩展
  现有
  驱动
  类
  吗？**

  如果
  是，
  扩展
  现有
  类；
  不
  创建
  厂商
  特定
  API。

- **功能
  可以
  变成
  跨
  厂商
  驱动
  类
  吗？**

  如果
  硬件
  概念
  不
  明显
  独特
  于
  单个
  厂商，
  或
  类似
  可能
  出现
  在
  多个
  架构
  中
  的
  模式，
  创建
  新
  驱动
  类。

- **功能
  明显
  厂商
  特定
  且
  不
  可能
  通用
  化
  吗？**

  在
  这种
  情况
  下，
  将
  头
  文件
  和
  实现
  都
  放在：

  .. code-block:: none

     soc/<vendor>/..


  这
  确保
  真正
  的
  封装、
  长期
  可
  维护性
  和
  SoC
  被
  移除
  时
  的
  干净
  移除。

  厂商
  特定
  代码
  应该
  在
  位于
  ``soc/<vendor>/include``
  下
  的
  头
  文件
  中
  实现
  和
  ``soc/<vendor>/common``
  或
  ``soc/<vendor>/<series>``
  中
  的
  代码
  中
  实现。

  这种
  接口
  将
  是
  私有
  和/或
  厂商
  内部
  的
  以
  支持
  其
  特定
  硬件
  并
  将
  被
  审查
  以
  避免
  创建
  特定
  于
  厂商
  的
  功能
  孤岛。

  使用
  这些
  接口
  的
  应用，
  鉴于
  它们
  是
  厂商
  内部
  和/或
  私有
  的，
  应该
  预期
  不
  有
  关于
  生命周期
  或
  向后
  兼容性
  的
  保证。

允许
位置
摘要
*************************

1. 扩展
   现有
   驱动
   类

   - 哪里：

     .. code-block:: none

        include/zephyr/drivers/<class>.h
        drivers/<class>/

   - 使用
     时：

     功能
     适合
     或
     扩展
     现有
     类。


2. 对
   现有
   驱动
   类
   的
   厂商
   特定
   扩展

   - 哪里：

     .. code-block:: none

        include/zephyr/drivers/<class>/
        drivers/<class>/

   - 使用
     时：

     功能
     是
     对
     现有
     类
     的
     厂商
     特定
     扩展，
     但
     核心
     概念
     不
     独特
     于
     单个
     厂商
     且
     未来
     可以
     被
     标准化。

3. 创建
   新
   驱动
   类
   （跨
   厂商）

   - 哪里：

     .. code-block:: none

        include/zephyr/drivers/<class>.h
        drivers/<class>/

   - 使用
     时：

     功能
     可以
     合理
     适用
     于
     多个
     厂商
     或
     演进
     为
     通用
     抽象。

4. 厂商
   特定、
   SoC
   本地
   代码
   （厂商
   独特
   功能
   的
   默认）

   - 哪里：

     厂商
     特定
     代码
     应该
     在
     位于
     ``soc/<vendor>/include``
     下
     的
     头
     文件
     中
     实现
     和
     ``soc/<vendor>/common``
     或
     ``soc/<vendor>/<series>``
     中
     的
     代码
     中
     实现。

   - 使用
     时：

     功能
     独特
     于
     厂商
     或
     SoC
     且
     不
     意图
     作为
     公共
     API。
