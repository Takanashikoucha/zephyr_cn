.. _design_guidelines:

API
设计
指南
#####################

Zephyr
开发
和
演进
是
一个
团队
努力，
为
了
简化
维护
和
增强，
开发
新
能力
或
接口
时
应该
遵循
一些
通用
策略。

所有
公共
API
必须
用
Doxygen
文档化。
细节
见
:ref:`doxygen_style`。

使用
回调
***************

许多
API
涉及
传递
回调
作为
参数
或
配置
结构
的
成员。
指定
回调
签名
时
应该
遵循
以下
策略：

* 第一个
  参数
  应该
  是
  指向
  与
  回调
  最
  密切
  关联
  的
  对象
  的
  指针。
  对于
  设备
  驱动
  这
  将
  是
  ``const
  struct
  device
  *dev``。
  对于
  库
  函数
  它
  可能
  是
  指向
  另一
  个
  对象
  的
  指针，
  该
  对象
  在
  提供
  回调
  时
  被
  引用。

* 下一个
  参数
  应该
  是
  特定
  于
  回调
  调用
  的
  额外
  信息，
  如
  通道
  标识符、
  新
  状态
  值、
  和/或
  消息
  指针
  后
  跟
  消息
  长度。

* 最后
  的
  参数
  应该
  是
  ``void
  *user_data``
  指针，
  携带
  允许
  共享
  回调
  函数
  定位
  处理
  回调
  所需
  额外
  材料
  的
  上下文。

当
回调
本身
通过
一个
将
被
嵌入
在
另一
个
结构
中
的
结构
提供
时，
将
``user_data``
作为
最后
参数
提供
的
例外
可能
被
允许。
这种
情况
的
示例
是
:c:struct:`gpio_callback`，
通常
定义
在
特定
于
也
定义
回调
函数
的
代码
的
数据
结构
内。
在
那些
情况
下，
回调
可以
通过
:c:macro:`CONTAINER_OF`
间接
访问
更多
上下文。

示例
========

* :c:type:`k_timer_expiry_t`
  在
  系统
  定时器
  闹钟
  触发
  时
  调用
  的
  要求
  被
  满足
  用::

    void
    handle_timeout(struct
    k_timer
    *timer)
    {
    ...
    }

  这里
  的
  假设，
  与
  :c:struct:`gpio_callback`
  一样，
  是
  定时器
  嵌入
  在
  从
  :c:macro:`CONTAINER_OF`
  可
  达
  的
  结构
  中，
  该
  结构
  可以
  为
  回调
  提供
  额外
  上下文。

* :c:type:`counter_alarm_callback_t`
  在
  计数器
  设备
  闹钟
  触发
  时
  调用
  的
  要求
  被
  满足
  用::

    void
    handle_alarm(const
    struct
    device
    *dev,
    uint8_t
    chan_id,
    uint32_t
    ticks,
    void
    *user_data)
    {
    ...
    }

  这
  提供
  更
  完整
  的
  有用
  信息，
  包括
  哪个
  计数器
  通道
  超时
  和
  超时
  发生
  时
  的
  计数器
  值，
  以及
  用户
  上下文，
  它
  可能
  或
  不
  可能
  是
  用于
  注册
  回调
  的
  :c:struct:`counter_alarm_cfg`，
  取决于
  用户
  需求。

条件
数据
和
API
*************************

API
和
库
可能
提供
在
RAM
或
代码
大小
上
昂贵
但
在
某些
应用
可以
不
使用
它们
实现
的
意义
上
可选
的
功能。
这种
功能
的
示例
包括
:kconfig:option:`捕获
时间
戳
<CONFIG_CAN_RX_TIMESTAMP>`
或
:kconfig:option:`提供
替代
接口
<CONFIG_SPI_ASYNC>`。
开发者
与
社区
协调
必须
确定
启用
功能
是否
应该
通过
Kconfig
选项
控制。

在
功能
被
确定
为
可选
的
情况
下，
应该
遵循
以下
实践。

* 只
  在
  功能
  启用
  时
  访问
  的
  任何
  数据
  应该
  在
  结构
  或
  联合
  声明
  中
  通过
  ``#ifdef
  CONFIG_MYFEATURE``
  条件
  包含。
  这
  减少
  不
  需要
  该
  能力
  的
  应用
  的
  内存
  使用。
* 只
  在
  选项
  启用
  时
  可用
  的
  函数
  声明
  应该
  无条件
  提供。
  在
  描述
  中
  添加
  注意
  函数
  只
  在
  指定
  功能
  启用
  时
  可用，
  按
  名称
  引用
  需要
  的
  Kconfig
  符号。
  在
  函数
  被
  使用
  但
  不
  启用
  的
  情况
  下，
  函数
  的
  定义
  应该
  被
  排除
  出
  编译，
  因此
  对
  不
  受
  支持
  API
  的
  引用
  将
  导致
  链接
  时
  错误。
* 当
  特定
  于
  功能
  的
  代码
  隔离
  在
  没有
  其他
  内容
  的
  源
  文件
  中，
  该
  文件
  应该
  在
  ``CMakeLists.txt``
  中
  条件
  包含::

    zephyr_sources_ifdef(CONFIG_MYFEATURE
    foo_funcs.c)
* 当
  特定
  于
  功能
  的
  代码
  是
  有
  其他
  内容
  的
  源
  文件
  的
  部分，
  功能
  特定
  代码
  应该
  用
  ``#ifdef
  CONFIG_MYFEATURE``
  条件
  处理。

如何
确保
条件
代码
对
Doxygen
可见
并
被
包括
在
公共
API
文档
中
的
细节
见
:ref:`doxygen_conditional_code`。

返回
代码
************

API
的
实现，
例如
访问
外设
的
API
可能
只
实现
最小
运行
所需
函数
的
子集。
需要
在
不
受
支持
的
API
和
未
实现
或
可选
的
API
之间
做
区分：

- 受
  支持
  但
  未
  实现
  的
  API
  应该
  返回
  ``-ENOSYS``。

- 硬件
  不
  支持
  的
  可选
  API
  应该
  被
  实现
  并
  这种
  情况
  下
  的
  返回
  代码
  应该
  是
  ``-ENOTSUP``。

- 当
  API
  被
  实现，
  但
  调用
  中
  请求
  的
  选项
  特定
  组合
  不
  能
  被
  实现
  满足
  时，
  调用
  应该
  返回
  ``-ENOTSUP``。
  （例如，
  在
  只
  支持
  边沿
  触发
  中断
  的
  硬件
  上
  请求
  电平
  触发
  GPIO
  中断）
