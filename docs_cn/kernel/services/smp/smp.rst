.. _smp_arch:

对称多处理
#########################

在多处理器架构上，Zephyr 支持使用多个运行 Zephyr 应用代码的物理 CPU。

这种支持是"对称"的，意思是默认情况下没有任何特定的 CPU 被特殊对待。任何处理器都能运行任何 Zephyr 线程，并可访问所有受支持的标准 Zephyr API。

要利用此特性，无需编写特殊的应用代码。

如果在一个受支持的双处理器设备上有两个可运行的 Zephyr 应用线程，它们将同时运行。

SMP 配置由 :kconfig:option:`CONFIG_SMP` kconfig 变量控制。

必须将其设为 "y" 才能启用 SMP 特性，否则将构建单处理器内核。

通常，平台默认会在所有受支持的地方启用它。启用后，可用的物理 CPU 数量在构建时可见于 :kconfig:option:`CONFIG_MP_MAX_NUM_CPUS`。

同样，其默认值将是平台上可用的 CPU 数量，不预期典型应用会更改它。

但出于特殊目的（例如用于测试，或为运行非 Zephyr 代码保留一个物理 CPU）将其设为较小（显然不能更大）的数量是合法的且受支持的。

同步
***************

在应用层面，核心 Zephyr IPC 和同步原语在 SMP 内核下行为完全相同。

例如，用于实现阻塞式互斥的信号量仍然是恰当的应用选择。

但在最底层，Zephyr 代码通常使用 :c:func:`irq_lock`/:c:func:`irq_unlock` 原语通过中断屏蔽实现细粒度的关键区。

这些 API 通过一个仿真层继续工作（见下文），但屏蔽技术不行：你的 CPU 在关键区内不会被中断这一事实，并不意味着另一个 CPU 不会同时运行并检查或修改相同的数据！

自旋锁
=========

SMP 系统提供更受限的 :c:func:`k_spin_lock` 原语。

它像 :c:func:`irq_lock` 一样在本地屏蔽中断，同时原子地保护一个共享锁变量，使任一时刻只有一个 CPU 进入关键区。

与旧版 IRQ 锁不同，自旋锁是可分离的（separable），且不得递归获取。

完整描述（包括票据自旋锁和 API 参考）参见 :ref:`spinlocks`。

旧版 irq_lock() 仿真
===========================

为兼容按单处理器锁 API 编写的应用，:c:func:`irq_lock` 和 :c:func:`irq_unlock` 在 SMP 系统上继续兼容工作，语义与其旧版完全相同。

它们被实现为单个全局自旋锁，带有嵌套计数，并能在上下文切换到已加锁线程时原子地重新获取。

内核将确保任一时刻所有 CPU 上只有一个线程能持有该锁，上下文切换时释放它，并在线程切入时重新获取以恢复锁状态。

其他 CPU 将自旋等待锁被释放。

然而，这一过程涉及的开销有可测量的性能影响。

与单处理器应用不同，使用 :c:func:`irq_lock` 的 SMP 应用并不是简单地调用一个非常短（通常约 1 条指令）的中断屏蔽操作。

加上 IRQ 锁是全局的，这意味着预期在 SMP 上下文中运行的代码应尽可能使用自旋锁 API。

内存一致性
================

一些多处理器架构是*缓存非一致*（cache-incoherent）的：每个 CPU 的缓存不会自动保持一致，因此一个 CPU 写入的数据在从缓存刷出之前可能对另一个 CPU 不可见。

在这样的系统上，共享的内核数据结构必须驻留在所有 CPU 都能一致观察到的内存中。

启用 :kconfig:option:`CONFIG_KERNEL_COHERENCE` 时，内核将所有共享数据放入多处理器一致（通常为非缓存）内存。

线程栈保持缓存，应用内存中显式声明为 ``__incoherent`` 的也保持缓存。

此模式仅用于运行在缓存非一致架构上的 SMP 内核，并带有隐含的 API 约定：传入内核的任何内存都被假设为缓存一致的，因此不得在非缓存区域中创建内核数据结构。

CPU 掩码
********

实时应用通常希望有意地将工作划分到各物理 CPU 上，而不是仅依赖内核调度器决定运行哪些线程。

Zephyr 提供一个由 :kconfig:option:`CONFIG_SCHED_CPU_MASK` kconfig 变量控制的 API，可以为每个线程关联一组特定的 CPU，指示它可以在哪些 CPU 上运行。

默认情况下，新线程可以在任何 CPU 上运行。

调用 :c:func:`k_thread_cpu_mask_disable` 并传入某个 CPU ID，将阻止该线程今后在该 CPU 上运行。

同样，:c:func:`k_thread_cpu_mask_enable` 将重新启用执行。

还有 :c:func:`k_thread_cpu_mask_clear` 和 :c:func:`k_thread_cpu_mask_enable_all` 两个 API 可供便捷使用。

出于显而易见的原因，对可运行线程调用这些 API 是非法的。线程必须处于阻塞或挂起状态，否则将返回 ``-EINVAL``。

三种调度器后端都支持 CPU 掩码过滤。性能影响因后端而异：

- :kconfig:option:`CONFIG_SCHED_SIMPLE` — 对运行队列进行 O(N) 线性扫描；每次上下文切换都遍历完整列表寻找第一个符合条件的线程。
- :kconfig:option:`CONFIG_SCHED_SCALABLE` — 对红黑树进行 O(N) 有序遍历；优先级顺序得以保持，但屏蔽了大量线程时可能遍历整棵树。
- :kconfig:option:`CONFIG_SCHED_MULTIQ` — 从最高优先级桶到低优先级桶扫描，并遍历每个桶的列表；最坏情况为 O(P·N)，P 为被占用的优先级级别数。

对于使用 :kconfig:option:`CONFIG_SCHED_CPU_MASK_PIN_ONLY` 的工作负载，每个 CPU 维护自己独立的运行队列，因此调度器只需检查该队列，没有掩码过滤开销。

注意 :c:func:`k_thread_cpu_mask_clear`、:c:func:`k_thread_cpu_mask_enable_all` 和 :c:func:`k_thread_cpu_mask_disable` 在 :kconfig:option:`CONFIG_SCHED_CPU_MASK_PIN_ONLY` 模式下不被允许，因为它们可能产生不是恰好一位的掩码，这违反了"每个线程恰好固定（pinned）在一个 CPU 上"的不变量。

SMP 启动过程
****************

Zephyr SMP 内核的启动与单处理器内核完全相同。

辅助 CPU 在架构层初始处于禁用状态。

所有标准内核初始化，包括设备初始化，都在其他 CPU 上线之前在单个 CPU 上完成。

在进入应用 :c:func:`main` 函数之前，内核调用 :c:func:`z_smp_init` 启动 SMP 初始化过程。

它遍历所有配置的 CPU，对每个 CPU 使用 :c:func:`arch_cpu_start` 调用架构层。

该函数接收一个用作外部 CPU 上栈的内存区域（实际上使用将成为该 CPU 中断栈的区域）、一个在该 CPU 上运行的本地 :c:func:`smp_init_top` 回调函数地址，以及一个"启动标志"地址指针，它将被用作原子信号。

随后，架构层在每个 CPU 上调用本地 SMP 初始化（:c:func:`smp_init_top`）。

注意，此时中断仍处于屏蔽状态。

该例程负责调用 :c:func:`smp_timer_init` 在定时器驱动中设置所需的状态。

在许多架构上，定时器是每 CPU 设备，需要在辅助 CPU 上进行特殊配置。

然后它（自旋）等待主线程中原子"启动标志"被释放，以保证在任何 Zephyr 应用代码运行之前所有 SMP 初始化都已完成，最后调用 :c:func:`z_swap`，通过标准调度器 API 将控制权转移给合适的可运行线程。

.. figure:: smpinit.svg
   :align: center
   :alt: SMP 初始化
   :figclass: align-center

   SMP 初始化过程示例，展示了一个包含两个 CPU 和两个应用线程同时开始运行的配置。

默认情况下，内核在此启动序列中启用所有可用 CPU。

devicetree 节点带有 ``zephyr,deferred-start`` 标志的 CPU 会被跳过并保持禁用，以便架构、SoC、板级或应用代码稍后在运行时启动它。

延迟是按 CPU 的，因此系统可以在启动时启用部分次级 CPU，其余的按需启动。

延迟 CPU 通过 :c:func:`k_smp_cpu_start` 启动，它执行完整的每 CPU 初始化。

:c:func:`k_smp_cpu_resume` 是对应的 API，用于将先前停止的 CPU 重新上线，而不重复一次性初始化。

处理器间中断
*************************

在多处理器环境中运行时，有时本地 CPU 上修改的状态需要在另一个处理器上被同步处理。

一个例子是 Zephyr 的 :c:func:`k_thread_abort` API，在被中止的线程不再可运行之前它无法返回。

如果该线程当前在另一个 CPU 上运行，实现起来就困难了。

另一个例子是低功耗空闲。

许多设备严格要求系统空闲必须使用低功耗模式实现，尽可能禁用或延迟所有中断（包括周期性定时器中断）。

如果某个 CPU 处于这种状态，而另一个 CPU 上某线程变为可运行，空闲 CPU 就没有"唤醒"以处理新可运行负载的途径。

因此，在可能的情况下，Zephyr SMP 架构应当实现处理器间中断（IPI）。

当前框架非常简单：架构至少提供一个 :c:func:`arch_sched_broadcast_ipi` 调用，调用后将在所有 CPU 上（除当前 CPU 外，尽管允许包含当前 CPU）触发一个中断。

如果架构支持定向 IPI（参见 :kconfig:option:`CONFIG_ARCH_HAS_DIRECTED_IPIS`），则架构还提供一个 :c:func:`arch_sched_directed_ipi` 调用，调用后将在指定的 CPU 上触发中断。

当某 CPU 上触发中断时，调度器中实现的 :c:func:`z_sched_ipi` 函数将在那些 CPU 上被调用。

预期这些 API 会随时间演进以涵盖更多功能（例如跨 CPU 调用），且这里的调度器专用调用将通过更通用的框架来实现。

当定向 IPI 可用时，线程变为就绪时，调度器只向确实需要再调度的 CPU 发出信号，而不是向每个其他 CPU 广播。

这避免打扰当前运行线程无需被抢占的 CPU，降低了整体中断负载。

注意，并非所有 SMP 架构都有可用的 IPI 机制（可能缺失，或仅未记录/未实现）。

在这些情况下 Zephyr 提供正确的后备行为，但可能并非最优。

借助此机制，:c:func:`k_thread_abort` 在 SMP 下仅稍微复杂一点：对于线程实际在另一个 CPU 上运行的情况（可以在调度器内部原子地检测到），我们广播一个 IPI 并自旋，等待线程变为 "DEAD" 或重新进入队列（此时我们以与单处理器模式相同的方式终止它）。

注意"被中止"检查发生在任何中断退出时，因此 IPI 本身无需特殊处理。

这允许我们在 IPI 不可用时实现合理的后备：我们只需自旋，等待外部 CPU 收到任何中断，尽管这可能时间长得多！

同样，空闲唤醒可以通过一个空 IPI 处理程序轻松实现。

如果一个线程被加入空的运行队列（即可能存在空闲 CPU），我们广播一个 IPI。

外部 CPU 随后在中断退出时就能看到新线程，并在可用时切换到它。

然而没有 IPI 时，需要中断的低功耗空闲将无法同步运行新线程。

该情况下的变通方法更具侵入性：Zephyr 将**不**进入系统空闲处理程序，而是在其空闲循环中自旋，以高频（但并非自旋于该状态上，那将涉及严重的锁竞争）测试调度器状态以发现新线程。

预期功耗受限的 SMP 应用总是提供 IPI，这段代码仅用于测试目的或无功耗要求的系统。

IPI 级联
=============

内核无法控制系统中各 CPU 处理 IPI 的顺序。

通常这不是问题，一组 IPI 就足以触发 N 个 CPU 的再调度，结果是它们调度优先级最高的 N 个就绪线程执行。

当使用 CPU 掩码时，可能存在多组有效线程集合（注意不要与"最优线程集合"混淆），可在 N 个 CPU 上调度，而一组 IPI 可能不足以产生其中任何有效集合。

.. note::
    未使用 CPU 掩码时，最优线程集合与有效线程集合相同。但使用 CPU 掩码时，可能存在多组有效集合——其中一组可能是最优的。

    为更好地说明这一区别，考虑一个 2 CPU 系统，就绪线程 T1 和 T2 优先级分别为 1 和 2。设 T2 固定在 CPU0 上，T1 未固定。如果 CPU0 正在执行 T2 且 CPU1 正在执行 T1，则该集合既有效又最优。但如果 CPU0 正在执行 T1 且 CPU1 处于空闲，则该集合也有效但非最优。

在单组 IPI 不足以产生有效集合的情况下，产生的正在运行的线程集合预期接近有效集合，且后续 IPI 通常可以很快纠正该情况。

然而对于近似度或延迟都不可接受的情况，启用 :kconfig:option:`CONFIG_SCHED_IPI_CASCADE` 将允许内核产生级联 IPI，直到内核为各 CPU 选出一组有效的就绪线程。

IPI 级联有三种相关的成本/惩罚——正因如此它们默认禁用。

第一种是产生 IPI 的 CPU 在新线程抢占旧线程时产生的成本，因为必须执行检查将旧线程与其他 CPU 上正在运行的线程进行比较。

第二种是接收 IPI 的 CPU 产生的成本，因为它们必须处理这些 IPI。

第三种是线程由于源自前述第一种成本的级联而"闪现"（winks in）随后"消失"（winks out）的明显抖动。

IPI 工作项
=============

内核允许开发者使用一个或多个 IPI 工作项在 ISR 级别于其他 CPU 上执行函数。

通过 :c:func:`k_ipi_work_add` 将 IPI 工作项添加到指定 CPU 的工作队列后，目标 CPU 在收到 IPI 后将处理它们。

发出 IPI 信号通过调用 :c:func:`k_ipi_work_signal` 完成。

等待 IPI 工作项被目标 CPU 完成通过调用 :c:func:`k_ipi_work_wait` 完成。

任一时刻只允许一个等待者。

.. note::
    IPI 工作项只会被添加到其他 CPU 的 IPI 工作队列中。如果在线程级别添加 IPI 工作项，开发者必须确保当前线程在发出 IPI 信号之前不切换 CPU。

示例用法
----------

下面的代码概述了如何使用 IPI 工作项，在一个 CPU 处理 ISR 的结果跨一组 CPU 更新状态信息。

.. code-block:: c

    struct k_ipi_work my_work;

    void remote_cpu_action(struct k_ipi_work *arg)
    {
        ...
    }

    void my_isr(void)
    {
        /*
         * Wait for previous use of <my_work> to complete.
         * It assumes that <my_work> was initialized elsewhere.
         */

        uint32_t cpu_mask = <bitmask identifying CPUs to update>;

        while (k_ipi_work_wait(&my_work, K_NO_WAIT) == -EAGAIN) {
        }

        /* Add and signal the new work */

        k_ipi_work_add(&my_work, cpu_mask, remote_cpu_action);

        k_ipi_work_signal();
    }


SMP 内核内部
********************

总体而言，Zephyr 内核代码与 SMP 无关，与应用代码一样，无论可用 CPU 数量多少都能正确工作。

但在少数领域，结构或行为有显著变化。


每 CPU 数据
=============

核心内核数据的许多元素在 SMP 模式下需要为每个 CPU 实现。

例如，``_current`` 线程指针显然需要反映本地正在运行什么，有许多线程并发运行。

同样，内核提供的中断栈需要为每个物理 CPU 创建并分配，用于检测 ISR 状态的中断嵌套计数也是如此。

这些字段现在被移入 :c:struct:`_kernel` 结构体中一个独立的 :c:struct:`_cpu` 实例，它有一个按 ID 索引的 ``cpus[]`` 数组。

为旧版单处理器代码提供兼容字段，使其能用旧的语法和汇编偏移量访问 ``cpus[0]`` 的字段。

注意，对架构层的一个重要要求是：在内核上下文中该 CPU 结构体的指针必须能快速获得。

预期 :c:func:`arch_curr_cpu` 使用 CPU 提供的寄存器或寻址模式实现，可在任意上下文切换或中断之间保存该值，并使任何内核态代码都能访问它。

类似地，在单处理器系统上 Zephyr 只需在最低优先级创建一个全局"空闲线程"，而在 SMP 中可能需要每个 CPU 一个。

这使得调度器中热路径性能环境下的内部谓词测试 "_is_idle()" 比简单地测试线程指针与某个已知静态变量相等更复杂。

在 SMP 模式下，空闲线程通过线程结构体中一个独立字段来区分。

基于 switch 的上下文切换
==============================

传统 Zephyr 上下文切换原语是 :c:func:`z_swap`。

遗憾的是，该函数不接受指定要切换到哪个线程的参数。

一直的预期是：当调度器状态最后一次被修改时，调度器已做出抢占决策，并将由此产生的"下一线程"指针缓存在架构上下文切换原语能通过简单结构体偏移量找到的位置。

该技术在 SMP 中行不通，因为另一个 CPU 可能自当前 CPU 上次退出调度器以来修改了调度器状态（例如：它可能已经在运行那个被缓存的线程了！）。

相反，SMP 的"切换到"决策必须与 swap 调用同步做出，且我们不想让每架构的汇编代码处理调度器内部状态，Zephyr 要求 SMP 系统使用较低层次的上下文切换原语。

:c:func:`arch_switch` 总是在中断屏蔽状态下被调用，且恰好接受两个参数。

第一个是不透明的（架构定义的）要切换到的上下文句柄，第二个是指向这样的句柄的指针，它应存储被切换出线程产生的句柄。

然后内核在该原语之上实现一个可移植的 :c:func:`z_swap` 实现，在架构无需理解的位置包含相关的调度器逻辑。

类似地，在中断退出时，基于 switch 的架构预期调用 :c:func:`z_get_next_switch_handle` 从调度器获取下一个要运行的线程。

:c:func:`z_get_next_switch_handle` 的参数是被中断线程的"句柄"，反映 :c:func:`arch_switch` 使用的相同不透明类型，或者如果该线程暂时还无法释放给调度器，则为 NULL。

句柄值或 NULL 之间的选择取决于 CPU 中断模式的实现方式。

拥有较大 CPU 寄存器文件的架构通常在中断时只将调用者保存寄存器保存在当前线程栈上以最小化中断延迟，只在调用 :c:func:`arch_switch` 时保存被调用者保存寄存器以最小化上下文切换延迟。

这类架构必须使用 NULL 作为 :c:func:`z_get_next_switch_handle` 的参数以确定是否有新线程要调度，如有则继续执行自己的 :c:func:`arch_switch` 或其衍生形式，否则直接退出中断模式。

在前一种情况下，由该切换代码负责在其上下文完全保存后将被切换出线程产生的句柄存储在该线程的 "switch_handle" 字段中。

进入中断模式时已保存完整线程状态的架构可以直接将该线程的句柄传递给 :c:func:`z_get_next_switch_handle`，一步完成。

注意 SMP 要求 :kconfig:option:`CONFIG_USE_SWITCH`，反之则不然。将 :kconfig:option:`CONFIG_SMP` 设为 No 构建的单处理器架构仍可能决定使用 :c:func:`arch_switch` 实现上下文切换。

线程队列排序
====================

在 SMP 系统中，当线程被更高优先级线程抢占时，它被移到其优先级级别队列的末尾。相比之下，在 UP 系统中，被抢占的线程不会移到其优先级队列末尾；它只是等待重新获得 CPU，保持其相对于其他相同优先级线程的原始顺序。
