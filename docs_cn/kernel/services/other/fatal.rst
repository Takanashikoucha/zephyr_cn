.. _fatal:

致命错误
############

由源代码触发的软件错误
****************************************

Zephyr 提供多种方法通过构建期检查、条件编译的断言，
或有意调用的 panic 或 oops 条件来触发致命错误状态。

失败的运行时断言（``ZASSERT()`` 和旧版 ``__ASSERT()``）会触发
致命错误。断言 API 的详情及其失败行为的配置方式
参见 :ref:`assert`。

内核 Oops
===========

内核 oops 是由 :c:func:`k_oops()` 调用的软件触发的致命错误。
它应用于指示应用逻辑中不可恢复的条件。

生成的致命错误原因码为 ``K_ERR_KERNEL_OOPS``。

内核 Panic
=============

内核 panic 是由 :c:func:`k_panic()` 调用的软件触发的致命错误。
它应用于指示 Zephyr 内核处于不可恢复状态。
:c:func:`k_sys_fatal_error_handler()` 的实现
在内核遇到 panic 条件时不应返回，因为整个系统需要被重置。

运行于用户模式的线程不允许调用 :c:func:`k_panic()`，
这样做会转而生成一个内核 oops。否则，生成的致命错误
原因码为 ``K_ERR_KERNEL_PANIC``。

异常
**********

虚假中断
===================

如果 CPU 在一条未通过 ``IRQ_CONNECT()`` 或 :c:func:`irq_connect_dynamic()`
安装处理程序的中断线上收到硬件中断，
内核会生成一个原因码为 ``K_ERR_SPURIOUS_IRQ()`` 的致命错误。

栈溢出
==================

如果线程向其执行栈压入的数据超过其
栈缓冲区所能提供的空间，内核可能能够检测到这种情况
并生成一个原因码为 ``K_ERR_STACK_CHK_FAIL`` 的致命错误。

如果线程运行于用户模式，栈溢出总能被捕获，
因为线程根本无权写入栈缓冲区之外的相邻
内存地址。由于这由内存保护硬件强制执行，
不存在线程原本无法写入的内存被损坏的风险。

如果线程运行于超级用户（supervisor）模式，或者
:kconfig:option:`CONFIG_USERSPACE` 未启用，
栈溢出是否被捕获取决于配置。
:kconfig:option:`CONFIG_HW_STACK_PROTECTION` 在一些
架构上受支持，能捕获超级用户模式下的栈溢出，
包括代表用户线程处理系统调用时。通常
它通过专用 CPU 特性实现，或通过紧邻栈缓冲区放置的
只读 MMU/MPU 保护区域实现。以这种方式捕获的栈溢出
可以检测到溢出，但无法保证不发生数据损坏，
应被视为影响整个系统健康的非常严重的状况。

如果平台缺乏内存管理硬件支持，
:kconfig:option:`CONFIG_STACK_SENTINEL` 是一个纯软件的栈溢出检测
特性，它周期性检查栈缓冲区末尾的哨兵值
是否被损坏。它不需要硬件支持，但
不提供任何防数据损坏的保护。由于检查通常在
中断退出时进行，溢出可能在栈实际溢出后
相当长一段时间才被检测到。

最后，Zephyr 通过 :kconfig:option:`CONFIG_STACK_CANARIES`
支持 GCC 编译器栈金丝雀（stack canaries）。
启用后，编译器会在函数栈帧中插入一个
启动时随机生成的金丝雀值，并在函数退出时
检查金丝雀是否被覆盖。如果检查失败，
编译器调用 :c:func:`__stack_chk_fail()`，其 Zephyr 实现
触发致命栈溢出错误。这种情况下的错误并不表示
整个栈缓冲区已溢出，而是当前
函数栈帧已被损坏。更多细节参见编译器文档。

默认情况下，单个启动时生成的金丝雀值由所有线程共享。
启用 :kconfig:option:`CONFIG_STACK_CANARIES_TLS` 时，金丝雀
改存于 :ref:`线程局部存储 <thread_local_storage>` 中，
使每个线程拥有自己的值，以额外的每线程初始化开销
为代价，使金丝雀的位置和值更难预测。

作为互补的加固措施，:kconfig:option:`CONFIG_STACK_POINTER_RANDOM`
在线程创建时对其初始栈指针施加一个随机偏移。
这是一种有限形式的地址空间布局随机化，
使任意给定栈帧的位置不确定，从而妨碍
某些类别的安全攻击，代价是从每个线程的栈区域
消耗最多所配置的字节数。

其他异常
================

任何其他类型的未处理 CPU 异常都会生成错误码
``K_ERR_CPU_EXCEPTION``。

致命错误处理
********************

遇到致命错误时如何处理，其策略由
:c:func:`k_sys_fatal_error_handler()` 函数的实现决定。
该函数有一个弱链接的默认实现，它调用
``LOG_PANIC()`` 转储所有待处理的日志消息，
然后无条件地以 :c:func:`k_fatal_halt()` 停止系统。

应用可以通过覆盖 :c:func:`k_sys_fatal_error_handler()`
的实现来自由定义自己的错误处理策略。
如果该实现返回，出错线程将被中止，
系统其余部分将继续运行。更多细节和约束
参见该函数的文档。
