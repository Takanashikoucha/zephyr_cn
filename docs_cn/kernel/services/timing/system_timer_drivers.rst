.. _system_timer_drivers:

系统定时器驱动
####################

本页描述内核 tick 簿记与
产生这些 tick 的硬件驱动之间
的接口。
该簿记的内核侧，
以及应用看到的一切，
在
:ref:`kernel_timing`
中
描述。

定时器驱动
=============

tick 级别的内核定时由
具有
相对
简单
API 的
定时器
驱动
驱动。

* 预期驱动
能够通过
:c:func:`sys_clock_announce`
调用
向
内核
"通知"
新
tick，
该
调用
传递
自
上次
announce
调用
（或
系统
启动）
以来
经过
的
整数
tick
数。
这些
调用
可以
在
任何
时间
发生，
但
预期
驱动
尝试
确保
（在
考虑
中断
延迟
交互
的
可行
范围
内）
它们
在
tick
边界
附近
发生
（即
不
在
tick
"中间"），
最
重要
的
是
它们
随
时间
正确
且
与
其他
计数器
和
真实
世界
时间
相比
偏斜
最小。

* 预期驱动
向
内核
提供
:c:func:`sys_clock_set_timeout`
调用，
指示
在
内核
必须
接收
announce
调用
以
触发
已
注册
超时
之前
可能
经过
多少
tick。
在
该
时刻
之前
通知
新
tick
是
合法
的
（尽管
它们
必须
正确），
但
之后
延迟
将
导致
事件
被
错过。
注意
这里
传递
的
超时
值
是
相对于
当前
时间
的
差值，
但
这
不
免除
驱动
随
时间
以
稳定
速率
提供
tick
的
要求。
此
函数
的
朴素
实现
存在
bug，
分数
tick
被
错误
"重置"
导致
时钟
偏斜。

* 预期驱动
提供
:c:func:`sys_clock_elapsed`
调用，
提供
自
上次
调用
:c:func:`sys_clock_announce`
以来
经过
了多少
tick
的
当前
指示
（与
真实
世界
时钟
相比），
内核
需要
它
来
测试
新
到达
的
超时
是否
到期。

* 驱动
可选
提供
:c:func:`sys_clock_no_timeout`
调用。
当
没有
挂起
超时
（即
超时
队列
为
空）
且
启用
:kconfig:option:`CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE`
时，
内核
在
:c:func:`sys_clock_set_timeout`
的
位置
调用
它。

  没有
  即将到来的
  tick
  通知，
  系统
  不
  关心
  精确
  运行时间
  保持，
  因此
  驱动
  可以
  做
  某些
  事情
  来
  节省
  资源。
  正常
  操作
  在
  下次
  :c:func:`sys_clock_set_timeout`
  时
  恢复；
  与
  :c:func:`sys_clock_disable`
  不同，
  这
  不是
  拆除。

  定时器*计数器*
  不得
  停止。
  :c:func:`sys_clock_cycle_get_32`
  和
  :c:func:`sys_clock_cycle_get_64`
  必须
  继续
  计数，
  好像
  该
  调用
  从未
  发生。

  .. note::

     CPU
     在
     空
     超时
     队列
     上
     继续
     运行，
     例如
     因为
     就绪
     队列
     仍
     持有
     线程，
     或
     因为
     中断
     触发。
     那些
     线程
     和
     ISR
     可能
     调用
     :c:func:`k_cycle_get_32`
     或
     :c:func:`k_busy_wait`。
     这
     限制
     了
     实现
     可以
     做
     的
     事情：
     屏蔽
     定时器
     中断
     是
     安全
     的，
     门控
     定时器
     的
     时钟
     很可能
     不
     安全。
     恰好
     什么
     是
     安全
     的
     是
     硬件
     特定
     的。

  该
  钩子
  是
  可选
  的。
  没有
  它，
  :c:func:`sys_clock_set_timeout`
  被
  要求
  其
  能
  表达
  的
  最
  长
  等待，
  ``UINT32_MAX``
  tick。
  这
  在
  数值
  上
  就是
  这里
  的
  ``K_TICKS_FOREVER``，
  长期
  的
  "无
  截止
  时间"
  信号，
  因此
  未
  转换
  的
  驱动
  继续
  工作。

* 驱动
  可选
  提供
  :c:func:`sys_clock_idle_enter`
  调用，
  电源
  管理
  路径
  在
  CPU
  即将
  进入
  低功耗
  空闲
  时
  在
  :c:func:`sys_clock_set_timeout`
  的
  位置
  使用
  它。
  它
  接收
  到
  下次
  预期
  唤醒
  的
  tick
  数，
  或
  在
  没有
  且
  运行时间
  簿记
  可以
  漂移
  时
  为
  ``SYS_CLOCK_IDLE_FOREVER``。

  将
  工作
  移交
  给
  低功耗
  唤醒
  定时器
  的
  驱动，
  或
  否则
  为
  睡眠
  重新
  配置
  自身
  的
  驱动，
  在
  这里
  这样做。
  被告知
  ``SYS_CLOCK_IDLE_FOREVER``
  时
  它
  还
  可以
  停止
  其
  时间
  基准，
  这是
  :c:func:`sys_clock_no_timeout`
  不
  允许
  的，
  因为
  CPU
  正在
  退出
  且
  :c:func:`sys_clock_idle_exit`
  保证
  在
  返回
  时
  运行。
  只有
  调用
  CPU
  进入
  空闲，
  因此
  时间
  基准
  在
  CPU
  之间
  共享
  的
  驱动
  必须
  确保
  只有
  最后
  进入
  空闲
  的
  CPU
  停止
  时钟。

  该
  钩子
  是
  可选
  的。
  没有
  它，
  :c:func:`sys_clock_set_timeout`
  被
  调用
  时
  其
  已
  弃用
  的
  ``idle``
  参数
  设置
  为
  ``true``，
  因此
  仍
  以
  该
  参数
  为
  键
  进行
  低功耗
  处理
  的
  驱动
  继续
  工作。

最后
三个
入口
点
划分
系统
可以
处于
的
四个
状态：

.. list-table::
   :header-rows: 1
   :widths: 15 45 40

   * -
     - 无
       挂起
     - 有
       挂起
   * - **运行**
     - ``sys_clock_no_timeout()``
     - ``sys_clock_set_timeout(ticks)``
   * - **空闲**
     - ``sys_clock_idle_enter(SYS_CLOCK_IDLE_FOREVER)``
     - ``sys_clock_idle_enter(ticks)``

没有
:kconfig:option:`CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE`
时
左列
从不
出现：
内核
保持
合成
截止时间
就绪
以
使
运行时间
保持
精确，
驱动
只
看到
右列。

定时器
驱动
锁
====================

内核
通过
:c:func:`sys_clock_lock`
和
:c:func:`sys_clock_unlock`
暴露
统一
定时器
锁。
此
锁
保护
内核
内部
tick
簿记
（``curr_tick``、
超时
队列）
和
任何
必须
与之
一致
的
驱动
私有
状态
（例如
硬件
周期
计数器
基准）。

维护
内部
状态
的
定时器
驱动
应
在
其
ISR
开始
时
获取
此
锁，
更新
其
硬件
状态，
然后
将
锁
键
传递
给
:c:func:`sys_clock_announce_locked`
（该
函数
消费
它）。
这
确保
驱动
的
周期
计数器
基准
和
内核
的
``curr_tick``
始终
在
同一
锁
下
更新，
消除
使用
两个
分离
锁
时
在
SMP
系统
（或
较少
常见
地，
在
需要
一致
实时
参考
的
更高
优先级
ISR
的
UP
系统）
上
可能
出现
的
竞态
条件。

驱动
提供
的
回调
:c:func:`sys_clock_set_timeout`
和
:c:func:`sys_clock_elapsed`
始终
由
内核
在
已
持有
此
锁
时
调用。

为
向后
兼容，
:c:func:`sys_clock_announce`
仍
可用
且
内部
获取
锁。
新
和
已
迁移
的
驱动
应
优先
使用
:c:func:`sys_clock_lock`
/
:c:func:`sys_clock_announce_locked`
模式。

注意
此
API
的
自然
实现
导致
"无
tick"
内核，
仅
为
已
注册
事件
接收
和
处理
定时器
中断，
依赖
可
编程
硬件
计数器
提供
不规则
中断。
但
传统
的
"有
tick"
或
"简单"
计数器
驱动
也
可以
轻松
实现：

* 驱动
可以
以
对应
OS
tick
速率
的
规则
速率
接收
中断，
每次
调用
:c:func:`sys_clock_announce`
参数
为
一。

* 驱动
可以
忽略
:c:func:`sys_clock_set_timeout`
调用，
因为
无论
超时
状态
如何
每个
tick
都
会
被
通知。

* 驱动
可以
对
每次
:c:func:`sys_clock_elapsed`
调用
返回
零，
因为
最多
只能
检测到
一个
tick
已经
经过
（否则
会
收到
中断）。

SMP
细节
===========

一般
来说，
上述
定时器
API
在
多
处理器
上下文
中
运行
时
不
变。
内核
内部
适当
同步
所有
访问，
确保
所有
关键
区段
小
且
最小。
但
某些
说明
重要
到
需要
详细
说明：

* Zephyr
  对
  哪个
  CPU
  服务
  定时器
  中断
  不
  敏感。
  所有
  定时器
  中断
  在
  单个
  处理器
  上
  处理
  不
  违反
  规则
  （尽管
  在
  某些
  情况
  下
  可能
  不
  期望）。
  现有
  SMP
  架构
  实现
  对称
  定时器
  驱动。

* 预期
  :c:func:`sys_clock_announce`
  调用
  在
  驱动
  级别
  全局
  同步。
  内核
  不
  做
  任何
  每
  CPU
  跟踪，
  预期
  如果
  两个
  定时器
  中断
  几乎
  同时
  触发，
  只有
  一个
  将
  向
  定时
  子系统
  提供
  当前
  tick
  计数。
  另一个
  可以
  合法
  提供
  零
  tick
  计数
  如果
  没有
  tick
  经过。
  它
  不
  应
  因为
  时间
  切片
  要求
  "跳过"
  announce
  调用
  （请参阅
  :ref:`kernel_timing`
  中
  的
  时间
  切片
  说明）。

* 某些
  SMP
  硬件
  使用
  单一
  全局
  定时器
  设备，
  其他
  使用
  每
  CPU
  计数器。
  这里
  的
  复杂
  性
  （例如：
  确保
  CPU
  之间
  计数器
  同步）
  预期
  由
  驱动
  管理，
  而
  非
  内核。

* 通过
  :c:func:`sys_clock_set_timeout`
  传回
  驱动
  的
  下一
  超时
  值
  对
  每个
  CPU
  完全
  相同。
  因此
  默认
  情况下，
  每个
  CPU
  将
  为
  每个
  事件
  看到
  同时
  的
  定时器
  中断，
  尽管
  按
  定义
  只有
  一个
  应
  看到
  非
  零
  tick
  参数
  的
  :c:func:`sys_clock_announce`。
  这
  可能
  是
  时间
  敏感
  应用
  的
  正确
  默认
  （因为
  它
  最小化
  错误
  ISR
  或
  中断
  锁
  延迟
  超时
  的
  机会），
  但
  在
  某些
  情况
  下
  可能
  是
  性能
  问题。
  当前
  设计
  预期
  任何
  此类
  优化
  是
  定时器
  驱动
  的
  责任。

通用
无
tick
核心
=====================

上述
工作，
周期
到
tick
转换、
announce
基准、
tick
对齐
截止时间
计算
和
计数器
回绕
和
范围
处理，
在
每个
无
tick
驱动
中
几乎
相同，
手工
编写
的
变体
是
定时器
bug
的
反复
来源。
:zephyr_file:`drivers/timer/system_timer_generic.h`
一次
承载
该
逻辑。

它
是
实现
头
文件，
不
是
声明
头
文件：
包含
它
*定义*
:c:func:`sys_clock_set_timeout`、
:c:func:`sys_clock_elapsed`
和
:c:func:`sys_clock_cycle_get_32`
/
:c:func:`sys_clock_cycle_get_64`。
任意
数量
的
驱动
可以
基于
它
构建；
每个
包含
一次，
在
提供
以下
宏
和
原语
之后。
构建
编译
单个
系统
定时器
驱动，
因此
那些
定义
落
一次。
驱动
然后
只
以
周期
工作；
核心
拥有
tick
域。

核心
发出
两个
周期
获取器，
64 位
的
无论
计数器
宽度
如何：
announce
基准
是
64 位，
链接器
在
没有
调用
它的
地方
丢弃
获取器。

驱动
是否
也
选择
:kconfig:option:`CONFIG_TIMER_HAS_64BIT_CYCLE_COUNTER`
仍
是
其
自己
的
决定。
该
选项
表示
64 位
读取
廉价，
或
至少
不
比
32 位
读取
更
昂贵，
因此
优先
选择
更
窄
的
获取器
没有
收益。
在
``TIMER_CORE_COUNTER_NONATOMIC``
下
两者
都
通过
时钟
锁
且
这
成立；
在
原子
计数器
窄于
64 位
时
只有
64 位
获取器
获取
锁，
32 位
的
保持
无
锁
读取。

需要
两个
原语：
``timer_driver_cycle_get()``
（读取
硬件
周期
计数器）
和
一个
就绪
函数
``timer_driver_set_compare()``
或
``timer_driver_set_reload()``
（取决于
后端）。
驱动
的
ISR
确认
硬件
然后
调用
``timer_core_announce()``，
其
init
连接
IRQ
然后
调用
``timer_core_init()``，
在
SMP
上
其
``smp_timer_init()``
调用
``timer_core_smp_prime()``。

后端
选择
-----------------

恰好
一个
说明
硬件
是
什么：

``TIMER_CORE_BACKEND_COMPARE_ORDERED``
   绝对
   比较器，
   有序
   匹配：
   计数器
   达到
   或
   超过
   编程
   值
   后
   中断
   触发，
   因此
   已
   在
   过去
   的
   截止时间
   立即
   触发。
   可用
   范围
   是
   计数器
   宽度
   的
   一半。

``TIMER_CORE_BACKEND_COMPARE_EXACT``
   绝对
   比较器，
   相等
   匹配：
   计数器
   超过
   后
   写入
   的
   值
   在
   整个
   计数器
   周期
   内
   被
   错过。
   核心
   通过
   验证
   循环
   写入
   比较器，
   因此
   驱动
   不
   需要
   自己
   的
   最小
   延迟
   下限。

``TIMER_CORE_BACKEND_RELOAD``
   相对
   延迟：
   倒
   计数
   和
   比较
   匹配
   重置
   周期
   定时器。
   假设
   自动
   重新
   加载，
   因此
   有
   tick
   内核
   从
   init
   时
   设置
   的
   值
   自由
   运行。

可选
宏
---------------

每个
仅
在
默认
值
（见
下方）
不
适合
时
定义：

``TIMER_CORE_CYCLES_PER_SEC``
   计数器
   速率，
   单位
   Hz。
   默认
   为
   内核
   系统
   时钟
   速率。
   在
   计数器
   预
   缩放
   或
   以
   自己
   固定
   速率
   运行
   时
   设置
   它。
   核心
   从
   它
   派生
   ``TIMER_CORE_CYC_PER_TICK``，
   驱动
   可以
   读取
   用于
   自己
   的
   硬件
   设置
   （通常
   是
   init
   时
   编程
   的
   一个
   tick
   周期），
   但
   永远
   不
   自己
   定义。

``TIMER_CORE_CYCLES_PER_SEC_RUNTIME``
   上述
   速率
   是
   变量，
   不
   是
   构建
   时
   常量，
   因为
   它
   从
   时钟
   控制器
   读取
   或
   在
   init
   时
   计算。
   核心
   然后
   一次
   预
   计算
   每
   tick
   周期数
   而
   不
   依赖
   除法
   折叠。
   变量
   必须
   在
   调用
   ``timer_core_init()``
   之前
   保持
   其
   最终
   值。
