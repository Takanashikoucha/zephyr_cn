.. _kernel_timing:

内核定时
#############

Zephyr 提供了一个健壮且可扩展的定时框架，
用于从任意精度的硬件定时源
报告和跟踪定时事件。

时间单位
==========

内核时间以若干单位跟踪，用于不同
用途。

实时值，通常以毫秒或微秒指定，
是面向应用代码的默认时间呈现方式。
它们的优点是普遍可移植且被广泛
理解，尽管它们可能不完全匹配底层
硬件的精度。

内核通过 :c:func:`k_cycle_get_32`
和 :c:func:`k_cycle_get_64` API 呈现"周期"计数。
其意图是该计数器
代表操作系统能够
呈现给用户的最快周期计数器（例如，CPU 周期计数器），
且读取操作非常快。
预期非常敏感的应用
代码可能以轮询方式使用它
以获得最大精度。
该计数器的频率可从
:c:func:`sys_clock_hw_cycles_per_sec` 获取。在大多数
平台上，这是一个运行时
常量，求值为 :kconfig:option:`CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC`
，并在系统生命周期内固定。在
系统
定时器频率
不固定的
平台上，
:c:func:`sys_clock_hw_cycles_per_sec`
返回
运行时
值，
应用
代码
必须
不
假设
单一
不可变
频率。

运行时系统定时器频率
------------------------------

某些平台需要在运行时
获取
系统
定时器
频率，
要么
因为
定时器
驱动
从
硬件
发现
时钟
速率，
要么
因为
定时器
时钟
速率
在
启动
后
可能
变化。

可以在
运行时
更改
活动
系统
定时器
频率的
平台
必须
启用
:kconfig:option:`CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE`
并：

* 在
应用
时钟
更改
后
调用
:c:func:`z_sys_clock_hw_cycles_per_sec_update`。
* 如果
系统
定时器
驱动
缓存
派生
常量
（例如
每
tick
周期数）
或
在
时钟
变化
时
需要
重新
编程
硬件，
提供
定时器
驱动
对
:c:func:`z_sys_clock_hw_cycles_per_sec_update`
的
覆盖。

:c:func:`z_sys_clock_hw_cycles_per_sec_update`
的
默认
实现
仅
更新
存储的
频率
值。

.. note::

   :kconfig:option:`CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE`
   将
   系统
   定时器
   频率
   跟踪
   为
   单一
   **全局**
   值。
   它
   不
   兼容
   每
   CPU
   频率
   缩放
   配置，
   在
   该
   配置
   中
   不同
   CPU
   可能
   观察
   到
   不同
   的
   系统
   定时器
   频率。

   启用
   时，
   :c:func:`sys_clock_hw_cycles_per_sec`
   和
   时间
   单位
   转换
   遵循
   当前
   运行时
   值。

对于
异步
计时，
内核
定义
了
"tick"
概念。
一个
"tick"
是
内核
执行
所有
内部
运行时间
和
超时
簿记
的
内部
计数。
中断
预期
在
可能
的
范围内
在
tick
边界
处
递送，
且
不
跟踪
分数
tick。
tick
速率
的
选择
可
通过
:kconfig:option:`CONFIG_SYS_CLOCK_TICKS_PER_SEC`
配置。
大多数
硬件
平台
（支持
设置
任意
中断
超时的
平台）
的
默认
值
预期
在
10 kHz
范围
内，
软件
仿真
平台
和
遗留
驱动
使用
更
传统
的
100 Hz
值。

转换
----------

Zephyr
提供
了
一个
广泛
枚举
的
转换
库，
带
舍入
控制，
覆盖
所有
时间
单位。
任何
"ms"
（毫秒）、
"us"
（微秒）、
"tick"
或
"cyc"
单位
可以
转换
为
任何
其他
单位。
提供
了
舍入
控制，
每个
转换
可
用
于
"floor"
（向下
舍入
到
最近
的
输出
单位）、
"ceil"
（向上
舍入）
和
"near"
（舍入
到
最近）。
最后，
输出
精度
可以
指定
为
32
或
64
位。

例如：
:c:func:`k_ms_to_ticks_ceil32`
将
毫秒
输入
值
转换
为
下一个
更高
的
tick
数，
返回
截断
到
32
位
精度的
结果；
而
:c:func:`k_cyc_to_us_floor64`
将
测量
的
周期
计数
转换
为
经过
的
微秒
数，
具有
完整
64
位
精度。
完整
的
转换
例程
枚举
请参阅
参考
文档。

在
大多数
平台上，
各
计数器
速率
互为
整数
倍
且
输出
适合
单个
字
时，
这些
转换
展开
为
2-4
操作
序列，
仅
在
实际
需要
且
请求
时
要求
完整
精度。

.. _kernel_timing_uptime:

运行时间
=======

内核
代表
应用
跟踪
系统
运行时间
计数。
这
随时
可
通过
:c:func:`k_uptime_get`
获取，
提供
自
系统
启动
以来
的
毫秒
运行时间
值。
这
预期
是
大多数
可移植
应用
代码
使用
的
工具。

内部
跟踪
然而
是
64 位
整数
tick
计数。
具有
精确
定时
需求
（愿意
做
自己
的
可移植
实时
单位
转换
的）
应用
可
通过
:c:func:`k_uptime_ticks`
访问
此
计数。

:c:func:`k_uptime_delta`
可以
用于
获取
参考
时间
与
当前
时间
之间
经过
的
时间。
参考
时间
将
更新
为
当前
运行时间，
以
方便
计算
下一个
经过
时间。


超时
========

Zephyr
内核
提供
许多
带
"timeout"
参数
的
API。
概念
上，
这
指示
事件
将
发生
的
时间。
例如：

* 内核
阻塞
操作
如
:c:func:`k_sem_take`
或
:c:func:`k_queue_get`
可能
提供
超时，
超时
后
如果
没有
可用
数据
例程
将
返回
错误
代码。

* 内核
:c:struct:`k_timer`
对象
必须
为其
持续时间和
周期
指定
延迟。

* 内核
:c:struct:`k_work_delayable`
API
提供
超时
参数，
指示
工作
队列
项
何时
被
添加
到
系统
队列。

所有
这些
值
使用
:c:type:`k_timeout_t`
值
指定。
这是
一个
不透明
结构
类型，
必须
使用
内核
超时
宏
系列
之一
初始化。
最
常见
的
:c:macro:`K_MSEC`
定义
当前
时间
之后
的
毫秒
时间。

相对
超时
中
"当前
时间"
的
含义
取决于
上下文：

* 在
超时
回调
内
（例如
在
传递给
:c:func:`k_timer_init`
的
到期
函数
或
传递给
:c:func:`k_work_init_delayable`
的
工作
处理程序
内）
调度
相对
超时
时，
"当前
时间"
是
当前
触发
超时
最初
被
调度
的
精确
时间，
即使
"真实
时间"
已经
前进。
这是
为了
确保
从
另一个
定时器
的
回调
中
调度
的
定时器
始终
以
相对于
触发
定时器的
精确
偏移
计算。
从而
可以
以
规则
间隔
触发
而
不
引入
随
时间
累积
的
系统
时钟
漂移。

* 从
应用
上下文
调度
超时
时，
"当前
时间"
指
内核
接收
超时
值
时
:c:func:`k_uptime_ticks`
返回
的
值。

超时
初始化
的
其他
选项
遵循
上述
单位
约定：
:c:macro:`K_NSEC()`、
:c:macro:`K_USEC`、
:c:macro:`K_TICKS`
和
:c:macro:`K_CYC()`
分别
指定
在
指定
纳秒、
微秒、
tick
和
周期
数
后
到期
的
超时
值。

:c:type:`k_timeout_t`
值的
精度
可
配置，
默认
为
32 位。
非
tick
单位
的
大
运行时间
计数
将
经历
复杂
的
回绕
语义，
因此
预期
具有
长
运行时间
的
时间
敏感
应用
将
配置
为
使用
64 位
超时
类型。

最后，
可以
将
超时
指定
为
自
系统
启动
以来
的
绝对
时间。
用
:c:macro:`K_TIMEOUT_ABS_MS`
初始化
的
超时
指示
在
系统
运行时间
达到
指定
值
后
到期
的
超时。
同样
存在
此
API
的
纳秒、
微秒、
周期
和
tick
变体。

定时
内部
================

超时
队列
-------------

所有
Zephyr
:c:type:`k_timeout_t`
事件
（使用
上述
API
指定
的）
在
单一
全局
事件
队列
中
管理。
对
事件
采取
的
操作
指定
为
请求
事件
的
子系统
提供
的
回调
函数
指针，
连同
一个
:c:struct:`_timeout`
跟踪
结构
体，
预期
嵌入
在
子系统
定义
的
数据
结构
中
（例如：
:c:struct:`wait_q`
结构
或
:c:type:`k_tid_t`
线程
结构）。

注意
通过
:c:type:`k_timeout_t`
传递
的
所有
变体
单位
在
插入
队列
时
转换
一次
为
tick。
内核
内部
没有
多次
转换
步骤，
因此
无论
存在
多少
事件
或
超时
可能
多长，
精度
都
在
tick
级别
保证。

保存
队列
的
数据
结构
在
构建
时
通过
:kconfig:option:`CONFIG_TIMEOUT_BACKEND`
选择
选定。
只有
前端
在
后端
之间
共享
（通知
路径、
SMP
重
入
处理、
相对
与
绝对
超时
规则）；
每个
后端
提供
队列
本身，
因此
集成
者
可以
将
数据
结构
匹配
到
工作
负载
而
不
触及
公共
代码。

默认
的
:kconfig:option:`CONFIG_TIMEOUT_BACKEND_DLIST`
将
事件
存储
在
按
到期
排序
的
双向
链表
中，
每个
保存
与
其
前驱
的
tick
差
计数。
插入
是
O(N)
（N
为
挂起
超时
数）：
对
典型
系统
挂起
的
几个
超时
来说
开销
不大，
但
在
许多
未决
时
扩展
性
差。
四个
替代
后端
目前
均
为
实验性，
以
额外
内存
或
行为
换取
大规模
时
更快
的
插入：

* :kconfig:option:`CONFIG_TIMEOUT_BACKEND_MINHEAP`
  将
  事件
  保持
  在
  以
  绝对
  到期
  为
  键
  的
  二叉
  最小
  堆
  中，
  使
  插入
  和
  移除
  为
  O(log N)。
  它
  需要
  64 位
  tick
  （:kconfig:option:`CONFIG_TIMEOUT_64BIT`）
  和
  固定
  容量
  堆
  （:kconfig:option:`CONFIG_TIMEOUT_HEAP_MAX_ENTRIES`，
  其
  溢出
  是
  致命
  的），
  且
  不
  保留
  同一
  tick
  到期
  超时
  的
  触发
  顺序。

* :kconfig:option:`CONFIG_TIMEOUT_BACKEND_WHEEL`
  是
  分层
  定时器
  轮，
  近
  期
  未来
  插入
  和
  移除
  O(1)，
  更
  远
  处
  有
  排序
  溢出
  列表。
  它
  有
  最大
  的
  每
  事件
  和
  静态
  占用，
  不
  保留
  同一
  tick
  触发
  顺序，
  且
  周期
  唤醒
  无
  tick
  空闲
  CPU，
  因为
  其
  下一
  超时
  估计
  受
  轮
  周期
  限制
  （其他
  后端
  避免
  的
  功耗
  代价）。

* :kconfig:option:`CONFIG_TIMEOUT_BACKEND_BUCKET`
  是
  单
  级
  分
  桶
  差
  列表，
  轮
  的
  更
  简单
  的
  亲戚。
  它
  在
  可
  调
  近
  期
  未来
  窗口
  （:kconfig:option:`CONFIG_TIMEOUT_BUCKET_LISTS`）
  内
  提供
  O(1)
  插入，
  更
  远
  处
  回退
  到
  排序
  溢出
  列表。
  它
  也
  需要
  64 位
  tick，
  但
  与
  轮
  不同，
  它
  保留
  同一
  tick
  触发
  顺序
  且
  不
  增加
  空闲
  唤醒
  代价。

* :kconfig:option:`CONFIG_TIMEOUT_BACKEND_SKIPLIST`
  是
  以
  绝对
  到期
  为
  键
  的
  Pugh
  跳
  表。
  预期
  插入
  和
  移除
  为
  O(log N)
  且
  无
  容量
  限制，
  同一
  tick
  触发
  顺序
  为
  FIFO。
  它
  需要
  64 位
  tick。
  每个
  事件
  存储
  :kconfig:option:`CONFIG_TIMEOUT_SKIPLIST_MAX_LEVEL`
  个
  前向
  指针，
  因此
  每
  事件
  RAM
  高于
  差
  列表
  或
  最小
  堆。

非
默认
后端
面向
保持
许多
并发
超时
的
系统，
尤其
是
聚集
在
近
期
未来
的
系统。
对
大多数
应用，
差
列表
仍
是
适当
的
默认。

定时器
驱动
-------------

tick
级别
的
内核
定时
由
定时器
驱动
驱动。
该
接口
及其
运行
的
锁
在
:ref:`system_timer_drivers`
中
描述。

时间
切片
------------

定时
子系统
的
辅助
工作
是
向
调度器
提供
tick
计数器，
允许
实现
线程
时间
切片。
线程
时间
切片
不能
是
超时
值，
因为
它
不
反映
全局
到期，
而是
每
CPU
值，
在
SMP
上下文
中
需要
在
每个
CPU
上
独立
跟踪。

因为
可能
没有
其他
硬件
可用
来
驱动
时间
切片，
Zephyr
复用
现有
定时器
驱动。
这意味着
当
当前
调度
的
时间
切片
线程
时，
传递给
:c:func:`sys_clock_set_timeout`
的
值
可能
被
钳制
为
小于
当前
下一
超时的
值。

保持
毫秒
API
的
子系统
-------------------------------------

一般
来说，
像
这样的
代码
将
像
应用
代码
一样
移植。
用户
的
毫秒
值
可以
按
子系统
喜欢
的
任何
方式
处理，
然后
在
呈现
给
内核
时
使用
:c:macro:`K_MSEC()`
转换
为
内核
超时。

显然
这
以
不
能
使用
新
特性
为
代价，
如
更高
精度
超时
构造
器
或
绝对
超时。
但
对
许多
需求
简单
的
子系统，
这
可能
可以
接受。

一个
复杂
点
是
:c:macro:`K_FOREVER`。
过去
可能
能
接受
此
值
到
其
毫秒
API
的
子系统
不再
能，
因为
它
不再
是
整数
类型。
这样的
代码
将
需要
使用
不同
的、
整数
值
令牌
表示
"永远"。
:c:macro:`K_NO_WAIT`
当然
也有
相同
的
类型
安全
问题，
但
由于
它
（一直
以来）
只是
数值
零，
它
有
自然
的
移植
路径。

使用
``k_timeout_t``
的
子系统
--------------------------------

理想
地，
接受
指定
等待
时间
的
"timeout"
参数
的
代码
应该
在
可能
时
使用
内核
原生
抽象。
但
:c:type:`k_timeout_t`
是
不透明
的，
在
应用
检查
之前
需要
转换。

某些
转换
是
简单
的。
需要
测试
:c:macro:`K_FOREVER`
的
代码
可以
简单
使用
:c:macro:`K_TIMEOUT_EQ()`
宏
测试
不透明
结构
的
相等性
并
采取
特殊
操作。

更
复杂
的
情况
是
子系统
需要
接受
超时
并
循环，
等待
其
完成
同时
做
某些
处理，
该
处理
可能
需要
底层
内核
代码
上
的
多个
阻塞
操作。
例如，
考虑
此
设计：

.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
    {
        while (true) {
            uint32_t start = k_uptime_get_32();

            if (is_event_complete(obj)) {
                return;
            }

            /* Wait for notification of state change */
            k_sem_take(obj->sem, timeout_in_ms);

            /* Subtract elapsed time */
            timeout_in_ms -= (k_uptime_get_32() - start);
        }
    }

此
代码
要求
检查
超时
值，
这
不再
可能。
对
这样的

新
API

:c:func:`sys_timepoint_calc`
和
:c:func:`sys_timepoint_timeout`

.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
    {
        /* Compute the end time from the timeout */
        k_timepoint_t end = sys_timepoint_calc(timeout);

        do {
            if (is_event_complete(obj)) {
                return;
            }

            /* Update timeout with remaining time */
            timeout = sys_timepoint_timeout(end);

            /* Wait for notification of state change */
            k_sem_take(obj->sem, timeout);
        } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
    }
