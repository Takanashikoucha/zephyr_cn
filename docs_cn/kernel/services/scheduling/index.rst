调度
##########

内核的基于优先级的调度器允许应用的线程共享 CPU。

概念
********

调度器决定在任何给定时刻允许哪个线程
执行；该线程被称为**当前线程**（current thread）。

在若干时间点，调度器会获得改变
当前线程身份的机会，即
调度器将 CPU 的执行从一个线程
切换到另一个线程。这些点被称为**再调度点**（reschedule points）。
一些潜在的再调度点包括：

- 线程从运行状态迁移到挂起或等待
  状态，例如通过 :c:func:`k_sem_take` 或 :c:func:`k_sleep`。
- 线程迁移到 :ref:`就绪状态 <thread_states>`，例如
  通过 :c:func:`k_sem_give` 或 :c:func:`k_thread_start`
- 中断处理完成后返回线程上下文
- 运行中的线程调用 :c:func:`k_yield` 时

线程**睡眠**（sleeps）是指它自愿发起一个使其
迁移到挂起或等待状态的操作。

每当调度器改变当前线程的身份，
或当前线程的执行被 ISR 取代时，
内核首先保存当前线程的 CPU 寄存器值。
当该线程稍后恢复执行时，
这些寄存器值会被恢复。


调度算法
===================

内核的调度器选择优先级最高的就绪线程
作为当前线程。当存在多个相同优先级的就绪线程时，
调度器选择等待时间最长的那个。

线程的相对优先级主要由其静态优先级决定。
不过，当同时启用了最早截止时间优先调度
（:kconfig:option:`CONFIG_SCHED_DEADLINE`）且一组线程的
静态优先级相等时，截止时间更早的线程
被视为具有更高优先级。因此，启用
最早截止时间优先调度后，只有当两个线程
的静态优先级和截止时间都相等时，
它们才被视为具有相同优先级。例程
:c:func:`k_thread_deadline_set` 用于设置线程的截止时间。

.. note::
    ISR 的执行优先于线程执行，
    因此除非中断已被屏蔽，当前线程的执行
    随时可能被 ISR 取代。这对
    协作式线程和抢占式线程都适用。


内核可以以若干就绪队列
实现方案之一来构建，在代码大小、常数因子
运行时开销，以及线程数量增多时的
性能扩展性之间提供不同的权衡选择。

* 简单链表就绪队列（:kconfig:option:`CONFIG_SCHED_SIMPLE`）

  调度器就绪队列实现为一个简单的无序链表，
  单线程时具有非常快的常数时间性能，且代码量非常小。
  应将其用于代码空间受限、
  在任何时刻队列中可运行线程数量
  都不会超过少数几个（3 个左右）的系统。
  在大多数平台（未在其他地方使用红黑树的平台）上，
  这可节省约 2k 的代码量。

* 红黑树就绪队列（:kconfig:option:`CONFIG_SCHED_SCALABLE`）

  调度器就绪队列实现为一棵红黑树。
  其常数时间的插入和移除开销
  相对较慢，且在大多数
  平台（未在其他地方使用红黑树的平台）上
  需要额外约 2kb 的代码。其运行行为可以
  干净利落地扩展到成千上万个线程。

  适用于需要大量并发可运行线程（20 个
  或更多）的应用。大多数应用
  不需要这种就绪队列实现。

* 传统多队列就绪队列（:kconfig:option:`CONFIG_SCHED_MULTIQ`）

  选中后，调度器就绪队列实现为
  经典/教科书式的列表数组，
  每个优先级一个。

  这对应 Zephyr 1.12 之前版本
  使用的调度器算法。

  与"简单"调度器相比，它只引入极小的代码量
  开销，且在几乎所有情况下都以极小的常数因子
  运行于 O(1) 时间。但它
  需要相当可观的 RAM 预算来存储这些链表头，
  且其有限的功能使其与需要
  对线程进行更精细排序的功能（如截止时间调度）
  以及需要遍历线程列表的 SMP 亲和性
  不兼容。

  线程数量较少的典型应用
  可能更适合简单调度器。


IPC 原语中用于让线程挂起以便稍后唤醒的
wait_q 抽象，与调度器共享相同的后端
数据结构选择，并可使用相同的选项。

* 可扩展的 wait_q 实现（:kconfig:option:`CONFIG_WAITQ_SCALABLE`）

  选中后，wait_q 使用平衡树实现。
  如果预期会有大量线程
  等待在单个原语上，请选择此项。
  如果应用其他位置未使用红黑树，
  相比 :kconfig:option:`CONFIG_WAITQ_SIMPLE`（可能与
  :kconfig:option:`CONFIG_SCHED_SCALABLE` 共享）
  代码量增加约 2kb，且对"小型"
  队列的挂起/解挂起（pend/unpend）操作会
  稍慢一些（尽管这通常不是
  性能关键路径）。

* 简单链表 wait_q（:kconfig:option:`CONFIG_WAITQ_SIMPLE`）

  选中后，wait_q 使用双向链表实现。
  如果预期只有少量线程
  阻塞在单个 IPC 原语上，请选择此项。

协作式时间片
========================

协作式线程一旦成为当前线程，
它会一直保持当前线程身份，
直到执行某个使其不再就绪的动作。
因此，如果协作式线程执行耗时较长的计算，
可能导致其他线程（包括
优先级更高和优先级相同的线程）的调度
出现不可接受的延迟。


  .. image:: cooperative.svg
     :align: center

为克服这类问题，协作式线程可以主动地
不时让出 CPU，以便其他线程执行。
线程可以通过两种方式让出 CPU：

* 调用 :c:func:`k_yield` 将该线程放到调度器
  就绪线程优先级列表的末尾，然后调用调度器。
  之后，所有优先级高于或等于
  让出线程的就绪线程都被允许执行，
  之后才重新调度让出线程。如果不存在
  这样的就绪线程，调度器立即
  重新调度让出线程而不进行上下文切换。

* 调用 :c:func:`k_sleep` 使线程在指定
  时间段内不再就绪。之后*所有*优先级
  的就绪线程都被允许执行；
  但是，不保证优先级低于
  睡眠线程的线程在睡眠线程再次
  变为就绪之前一定被调度。

抢占式时间片
=======================

抢占式线程一旦成为当前线程，
它会一直保持当前线程身份，
直到某个更高优先级线程变为就绪，
或该线程执行某个使其不再就绪的动作。
因此，如果抢占式线程执行耗时较长的计算，
可能导致其他线程（包括
优先级相同的线程）的调度
出现不可接受的延迟。


  .. image:: preemptive.svg
     :align: center

为克服这类问题，抢占式线程可以执行
协作式时间片（如上所述），
或者可以使用调度器的时间片功能
允许其他相同优先级的线程执行。

.. image:: timeslicing.svg
   :align: center

.. note::
   对于 SMP，行为与上述 UP 图类似，
   只是线程 1 不会紧随线程 4 之后。
   而是线程 2、线程 3、线程 1、……

调度器将每个 CPU 上的时间划分为一系列
**时间片**，时间片以系统时钟滴答（tick）
计量。时间片大小可配置，
且该大小可以在应用运行期间更改。
调度一个新线程会使时间片定时器
被重置。

每个时间片结束时，调度器检查
当前线程是否可抢占，如果是，
则代表该线程隐式调用 :c:func:`k_yield`。
这让其他相同优先级的就绪线程
有机会在当前线程再次被调度之前执行。
如果没有其他相同优先级的就绪线程，
当前线程保持当前线程身份。

优先级高于指定上限的线程
豁免抢占式时间片，
永远不会被相同优先级的线程抢占。
这允许应用仅在对时间敏感度
较低的较低优先级线程之间
使用抢占式时间片。

.. note::
   内核的时间片算法*不*保证一组
   相同优先级的线程获得公平的 CPU 时间份额，
   因为它不测量线程实际获得执行的时间量。
   但该算法*确实*保证线程
   不会在未让出的情况下连续执行
   超过单个时间片。

每线程时间片
=======================

通过 :c:func:`k_sched_time_slice_set` 配置的时间片
全局适用于给定优先级及以下的所有可抢占线程。
启用 :kconfig:option:`CONFIG_TIMESLICE_PER_THREAD` 后，
单个线程可以改用 :c:func:`k_thread_time_slice_set`
拥有自己的时间片。
每线程时间片优先于全局值，
并且即使对优先级高于全局时间片上限的
线程也会生效。

除时间片时长（以 tick 表示）外，
每线程时间片还注册一个回调，
内核在时间片到期时调用该回调。
该回调在中断上下文中运行，此时
受影响线程仍是当前线程，
例如可以调整该线程下一次执行的
优先级或时间片，或将其挂起。

调度器锁定
================

不希望执行关键操作期间被抢占的可抢占线程，
可以通过调用 :c:func:`k_sched_lock` 指示调度器
暂时将其视为协作式线程。
这防止了其他线程在关键操作执行期间
进行干扰。

关键操作完成后，可抢占线程必须调用
:c:func:`k_sched_unlock` 恢复其
正常的可抢占状态。

如果线程调用 :c:func:`k_sched_lock` 之后
执行了使其不再就绪的动作，
调度器会将该锁定线程切换出去
并允许其他线程执行。当该锁定线程
再次成为当前线程时，其不可抢占
状态得以保持。

.. note::
    对可抢占线程而言，锁定调度器
    比将其优先级改为负值
    来防止被抢占是更高效的方式。


.. _thread_sleeping:

线程睡眠
===============

线程可以调用 :c:func:`k_sleep` 延迟其处理
指定时间段。线程睡眠期间，
CPU 被让出，允许其他就绪线程执行。
指定延迟时间过后，线程变为就绪
并再次有资格被调度。

正在睡眠的线程可以被另一个线程使用
:c:func:`k_wakeup` 提前唤醒。
有时可以使用这种技术
让次要线程向睡眠线程发出信号，
表明某事已经发生，*而无需*线程
定义内核同步对象（如信号量）。
唤醒一个未处于睡眠状态的线程是允许的，
但没有任何效果。

.. _busy_waiting:

忙等待
=============

线程可以调用 :c:func:`k_busy_wait` 执行
``busy wait``（忙等待），
延迟其处理指定时间段，
*而不会*将 CPU 让给其他就绪线程。

当所需延迟太短，不值得让调度器
从当前线程切换到另一个线程再切回来时，
忙等待通常用于替代线程睡眠。

强制进行调度决策
=============================

线程可以通过调用 :c:func:`k_reschedule` 强制调度器
在当前 CPU 上立即做出调度决策。
从线程调用（且中断未锁定）时，
调度器立即运行；从 ISR 调用时，
决策被延迟到 ISR 退出时。

与 :c:func:`k_yield` 不同，该例程
不保证切换到相同或更高优先级的线程——
它只是要求内核根据当前状态重新评估
下一个应运行哪个线程。大多数应用
从不需要该例程。

查询可抢占性
=======================

行为依赖于是否可被抢占的代码，
可以用 :c:func:`k_is_preempt_thread` 查询当前
上下文。仅当调用者是一个线程（而非 ISR）、
线程优先级在可抢占范围内，
且线程未锁定调度器时，
才返回非零值。

相关的 :c:func:`k_can_yield` 例程报告
当前上下文是否根本能够让出
或调用阻塞 API。在
ISR、内核初始化前阶段或空闲线程等
无法让出的上下文中，它返回 false。

建议用法
**************

对设备驱动程序和其他对性能要求高的工作
使用协作式线程。

使用协作式线程实现互斥，
而无需内核对象（如互斥锁）。

使用抢占式线程，
让时间敏感的处理优先于
时间敏感度较低的处理。


配置选项
**********************

* :kconfig:option:`CONFIG_TIMESLICING`
* :kconfig:option:`CONFIG_TIMESLICE_SIZE`
* :kconfig:option:`CONFIG_TIMESLICE_PRIORITY`

.. _cpu_idle:

CPU 空闲
##########

虽然通常由空闲线程负责，但在某些特殊
应用中，线程可能希望让 CPU 进入空闲状态。

.. contents::
    :local:
    :depth: 2

概念
********

让 CPU 进入空闲状态会使内核暂停所有操作，
直到某事件（通常是中断）唤醒 CPU。
在常规系统中，空闲线程负责这项工作。
但在某些受限系统中，
可能由另一个线程承担这一职责。

实现
**************

让 CPU 进入空闲状态
===================

让 CPU 进入空闲状态很简单：调用 :c:func:`k_cpu_idle` API。
CPU 将停止执行指令，
直到某事件发生。通常，
该函数会在一个循环内被调用。
注意，在某些架构上，返回时
:c:func:`k_cpu_idle` 会无条件地解除
中断屏蔽。

.. code-block:: c

    static k_sem my_sem;

    void my_isr(void *unused)
    {
        k_sem_give(&my_sem);
    }

    int main(void)
    {
        k_sem_init(&my_sem, 0, 1);

        /* wait for semaphore from ISR, then do related work */

        for (;;) {

            /* wait for ISR to trigger work to perform */
            if (k_sem_take(&my_sem, K_NO_WAIT) == 0) {

                /* ... do processing */

            }

            /* put CPU to sleep to save power */
            k_cpu_idle();
        }
    }

以原子方式让 CPU 进入空闲状态
========================================

可能需要以原子方式先完成一些工作，
然后再让 CPU 进入空闲状态。
在这种情况下，应改用 :c:func:`k_cpu_atomic_idle`。

实际上，前面的示例中存在竞争条件：
中断可能发生在获取信号量
（发现不可用）之后、
再次让 CPU 进入空闲状态之前。
在一些系统中，这会导致 CPU 一直空闲
直到*另一个*中断发生，而该中断
可能*永远不会*到来，
从而完全挂起系统。
为防止这种情况，应使用
:c:func:`k_cpu_atomic_idle`，
如下例所示。

.. code-block:: c

    static k_sem my_sem;

    void my_isr(void *unused)
    {
        k_sem_give(&my_sem);
    }

    int main(void)
    {
        k_sem_init(&my_sem, 0, 1);

        for (;;) {

            unsigned int key = irq_lock();

            /*
             * Wait for semaphore from ISR; if acquired, do related work, then
             * go to next loop iteration (the semaphore might have been given
             * again); else, make the CPU idle.
             */

            if (k_sem_take(&my_sem, K_NO_WAIT) == 0) {

                irq_unlock(key);

                /* ... do processing */


            } else {
                /* put CPU to sleep to save power */
                k_cpu_atomic_idle(key);
            }
        }
    }


建议用法
**************

当线程除让 CPU 空闲以等待事件外，
还必须做一些实际工作时，
使用 :c:func:`k_cpu_atomic_idle`。参见上文示例。

仅当线程只负责让 CPU 空闲
（即不做任何实际工作）时，才使用 :c:func:`k_cpu_idle`，
如下例所示。

.. code-block:: c

    int main(void)
    {
        /* ... do some system/application initialization */


        /* thread is only used for CPU idling from this point on */
        for (;;) {
            k_cpu_idle();
        }
    }

.. note::
     **除非绝对必要，不要使用这些 API。**
     在常规系统中，
     空闲线程负责电源管理，包括让 CPU 空闲。
