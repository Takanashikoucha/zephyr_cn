平衡红黑树
=======================

在排序容器可能在运行时变得很大的情况下，
由于搜索列表的算法开销，列表会变得难以处理。
对于这些情况，Zephyr 提供了一个平衡树实现，
其搜索和删除操作的运行时间对于大小为 N 的树
限制在 O(log2(N))。这是使用多个学术来源
所描述的传统红黑树实现的。

红黑的 :c:struct:`rbtree` 跟踪结构体可以在
用户可访问内存的任何位置初始化。
首次使用前它应只包含零位。
无需也不需要特定的初始化 API。

与位置显式表示的列表不同，rbtree 中
节点的排序必须由用户作为谓词函数提供。
一个 :c:func:`rb_lessthan_t` 类型的函数应被赋值给
:c:struct:`rbtree` 结构体的 ``lessthan_fn`` 字段，
在任何树操作开始之前。顾名思义，
如果第一个节点参数在树所期望的排序中
"小于"第二个，该函数应返回布尔 True 值。
注意不允许"相等"，树中的节点必须有
唯一的固定顺序，算法才能正确工作。

与 slist 和 dlist 容器一样，rbtree 中的
节点表示为一个 :c:struct:`rbnode` 结构体，
存在于用户管理的内存中，通常嵌入在
树中跟踪的数据结构中。与列表代码不同，
rbnode 中的数据是完全不透明的。
用户无法提取二叉树拓扑并像
列表那样"手动"遍历树。

节点可以用 :c:func:`rb_insert` 插入到树中，
用 :c:func:`rb_remove` 删除。对树中"第一个"和"最后一个"
节点（按比较函数定义的顺序的意义）的访问
由 :c:func:`rb_get_min` 和 :c:func:`rb_get_max` 提供。
还有一个谓词 :c:func:`rb_contains`，如果
提供的节点指针作为元素存在于树中，
则返回布尔 True。如上所述，
所有这些例程都保证至多具有
与树大小成对数关系的复杂度。

提供了两种机制来枚举 rbtree 中的所有元素。
第一种 :c:func:`rb_walk` 是简单的回调实现，
调用者指定一个 C 函数指针和一个要传递给它的
无类型参数，树代码按顺序对每个节点调用该函数。
它的优点是实现非常简单，代价是
对用户来说 API 略显繁琐（与 ISO C 的
:c:func:`bsearch` 例程颇为相似）。但它是
递归实现，因此在禁止使用无界
栈技术（如递归）的环境中并不总是可用。

还提供了 :c:macro:`RB_FOR_EACH` 迭代器，
与列表的类似 API 一样，它使用嵌套代码块
而非回调，以更自然的方式遍历列表。
它也是非递归的，虽然默认需要
在栈上占用对数大小的空间（不过，
在需要时它可以配置为使用固定/最大大小
缓冲区来代替，以避免动态分配）。
与列表一样，它还有 :c:macro:`RB_FOR_EACH_CONTAINER`
变体，使用指向容器字段的指针而非
原始节点指针进行枚举。

树内部实现
--------------

如上所述，Zephyr 的 rbtree 实现是学术界
来源中普遍描述的传统红黑树。
算法的低层细节超出了本文档的范围，
因为它们符合现有惯例。本讨论仅限于
Zephyr 实现中值得注意或特有的细节。

树保证的核心不变式是：从树根到
任何叶子的路径长度不超过到任何
其他叶子路径长度的两倍。这是通过
为每个节点关联一位"颜色"——红色或黑色——
并强制执行一条规则实现的：红色子节点
不能是另一个红色子节点的子节点（即
到根的任何路径上黑色节点的数量必须相同，
且额外红色节点的数量不能超过该数量）。
该规则通过一组用于在修改后
"修复"树的旋转规则来强制执行。

.. figure:: rbtree.png
    :align: center
    :alt: rbtree 示例
    :figclass: align-center

    一个黑色高度为 2 的最大不平衡 rbtree。
    在不重新平衡的情况下，无法再在最右侧节点
    下方添加更多节点。

这些旋转在概念上实现于一个基础原语之上，
该原语在列表中"交换"两个节点的位置。
典型实现通过简单交换节点内部的
"数据"指针来实现，但由于 Zephyr 的 :c:struct:`rbnode`
是侵入式的，这行不通。Zephyr 必须包含
略显复杂的代码来处理边界情况
（例如，一个被交换的节点可以是根，
或两个节点可能已经是父/子关系）。

Zephyr rbtree 的 :c:struct:`rbnode` 结构体
只包含两个指针，代表二叉树中节点的
"左"和"右"子节点。然而，修改后
遍历树进行重新平衡，通常需要
能够"向上"从一个节点迭代的能力。
工业界的红黑树通常存储第三个
"父节点"指针用于此目的。
Zephyr 通过在向下遍历树时
在本地构建节点指针的"栈"，
并在修改时相应更新它，来避免这一需求。
因此，Zephyr rbtree 的实现
运行时空闲开销不超过 dlist。

这些特性——一个只需每个节点两个数据指针
即可工作的平衡树数据结构，且无需
任何内存分配 API 即可工作——
在工业界相当罕见，
在某种程度上是 Zephyr 独有的。
