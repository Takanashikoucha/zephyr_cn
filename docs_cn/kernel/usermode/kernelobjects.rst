内核对象
##############

内核对象可以是三类数据之一：

* 核心内核对象，例如信号量、线程、管道等。
* 线程栈，即 :c:struct:`z_thread_stack_element` 的数组，
  用 :c:macro:`K_THREAD_STACK_DEFINE()` 声明
* 属于已定义的一组子系统之一的设备驱动实例（const struct device）

已知内核对象和驱动子系统的集合在
:zephyr_file:`include/zephyr/sys/kobject.h` 中定义为 :c:enum:`k_objects`。

内核对象对用户线程是完全不透明的（opaque）。
用户线程在发起 API 调用时操作的是内核对象的地址，
但绝不能解引用这些地址，这样做会导致内存保护故障。
所有内核对象都必须放置在用户线程不可访问的内存中。

由于用户线程不能直接操纵内核对象，
对它们的所有使用都必须通过系统调用。
要在某个内核对象上执行系统调用，
系统调用处理函数会检查内核对象地址有效，
且调用线程有足够权限操作该对象。

对象上的权限也具有"对该对象的引用"的语义。
这对于某些执行临时分配的对象 API，
或本身从运行时内存池分配的对象来说很重要。

如果一个对象失去了所有引用，可能发生两个事件：

* 如果对象有关联的清理函数，可能会调用该清理函数，
  以释放对象正在使用的任何运行时分配的缓冲区。

* 如果对象本身是动态分配的，该对象的内存将被释放。

对象放置
****************

仅由超级用户（supervisor）线程使用的内核对象没有任何限制，
可以位于二进制文件的任何位置，甚至声明在栈上。
但是，为防止用户线程意外或故意破坏，
它们不得位于用户线程可直接访问的任何内存中。

要使一个静态内核对象能通过系统调用 API 被用户线程使用，
内核对象的声明方式必须满足若干条件：

* 对象必须在构建时声明为顶层全局变量，使其出现在 ELF 符号表中。
  允许声明具有静态作用域的内核对象。
  构建后脚本 :ref:`gen_kobject_list.py` 会扫描生成的 ELF 文件
  以查找内核对象，并将其内存地址放入一个内核对象元数据的特殊表中。
  内核对象可以是数组的成员，也可以嵌入在其他数据结构中。

* 内核对象必须位于为内核保留的内存中。
  它们不得位于任何用户可访问的内存分区中。

* 为内核对象保留的任何内存必须专用于该对象。
  内核对象不得是联合体（union）数据类型的成员。

被发现但不满足上述条件的内核对象，
将不会被包含在用于验证从用户模式传入的内核对象指针的生成表中。

:ref:`gen_kobject_list.py` 脚本的调试输出
在调试"某个对象为何意外未被跟踪"时可能有用。
如果以 ``--verbose`` 标志运行该脚本，
或者以详细输出方式调用构建系统，就会打印这些信息。

动态对象
***************

如果启用了 :kconfig:option:`CONFIG_DYNAMIC_OBJECTS`，
内核对象也可以在运行时分配。在这种情况下，
可以使用 :c:func:`k_object_alloc` API 从调用线程的资源池
实例化一个对象。此类分配可以用两种方式释放：

* 超级用户线程可以调用 :c:func:`k_object_free` 强制释放一个动态对象。

* 如果一个对象的引用数降为零（当没有线程对其持有权限时就会发生），
  该对象将被自动释放。用户线程可以用 :c:func:`k_object_release`
  放弃自己对某对象的权限；线程终止时，其权限会被自动清除。
  超级用户线程还可以使用 :c:func:`k_object_access_revoke`
  额外撤销另一个线程的引用。

由于权限也用于引用计数，即使权限系统的访问控制方面并未被强制执行，
超级用户线程也务必对自己正在使用的对象获取权限。

实现细节
=====================

:ref:`gen_kobject_list.py` 脚本是一个构建后步骤，
用于查找二进制文件中所有有效的内核对象实例。
它通过解析内核生成的 ELF 文件中存在的 DWARF 调试信息来完成这一工作。

任何对应内核对象且满足对象放置条件的结构体或数组实例，
其内存地址都会被放入一个由 'gperf' 工具生成的
内核对象特殊完美哈希（perfect hash）表中。
当发起系统调用、内核拿到一个可能是也可能不是有效内核对象的内存地址时，
可以通过在该表中做常量时间查找来验证该地址。

驱动是一个特殊情况。所有驱动都是 :c:struct:`device` 的实例，
但知道一个驱动属于哪个子系统很重要，
这样才能防止错误的操作，例如在传感器驱动对象上调用 UART API。
当找到一个设备结构体时，会检查其 API 指针
以确定该驱动属于哪个子系统。

该表本身将内核对象的内存地址映射到 :c:struct:`z_object` 的实例，
其中包含该对象的所有元数据。这包括：

* 一个指示该对象上权限的位域（bitfield）。
  所有线程在构建时都被分配一个数值 ID，
  用于索引对象的权限位域，以查看该线程是否对该对象有权限。
  该位域的大小由 :kconfig:option:`CONFIG_MAX_THREAD_BYTES` 选项控制，
  如果该值太低，构建系统会生成错误。
* 一个类型字段，指示这是什么类型的对象，
  即 :c:enum:`k_objects` 的某个实例。
* 该对象的一组标志。当前用于跟踪初始化状态
  以及对象是否为公共（public）对象。
* 一个额外数据字段。该字段的语义因对象类型而异，
  参见 :c:union:`z_object_data` 的定义。

运行时分配的动态对象在一个运行时红黑树中跟踪，
验证对象指针时与 gperf 表并行使用。

超级用户线程访问权限
***********************************

超级用户线程可以访问任何内核对象。
然而，超级用户线程的权限仍会被跟踪，原因有二：

* 如果超级用户线程调用 :c:func:`k_thread_user_mode_enter`，
  该线程随后将以用户模式运行，
  并保留其作为超级用户线程时已被授予的权限
  （在许多情况下，是它自己授予的）。

* 如果超级用户线程使用 :c:macro:`K_INHERIT_PERMS` 选项
  创建一个用户线程，子线程将被授予与父线程相同的权限，
  除了父线程对象本身。

用户线程访问权限
*****************************

默认情况下，创建用户线程时，它只对自己的线程对象拥有访问权限。
其他内核对象默认不可用。对它们的访问需要显式或隐式地授予。
有若干种方式可以做到这一点。

* 如果一个线程使用 :c:macro:`K_INHERIT_PERMS` 创建，
  该线程将继承父线程的所有权限，除了父线程对象本身。

* 对某对象持有权限的线程，或运行在超级用户模式的线程，
  可以通过 :c:func:`k_object_access_grant` API
  将该对象上的权限授予另一个线程。
  便利伪函数 :c:func:`k_thread_access_grant` 也可以使用，
  它接受任意数量的内核对象指针，并对每个调用
  :c:func:`k_object_access_grant`。
  被授予权限的线程，或正在被授予访问权限的对象，
  都不需要处于已初始化状态。
  如果调用者来自用户模式，
  调用者必须对内核对象和目标线程对象都持有权限。

* 超级用户线程可以使用 :c:func:`k_object_access_all_grant` API
  声明某个特定内核对象为公共对象，供所有当前和将来的线程使用。
  你必须假设任何不可信或被利用的代码随后都能访问该对象。
  请谨慎使用此 API！

* 如果一个线程使用 :c:macro:`K_THREAD_DEFINE()` 静态声明，
  则可以使用 :c:macro:`K_THREAD_ACCESS_GRANT()`
  在启动时授予该线程访问一组内核对象的权限。

一旦某线程被授予对某对象的访问权限，
就可以用 :c:func:`k_object_access_revoke` API 移除该访问。
此 API 对用户线程不可用，但用户线程可以使用
:c:func:`k_object_release` 放弃自己对某对象的权限。

超级用户线程可以使用 :c:func:`k_object_access_revoke_others`
撤销除调用者之外所有线程的访问。
在访问先前被给予一个不可信用户线程
（该线程可能又转授给其他人）的情况下，
这很有用于重置对象的权限。
此 API 还会撤销先前可能通过
:c:func:`k_object_access_all_grant` 设置的公共访问状态。

从超级用户模式发起的、用于设置内核对象权限的 API 调用，
如果该对象未被内核跟踪，将是无操作（no-op）。
从用户模式做同样的事，会导致调用线程出现致命错误。

用 :c:func:`k_object_alloc` 分配的对象，
会隐式地将已分配对象上的权限授予调用线程。

初始化状态
********************

如果对象被认为处于未初始化状态，
对内核对象的大多数操作都会失败。
必须先执行该对象相应的初始化函数。

某些对象会在启动时隐式初始化：

* 用静态初始化宏（例如信号量的 :c:macro:`K_SEM_DEFINE`）声明的内核对象，
  在构建时就处于已初始化状态。

* 设备驱动对象在其初始化函数由内核在启动过程早期运行之后，
  被视为已初始化。

如果一个内核对象是用私有静态初始化器初始化的，
超级用户线程必须在某时刻对其调用 :c:func:`k_object_init`，
否则当用户线程访问该对象时，内核会认为它未初始化。
这种情况非常罕见，通常只针对嵌入在某个更大结构体中
并静态初始化的内核对象。

.. code-block:: c

    struct foo {
        struct k_sem sem;
        ...
    };

    struct foo my_foo = {
        .sem = Z_SEM_INITIALIZER(my_foo.sem, 0, 1),
        ...
    };

    ...
    k_object_init(&my_foo.sem);
    ...


创建新的内核对象类型
********************************

在实现新的内核特性或驱动子系统时，
可能需要定义一些新的内核对象类型。
创建核心内核对象和新的驱动子系统需要不同的步骤。

创建新的核心内核对象
================================

* 在 ``scripts/build/gen_kobject_list.py`` 中，
  将该结构体的名称添加到 :py:data:`kobjects` 列表。

新结构体的实例现在应被跟踪。

创建新的驱动子系统内核对象
==========================================

所有驱动实例都是 :c:struct:`device`。
它们通过被设置为什么 API 结构体来区分。

* 在 ``scripts/build/gen_kobject_list.py`` 中，
  将新子系统的 API 结构体名称添加到 :py:data:`subsystems` 列表。

新子系统的驱动实例现在应被跟踪。
