.. _syscalls:

系统调用
############

用户
线程
以
比
监督
线程
更
缩减
的
权限
集
运行：
某些
CPU
指令
可能
不
能
使用，
且
它们
只能
访问
内存
映射
的
有限
部分。
系统
调用
（可能）
允许
用户
线程
执行
不
直接
对
它们
可用
的
操作。

在
定义
系统
调用
时，
确保
对
API
私有
数据
的
访问
仅
通过
系统
调用
接口
进行
非常
重要。
私有
内核
数据
永远
不
应
直接
向
用户
模式
线程
提供。
例如，
``k_queue``
API
被
故意
不
提供，
因为
它们
将
关于
队列
的
簿记
信息
直接
存储
在
从
用户
模式
可见
的
队列
缓冲区
中。

允许
用户
注册
在
监督
模式
下
运行
的
回调
函数
的
API
永远
不
应
作为
系统
调用
公开。
将这些
保留
为
仅
监督
模式
访问。

本节
描述
如何
声明
新
的
系统
调用
并
讨论
与
它们
相关
的
若干
实现
细节。

组件
********

所有
系统
调用
都
有
以下
组件：

* 一个
  以
  :c:macro:`__syscall`
  为
  前缀
  的
  API
  **C
  原型**。
  它
  将
  声明
  在
  ``include/``
  下
  的
  某个
  头
  文件
  或
  另一个
  ``SYSCALL_INCLUDE_DIRS``
  目录
  中。
  此
  原型
  永远
  不
  手动
  实现，
  而
  是
  由
  :ref:`gen_syscalls.py`
  脚本
  创建。
  生成
  的
  是
  一个
  内联
  函数，
  它
  要么
  直接
  调用
  实现
  函数
  （如果
  从
  监督
  模式
  调用），
  要么
  经过
  提权
  和
  验证
  步骤
  （如果
  从
  用户
  模式
  调用）。

* 一个
  **实现
  函数**，
  即
  系统
  调用
  的
  真正
  实现。
  实现
  函数
  可以
  假设
  如果
  它
  从
  用户
  模式
  调用，
  所有
  传入
  参数
  都
  已
  被
  验证。

* 一个
  **验证
  函数**，
  它
  包装
  实现
  函数
  并
  验证
  所有
  传入
  参数。

* 一个
  **解组
  函数**，
  即
  自动
  生成
  的
  处理
  程序，
  必须
  被
  用户
  源
  代码
  包含。

C
原型
***********

C
原型
代表
API
如何
从
用户
或
监督
模式
调用。
例如，
初始化
信号量：

.. code-block:: c

    __syscall void k_sem_init(struct k_sem *sem, unsigned int initial_count,
                              unsigned int limit);

:c:macro:`__syscall`
属性
非常
特殊。
对
C
编译器
来说，
它
简单
展开
为
'static
inline'。
但是
对
构建
后
:ref:`parse_syscalls.py`
脚本
来说，
它
指示
此
API
是
系统
调用。
:ref:`parse_syscalls.py`
脚本
对
函数
原型
进行
某些
解析，
以
确定
其
返回值
和
参数
的
数据
类型，
且
有
某些
限制：

* 数组
  参数
  必须
  作为
  指针
  传入，
  不
  是
  数组。
  例如，
  ``int
  foo[]``
  或
  ``int
  foo[12]``
  不
  被
  允许，
  而
  应该
  表达
  为
  ``int
  *foo``。

* 函数
  指针
  严重
  困扰
  有限
  的
  解析
  器。
  变通
  方法
  是
  先
  对
  它们
  进行
  typedef，
  然后
  在
  参数
  列表
  中
  以
  该
  typedef
  的
  术语
  表达。

* :c:macro:`__syscall`
  必须
  是
  原型
  中
  的
  第一
  个
  东西。

在
确定
要
生成
的
系统
调用
集
时
故意
不
使用
预
处理
器。
但是，
任何
生成
的
系统
调用
如果
实际
没有
定义
验证
函数
（因为
相关
特性
在
内核
配置
中
未
启用），
将
改为
指向
未
实现
系统
调用
的
特殊
验证。
API
的
数据
类型
定义
不
应
对
编译器
具有
条件
可见性。

任何
声明
系统
调用
的
头
文件
必须
包含
一个
特殊
生成
的
头
文件，
该
头
文件
包含
所有
系统
调用
的
解组
函数
定义。
该
头
文件
由
:ref:`gen_syscalls.py`
脚本
生成，
命名
为
``syscall.h``，
放置
在
与
源
头
文件
相同
的
目录
中。

实现
函数
************

实现
函数
是
系统
调用
的
真正
实现。
它
可以
假设
如果
从
用户
模式
调用，
所有
传入
参数
都
已
被
验证。
实现
函数
的
命名
约定
是
在
API
名称
前
添加
``_syscall_``
前缀。

验证
函数
************

验证
函数
包装
实现
函数
并
验证
所有
传入
参数。
验证
函数
的
命名
约定
是
在
API
名称
前
添加
``_syscall_verify_``
前缀。

验证
函数
可以
使用
以下
辅助
宏
来
验证
参数：

* :c:macro:`K_SYSCALL_OBJ()`
  验证
  内核
  对象
  参数
  的
  类型
  和
  权限。
* :c:macro:`K_SYSCALL_OBJ_INIT()`
  验证
  内核
  对象
  参数
  已
  初始化。
* :c:macro:`K_SYSCALL_OBJ_NEVER_INIT()`
  验证
  内核
  对象
  参数
  未
  初始化。
* :c:macro:`K_OOPS()`
  在
  验证
  失败
  时
  生成
  错误
  消息。
* :c:macro:`K_SYSCALL_MEMORY_READ()`
  验证
  内存
  缓冲区
  参数
  可
  读。
* :c:macro:`K_SYSCALL_MEMORY_WRITE()`
  验证
  内存
  缓冲区
  参数
  可
  写。
* :c:macro:`K_SYSCALL_MEMORY_ARRAY_READ()`
  验证
  内存
  数组
  参数
  可
  读。
* :c:macro:`K_SYSCALL_MEMORY_ARRAY_WRITE()`
  验证
  内存
  数组
  参数
  可
  写。
* :c:macro:`K_SYSCALL_VERIFY_MSG()`
  验证
  条件
  并
  在
  失败
  时
  生成
  错误
  消息。
* :c:macro:`K_SYSCALL_VERIFY`
  验证
  条件。

API
****

创建
系统
调用
验证
函数
的
辅助
宏
在
:zephyr_file:`include/zephyr/internal/syscall_handler.h`
中
提供：

* :c:macro:`K_SYSCALL_OBJ()`
* :c:macro:`K_SYSCALL_OBJ_INIT()`
* :c:macro:`K_SYSCALL_OBJ_NEVER_INIT()`
* :c:macro:`K_OOPS()`
* :c:macro:`K_SYSCALL_MEMORY_READ()`
* :c:macro:`K_SYSCALL_MEMORY_WRITE()`
* :c:macro:`K_SYSCALL_MEMORY_ARRAY_READ()`
* :c:macro:`K_SYSCALL_MEMORY_ARRAY_WRITE()`
* :c:macro:`K_SYSCALL_VERIFY_MSG()`
* :c:macro:`K_SYSCALL_VERIFY`

调用
系统
调用
的
函数
在
:zephyr_file:`include/zephyr/syscall.h`
中
定义：

* :c:func:`_arch_syscall_invoke0`
* :c:func:`_arch_syscall_invoke1`
* :c:func:`_arch_syscall_invoke2`
* :c:func:`_arch_syscall_invoke3`
* :c:func:`_arch_syscall_invoke4`
* :c:func:`_arch_syscall_invoke5`
* :c:func:`_arch_syscall_invoke6`
