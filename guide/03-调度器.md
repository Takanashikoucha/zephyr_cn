# 指南 03：线程调度源码走读

**难度：★★★**
**主题：调度算法、优先级队列、上下文切换、关键函数走读**

这是三篇指南中最难的一篇。Zephyr 的调度核心在 `kernel/sched.c`（994 行），它回答三个问题：**谁该运行**（`next_up()`）、**何时切换**（`update_cache()` + `should_preempt()`）、**怎么切过去**（`z_get_next_switch_handle()` / `z_swap()`）。本篇按"数据结构 → 选线程 → 触发切换 → 执行切换 → 线程生命周期"的顺序走读，每一步都给出带注释的代码。

前置知识：请先读完指南 02 的 3.1-3.3 节（状态位掩码、优先级空间、就绪队列三实现）。

---

## 一、数据结构全景

调度器只依赖四个全局对象：

```c
/* kernel/sched.c:36 */
struct k_spinlock _sched_spinlock;  /* 调度器自旋锁，保护一切调度状态 */

/* kernel/sched.c:41 */
__incoherent struct k_thread _thread_dummy;  /* "假线程"，占位用 */
```

加上 `include/zephyr/kernel_structs.h` 中的：

- `_kernel`（`kernel_structs.h:208-248`）：全局内核对象，含 `cpus[]`（每 CPU 一个 `_cpu_t`）、`ready_q`（就绪队列）；
- `_cpu`（`kernel_structs.h:147-204`）：每 CPU 状态，关键是 `current`（当前线程指针）与 SMP 下的 `swap_ok`（"允许协作切换"标志）；
- `_ready_q`（`kernel_structs.h:130-143`）：就绪队列，单核下带 `cache` 字段。

**单核优化的关键**：`_ready_q.cache`（`kernel_structs.h:131-134`，注释"always contains next thread to run: cannot be NULL"）。它缓存"下一个要运行的线程"，使中断返回路径能在**不碰就绪队列**的情况下判断"要不要切"。SMP 下没有这个缓存（每 CPU 的决策依赖全局队列，无法单指针表达），所以 SMP 分支明显更复杂。

`_thread_dummy` 解决一个棘手的边角：如果当前线程正被 ISR 异步 abort，而中断返回时又要做上下文切换——切向一个已死的线程会踩到被释放的内存。`_thread_dummy` 是一个"永远就绪但不会真正运行"的占位线程（`kernel/thread.c:1609` 的 `z_dummy_thread_init()` 将其状态设为 `_THREAD_DUMMY` 并 `z_current_thread_set()`）。

## 二、选谁运行：`next_up()` 走读

`kernel/sched.c:57-158` 是调度器的心脏。先读单核分支（8 行）：

```c
/* kernel/sched.c:78-86（单核分支） */
struct k_thread *thread = runq_best();

thread = metairq_preempt_recover(thread);

/* In uniprocessor mode, we can leave the current thread in
 * the queue (actually we have to, otherwise the assembly
 * context switch code for all architectures would be
 * responsible for putting it back in z_swap and ISR return!),
 * which makes this choice simple.
 */
return (thread != NULL) ? thread : _current_cpu->idle_thread;
```

逻辑极简：① 取就绪队列最高优先级线程（`runq_best()` 映射到 `priority_q.h` 的三种实现之一）；② 若元中断（metairq）抢占过某个线程，恢复它（`metairq_preempt_recover()`）；③ 队列空则跑 idle 线程。

**单核的精妙之处在注释里**：当前线程**留在队列里**不取出。为什么？因为所有架构的汇编切换代码都不负责把旧线程放回队列——如果 `next_up()` 取走了它，就没人放回去了。这个"约定"让单核路径极短。

SMP 分支（`kernel/sched.c:87-157`）复杂得多，核心思想是**"队列里的最优者"与"当前线程"再比一次**：

```c
/* kernel/sched.c:98-116（节选） */
bool queued = z_is_thread_queued(_current);
bool active = z_is_thread_ready(_current);

if (thread == NULL) {
	thread = _current_cpu->idle_thread;
}

if (active) {
	int32_t cmp = z_sched_prio_cmp(_current, thread);

	/* Ties only switch if state says we yielded */
	if ((cmp > 0) || ((cmp == 0) && !_current_cpu->swap_ok)) {
		thread = _current;
	}

	if (!should_preempt(thread, _current_cpu->swap_ok)) {
		thread = _current;
	}
}
```

注意 SMP 下 `_current` **不在队列里**（`kernel/include/run_q.h:77-84` 的注释："_current is never in the run queue until context switch on SMP configurations"），所以必须显式把两者比较：

- `cmp > 0`：当前线程优先级更高 → 继续跑当前；
- `cmp == 0` 且 `swap_ok` 为假 → 平级不切（只有显式 `k_yield()` 置了 `swap_ok` 才在同级间轮转）；
- `should_preempt()` 再兜底（见下节）。

选中非当前线程后，`kernel/sched.c:118-145` 做两件事：把 `_current` 放回队列（若它活跃且未 queued 且非 idle 且未被 metairq 抢占），把新线程从队列取出。

### 2.1 抢占判定：`should_preempt()`

`kernel/include/kthread.h:225-260`，五层判断：

```c
/* kernel/include/kthread.h:225 */
static ALWAYS_INLINE bool should_preempt(const struct k_thread *thread,
					 int preempt_ok)
{
	/* ① 显式允许（如 k_yield() 置了 swap_ok） */
	if (preempt_ok != 0) {
		return true;
	}

	/* ② 当前线程被挂起/睡眠/死亡/假线程 → 必须切 */
	if (z_is_thread_prevented_from_running(_current)) {
		return true;
	}

	/* ③ 当前线程是协作优先级，或目标是元中断 → 允许切 */
	if (thread_is_preemptible(_current) || thread_is_metairq(thread)) {
		return true;
	}

	/* ④ 非原子切换架构的边角：超时已武装 */
	if (IS_ENABLED(CONFIG_SWAP_NONATOMIC)
	    && z_is_thread_timeout_active(thread)) {
		return true;
	}

	return false;
}
```

第 ③ 层依赖 `thread_is_preemptible()`（`kernel/include/kthread.h:66-70`）：`preempt <= 0x7F` 即可抢占——协作优先级（负数）拼出的 `preempt` 值 ≥ 0x80，天然不可抢占。

### 2.2 缓存更新：`update_cache()`

`kernel/sched.c:167-193`，每次调度状态变化后调用：

```c
/* kernel/sched.c:167 */
static ALWAYS_INLINE void update_cache(int preempt_ok)
{
#ifndef CONFIG_SMP
	struct k_thread *thread = next_up();

	if (should_preempt(thread, preempt_ok)) {
#ifdef CONFIG_TIMESLICING
		if (thread != _current) {
			z_time_slice_reset(thread);
		}
#endif
		update_metairq_preempt(thread);
		_kernel.ready_q.cache = thread;
	} else {
		_kernel.ready_q.cache = _current;
	}
#else
	_current_cpu->swap_ok = preempt_ok;
#endif
}
```

单核：重算最优线程，若应抢占则更新 cache，否则 cache 保持 `_current`。`preempt_ok` 参数即"调用者是否显式让出"（`k_yield()` 传 1，普通唤醒传 0）。SMP：只更新 `swap_ok` 标志，真正的选择推迟到中断返回的 `z_get_next_switch_handle()` 里做（SMP 下 cache 机制不适用，见 2.1 的分析）。

## 三、何时触发切换：从"状态变化"到 `z_swap()`

调度器是**事件驱动**的：任何改变"谁该运行"的事件（线程就绪、挂起、优先级变化、超时到期）最终都收敛到同一个出口——`reschedule()`（`kernel/sched.c:403-411`）：

```c
/* kernel/sched.c:403 */
static void reschedule(struct k_spinlock *lock, k_spinlock_key_t key)
{
	if (resched(key.key) && need_swap()) {
		z_swap(lock, key);
	} else {
		signal_pending_ipi();
		k_spin_unlock(lock, key);
	}
}
```

两个门槛：

**① `resched()`**（`kernel/sched.c:376-383`）：只有"中断已解锁 且 不在 ISR 中"才切。ISR 中不能切（切了谁？ISR 返回后还要回到被中断的线程），所以 ISR 里只做状态变更 + 置 IPI 标志，真正的切换推迟到中断返回路径。

**② `need_swap()`**（`kernel/sched.c:389-401`）：单核下查 cache——"下一个线程 == 当前线程"就不切，**省掉一次无谓的上下文切换**：

```c
/* kernel/sched.c:395-400 */
struct k_thread *new_thread;

new_thread = _kernel.ready_q.cache;
return new_thread != _current;
```

典型触发路径（以信号量 `k_sem_give()` 唤醒为例）：

```
k_sem_give()
  → z_unpend1_no_timeout()     /* sched.c:555 取 waitq 最优者 */
    → unpend_thread_no_timeout()
    → ready_thread()           /* sched.c:218 入队 + update_cache(0) + 置 IPI */
  → reschedule()               /* 若 cache 变了且可切 → z_swap() */
```

`ready_thread()`（`kernel/sched.c:218-235`）值得注意的一点：它先查 `thread_active_elsewhere()`（`kernel/sched.c:199-216`）——SMP 下若目标线程正跑在别的 CPU 上，**本 CPU 什么都不做**，靠 IPI 让那个 CPU 自己重新调度。这是 Zephyr SMP 调度"无中心"设计的体现。

### 3.1 挂起当前线程：`z_pend_curr()`

线程主动阻塞的入口（`kernel/sched.c:522-553`），三个值得注意的细节：

```c
/* kernel/sched.c:522 */
int z_pend_curr(struct k_spinlock *lock, k_spinlock_key_t key,
	       _wait_q_t *wait_q, k_timeout_t timeout)
{
	/* ① ISR 中阻塞 pend = 编程错误，直接 panic */
	if (arch_is_in_isr()) {
		__ASSERT(false, "blocking pend from ISR context");
		k_panic();
	}
	...
	/* ② "锁交换"：拿到调度器锁，释放调用者的锁 */
	(void) z_sched_spinlock_lock();
	pend_locked(_current, wait_q, timeout);
	k_spin_release(lock);
	/* ③ 在中断仍屏蔽的状态下执行切换 */
	return z_swap_locked(key);
}
```

第 ② 步是 Zephyr 的"锁交换"惯用法：调用者（如信号量）持有自己的锁，调度器需要自己的锁；直接嵌套拿锁会死锁（唤醒路径可能反向拿两把锁），所以**先拿调度器锁再释放调用者锁**，保证全局锁序一致。第 ③ 步保证从状态变更到切换之间中断不介入——状态一致性由"关中断"而非"持锁到切换完成"来保证。

### 3.2 异步 halt：`z_thread_halt()`

suspend/abort 是**异步**操作（`kernel/sched.c:307-374`），因为目标线程可能正跑在别的 CPU 上：

```c
/* kernel/sched.c:307（节选） */
void z_thread_halt(struct k_thread *thread, k_spinlock_key_t key,
				  bool terminate)
{
	...
	struct _cpu *cpu = thread_active_elsewhere(thread);

	if (cpu != NULL) {
		/* 目标在别的 CPU 上跑：置 halting 位 + 发 IPI */
		thread->base.thread_state |= (terminate ? _THREAD_ABORTING
					      : _THREAD_SUSPENDING);
		arch_sched_directed_ipi(IPI_CPU_MASK(cpu->id));
		if (arch_is_in_isr()) {
			thread_halt_spin(thread, key);   /* ISR 中：自旋等它 */
		} else {
			add_to_waitq_locked(_current, wq); /* 线程中：挂起自己等 */
			z_swap_locked(key);
		}
		/* 等 in-flight 超时处理器完成（防 UAF） */
		while (z_try_abort_thread_timeout(thread) == -EAGAIN) {
		}
	} else {
		/* 目标未运行：直接 halt_thread() 清理 */
		halt_thread(thread, terminate ? _THREAD_DEAD : _THREAD_SUSPENDED, &key);
		...
	}
}
```

三个机制配合完成异步 halt：

1. **halting 位**（`_THREAD_ABORTING`/`_THREAD_SUSPENDING`）：目标 CPU 在 `next_up()` 开头检查（`kernel/sched.c:63-71`），发现自己正被 halt 就自我清理（`halt_thread()`）；
2. **IPI**：通知目标 CPU 尽快到调度点；
3. **等待方策略**：ISR 上下文不能睡，只能 `thread_halt_spin()`（`kernel/sched.c:285-299`，关中断自旋 + `arch_spin_relax()`）；线程上下文则把自己挂到目标的 `halt_queue` 上睡过去。

`halt_thread()`（`kernel/sched.c:856-983`）是清理逻辑：移出队列、解除 join 等待者、禁用协处理器、**若 halt 的是 `_current` 且在中断中则 dummify**（`kernel/sched.c:907-909`——把 `_current` 指向 `_thread_dummy`，防止后续切换踩到已释放内存）。

## 四、怎么切过去：`z_get_next_switch_handle()` 与 `z_swap()`

### 4.1 中断返回路径（`CONFIG_USE_SWITCH` 架构）

`kernel/sched.c:725-799`，这是**每次中断返回都执行**的函数（单核分支仅 6 行）：

```c
/* kernel/sched.c:792-798（单核分支） */
struct k_thread *next = _kernel.ready_q.cache;

z_sched_usage_switch(next);
_current->switch_handle = interrupted;
set_current(next);
return next->switch_handle;
```

配合 `kernel/include/ksched.h:80-88` 的 `z_sched_next_handle()`，单核中断返回的完整判断是：

```
中断返回
  → z_sched_next_handle(_current)
      → _current == ready_q.cache ? 不切（返回 NULL，汇编直接恢复旧上下文）
      → 否则 z_get_next_switch_handle()
          → 保存旧线程 switch_handle，更新 _current，返回新线程 switch_handle
          → 汇编 arch_switch() 用两个 handle 完成寄存器上下文交换
```

`switch_handle` 是架构相关的"已保存上下文句柄"（`include/zephyr/kernel/thread.h:359-361`），通常指向线程栈上的寄存器保存区。**"切换"在 Zephyr 里就是交换两个指针**——C 代码负责决策，汇编只做寄存器搬运，这是 Zephyr 切换延迟低（典型 <1μs）的根本原因。

SMP 分支（`kernel/sched.c:729-790`）多了：在调度锁内调 `next_up()` 做完整选择（含把旧线程放回队列，`kernel/sched.c:770-778`）、更新 `new_thread->base.cpu`、`z_sched_spinlock_transfer_owner()`（锁的所有者随线程切换转移，防止验证机制误报）。

### 4.2 线程上下文路径：`z_swap()`

`z_swap()` 声明在 `kernel/include/kswap.h`，实现分架构：多数架构有汇编版（`arch/<arch>/` 下），`CONFIG_USE_SWITCH` 架构复用 `z_get_next_switch_handle()`。其语义是"立即执行上下文切换，返回被挂起线程的 `swap_retval`"。

`z_swap_locked()` 是"已持有调度器锁"版本，`z_swap_unlocked()` 是"中断已关"版本（idle 循环用）。三者的区别只在锁/中断状态，决策逻辑相同。

### 4.3 时间片：`z_sched_yield()`

`kernel/sched.c:427-434`，`k_yield()` 的实现只有 8 行：

```c
/* kernel/sched.c:427 */
void z_sched_yield(void)
{
	k_spinlock_key_t key = z_sched_spinlock_lock();

	runq_yield();        /* 把自己移到同级队列尾部 */
	update_cache(1);     /* preempt_ok=1：显式让出 */
	z_swap_locked(key);  /* 立即切换 */
}
```

`runq_yield()` 映射到 `priority_q.h` 的三种实现：simple 版（`kernel/include/priority_q.h:135-164`）把当前线程从队列取出再按优先级重插入（可能不在尾部，因为同优先级间保持 FIFO 只需"挪到同级最后"）；rb 版（`kernel/include/priority_q.h:239-245`）删除后重新插入（`order_key` 递增保证 FIFO）；mq 版（`kernel/include/priority_q.h:345-354`）从链表头挪到链表尾。

`update_cache(1)` 的 `preempt_ok=1` 使 `should_preempt()` 无条件返回 true——即使"最优线程"还是自己（同优先级 FIFO 的下一个），也强制切换。这就是协作线程间轮转的实现。

## 五、线程生命周期与调度的交互

### 5.1 创建：从 `k_thread_create` 到入队

`kernel/thread.c:1028` 的 `k_thread_create()` → `z_setup_new_thread()`（`kernel/thread.c:905`，初始化状态为 `_THREAD_SLEEPING`）→ `thread_schedule_new()`（`kernel/include/kthread.h:51`）：

```c
/* kernel/include/kthread.h:51 */
static inline void thread_schedule_new(struct k_thread *thread, k_timeout_t delay)
{
#ifdef CONFIG_SYS_CLOCK_EXISTS
	if (K_TIMEOUT_EQ(delay, K_NO_WAIT)) {
		k_thread_start(thread);      /* 立即就绪入队 */
	} else {
		z_add_thread_timeout(thread, delay);  /* 挂超时，到期再就绪 */
	}
#endif
}
```

`k_thread_start()` 最终调 `z_ready_thread()`（`kernel/sched.c:237`）：拿调度锁 → `ready_thread()` 入队 + `update_cache(0)` + 置 IPI。

### 5.2 终止：abort 的完整链路

`k_thread_abort()`（`kernel/thread.c:1795`）→ `z_thread_abort()`（`kernel/thread.c:1776`）→ `z_thread_halt(thread, key, true)`（见 3.2 节）。目标线程真正"死掉"发生在它下次到达调度点时（`next_up()` 的自我 halt 路径）或 halt 方直接清理（目标未运行时）。`halt_thread()` 中 `_THREAD_DEAD` 分支（`kernel/sched.c:872-910`）负责：解除 join 等待者（`unpend_all(&thread->join_queue)`——让 `k_thread_join()` 的等待者醒来）、等待 in-flight 超时处理器完成（防 UAF，`kernel/sched.c:893-898` 的锁释放-重拿循环）。

### 5.3 join：等待线程终止

`kernel/thread.c:1807` 的 `k_thread_join()` 是同步原语与线程生命周期的交汇点：

```c
/* kernel/thread.c:1814-1825（节选） */
if (z_is_thread_dead(thread)) {
	ret = 0;                              /* 已死，直接成功 */
} else if (K_TIMEOUT_EQ(timeout, K_NO_WAIT)) {
	ret = -EBUSY;                         /* 非阻塞且未死 */
} else if ((thread == _current) ||
	   (thread->base.pended_on == &_current->join_queue)) {
	ret = -EDEADLK;                       /* 自 join 或重复 join */
} else {
	z_sched_add_to_waitq_locked(_current, &thread->join_queue);
	z_add_thread_timeout(_current, timeout);
	ret = z_swap_locked(key);
}
```

每个线程对象自带 `join_queue`（`include/zephyr/kernel/thread.h:269`），`halt_thread()` 终止线程时唤醒其上所有等待者。注意 `k_thread_join()` **不释放**被 join 线程的存储——存储回收由 `k_thread_abort_cleanup()`（`kernel/thread.c:1561`）或动态线程的延迟清理（`kernel/thread.c:1490` 的 `defer_thread_cleanup()`）处理。

### 5.4 优先级变更：`z_thread_prio_set()`

`kernel/sched.c:587-641`，三种情况分治：

```c
/* kernel/sched.c:592-636（节选） */
if (need_sched) {
	if (!IS_ENABLED(CONFIG_SMP) || z_is_thread_queued(thread)) {
		dequeue_thread(thread);
		thread->base.prio = prio;
		queue_thread(thread);
		if (old_prio > prio) {
			flag_ipi(ipi_mask_create(thread));  /* 优先级升高，唤醒别的 CPU */
		}
	} else {
		/* SMP 下正在运行的线程：只改优先级，不重新入队 */
		thread->base.prio = prio;
		...
	}
	update_cache(1);
} else if (z_is_thread_pending(thread)) {
	/* 等待中的线程：从 waitq 取出改完再插回（保持 waitq 有序） */
	_priq_wait_remove(&wait_q->waitq, thread);
	thread->base.prio = prio;
	_priq_wait_add(&wait_q->waitq, thread);
} else {
	thread->base.prio = prio;
}
```

第三个分支（等待中线程）容易被忽略但很重要：waitq 也是按优先级排序的（唤醒时取最优者），优先级变了必须重新定位，否则唤醒顺序错乱。

## 六、关键函数速查表

| 函数 | 位置 | 一句话职责 |

## 七、读这篇代码时的常见困惑

1. **"为什么 `_current` 有时在队列里有时不在？"**——单核：始终在（汇编不负责放回）；SMP：运行中不在（切换时才放回）。所有相关代码都有 `#ifndef CONFIG_SMP` 分支，别把两种情况混在一起读。
2. **"cache 和 `swap_ok` 什么关系？"**——它们是同一目的（避免无谓切换）在两种拓扑下的不同实现：单核用"缓存最优线程"，SMP 用"每 CPU 一个允许协作切换标志"。
3. **"IPI 在哪里发、在哪里处理？"**——发：`ready_thread()` 的 `flag_ipi()`；处理：目标 CPU 在下次中断返回/调度点 `signal_pending_ipi()` 或 `z_swap_unlocked()` 时消费。`kernel/smp/ipi.c` 是入口。
4. **"为什么 `z_sched_wake()` 要原子完成三步？"**——见 `kernel/include/ksched.h:234-249` 的注释：非原子会暴露"超时处理器抢先唤醒 → 线程带着过期返回值醒来"的窗口。
5. **"metairq 是什么？"**——元中断：优先级高于所有中断的"软件中断线程"，用于把 ISR 工作挪到线程上下文。`kernel/include/metairq.h` 与 `kernel/sched.c` 中的 `update_metairq_preempt()`/`metairq_preempt_recover()` 是它与调度器的两个接触点。

1. **选一个架构看切换的落地**：`arch/riscv/` 或 `arch/arm/` 下的 swap 汇编（约 50-100 行），把"两个 switch_handle 交换"的寄存器搬运看懂；`arch/posix/` 的 `z_swap` 实现则展示了"用信号 + setcontext 模拟切换"的另一种思路；
2. **读 `kernel/timeslicing.c`**：时间片机制如何借用超时后端实现协程间轮转；
3. **读 `kernel/smp/smp.c` + `kernel/smp/ipi.c`**：SMP 调度的"无中心"协作模型；
4. **做实验**：`native_sim` 下开 `CONFIG_THREAD_MONITOR` + `CONFIG_SCHED_THREAD_USAGE`，用 `k_thread_runtime_stats_get()` 观察你写的多线程程序的调度行为，与本文的分析对照；
5. **进阶**：`kernel/deadline.c`（EDF 截止时间调度）与 `kernel/poll.c`（多条件轮询），它们展示了"在调度器之上叠加机制"的 Zephyr 惯用法。

> 心法：调度器代码的正确读法是**"事件 → 状态变更 → 缓存更新 → 切换判定"四段式**。任何函数都问四个问题：它由什么事件触发？改了哪些状态位/队列？调没调 `update_cache()`？最后走没走 `reschedule()`/`z_swap()`？四个问题答完，函数就懂了。
