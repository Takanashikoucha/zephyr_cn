# 指南 01：如何开始读 Zephyr 源码（快速入门）

**难度：★**
**主题：Zephyr 代码库整体结构概览、从哪里开始读、阅读工具推荐、常见陷阱**

Zephyr 是一个可扩展的实时操作系统（RTOS），面向资源受限设备优化，支持 ARM（Cortex-A/R/M）、RISC-V、x86、ARC、Xtensa、MIPS 等多种架构（见 `README.rst:26-28`）。本仓库当前版本为 **4.4.99**（开发版本，见 `VERSION:1-4`），这意味着你读到的代码处于两个稳定版之间的活跃开发状态——理解这一点会影响你对"代码为什么长这样"的判断。

本篇帮你建立对代码库的**地图感**：先知道每块砖放在哪里，再决定先拆哪块。

---

## 一、目录结构说明

### 1.1 顶层地图

仓库根目录约 30 个条目，按"谁在用"可分为四类：

| 类别 | 目录/文件 | 说明 |
|---|---|---|
| **内核** | `kernel/` | 内核核心：线程、调度、同步原语、内存管理 |
| **架构适配** | `arch/` | 各 CPU 架构的移植层（`arm/`、`riscv/`、`x86/`、`posix/` 等 16 个） |
| **硬件抽象** | `boards/` `soc/` `dts/` `drivers/` | 开发板定义、SoC 支持、设备树、驱动 |
| **子系统与用户** | `subsys/` `include/` `lib/` `samples/` `tests/` | 子系统实现、公共 API 头文件、C 库、示例、测试 |
| **构建与工具** | `cmake/` `scripts/` `Kconfig*` `west.yml` | 构建系统、工具脚本、配置定义、仓库清单 |

几个关键文件的定位：

- `README.rst`：项目门面，指向文档站、示例、社区渠道；
- `AGENTS.md`：给 AI 编码代理（也适合人类贡献者）的**规则摘要**，浓缩了 `doc/contribute/` 的要点；
- `west.yml`：仓库清单，声明 Zephyr 依赖哪些 HAL 与模块仓库（Zephyr 必须在 west 工作区内构建）；
- `MAINTAINERS.yml`（约 170KB）：路径 → 维护者/评审区的映射，找"这块代码归谁管"就查它；
- `Kconfig.zephyr`（约 37KB）：全局 Kconfig 符号定义；
- `CMakeLists.txt`（约 99KB）：顶层 CMake 脚本。

### 1.2 内核目录（`kernel/`）

这是整个仓库的心脏，约 50 个文件：

```
kernel/
├── thread.c          # 线程生命周期 API（create/suspend/abort/join/yield）
├── sched.c           # 单核调度核心（994 行）
├── scheduler.c       # SMP 调度入口（139 行）
├── priority_queues.c # 红黑树比较函数实现
├── idle.c            # 空闲线程主循环
├── sleep.c           # k_sleep / k_msleep
├── sem.c / mutex.c / msg_q.c / mailbox.c / pipe.c   # 同步原语
├── work.c / system_work_q.c / deadline.c / timeslicing.c
├── kheap.c / mempool.c / mem_slab.c / mmu.c / paging/  # 内存
├── timeout*.c/h      # 超时后端（min-heap / skiplist / wheel / bucket）
├── smp/              # SMP 支持（IPI、CPU 掩码）
├── userspace/        # 用户态支持（futex、内存域）
└── include/          # 内核内部头文件（非公共 API！）
```

**特别注意**：`kernel/include/` 下的头文件（`ksched.h`、`kthread.h`、`priority_q.h` 等）是**内核内部接口**，带 `z_` 前缀；应用可见的公共 API 全部在 `include/zephyr/` 下（如 `include/zephyr/kernel.h`，约 7300 行）。读源码时混淆这两层是新手最常见的迷路原因。

### 1.3 架构目录（`arch/`）

`arch/` 下每个子目录对应一个 CPU 架构。其中 `arch/posix/` 特别重要：它让 Zephyr 能编译成 `native_sim` 在主机上运行，是你**不需要硬件就能调试内核**的关键入口。

### 1.4 子系统目录（`subsys/`）

约 50 个子系统：`bluetooth/`、`net/`、`fs/`、`logging/`、`pm/`、`shell/`、`usb/` 等。子系统构建在 kernel 之上，读内核前先搞懂 kernel 是正确顺序。

## 三、从哪里开始读

### 3.1 推荐路径（由浅入深）

```
第 1 步：README.rst + doc/introduction/
        ↓  建立"Zephyr 是什么"的直觉
第 2 步：include/zephyr/kernel_structs.h
        ↓  看懂 _thread_base / _ready_q / z_kernel 三大结构
第 3 步：kernel/thread.c 的 k_thread_create 路径
        ↓  跟着一个线程从创建到运行
第 4 步：kernel/sched.c 的 next_up / update_cache
        ↓  看懂"选谁运行"
第 5 步：arch/posix/ 下的 swap 实现
        ↓  看懂"怎么切过去"
```

### 3.2 第一个值得精读的函数：`k_thread_create`

入口在 `kernel/thread.c:1028`，只有 15 行，却是理解线程模型的钥匙：

```c
/* kernel/thread.c:1028 */
k_tid_t z_impl_k_thread_create(struct k_thread *new_thread,
			      k_thread_stack_t *stack,
			      size_t stack_size, k_thread_entry_t entry,
			      void *p1, void *p2, void *p3,
			      int prio, uint32_t options, k_timeout_t delay)
{
	__ASSERT(!arch_is_in_isr(), "Threads may not be created in ISRs");

	z_setup_new_thread(new_thread, stack, stack_size, entry, p1, p2, p3,
			  prio, options, NULL);

	thread_schedule_new(new_thread, delay);

	return new_thread;
}
```

它只做两件事：① `z_setup_new_thread()`（`kernel/thread.c:905`）初始化线程对象——状态位、优先级、栈、架构相关上下文；② `thread_schedule_new()`（`kernel/include/kthread.h:51`）决定线程何时开始跑：`K_NO_WAIT` 直接 `k_thread_start()`，否则挂一个超时定时器。

**注意 `z_impl_` 前缀**：Zephyr 的公共 API 采用 `z_impl_`（实现）+ `z_vrfy_`（用户态校验）分离的模式，`__syscall` 宏在编译期选择其一。这个模式贯穿整个内核，看懂它你就不怕 7000 行的 `kernel.h` 了。

### 3.3 第二个值得精读的函数：`idle()`

`kernel/idle.c:22` 的空闲线程主循环是理解"系统没活干时发生什么"的最短路径：关中断 → `k_cpu_idle()` 进入低功耗 → 超时唤醒后 `z_swap_unlocked()` 重新调度。

## 四、阅读工具推荐

### 4.1 代码导航

- **ctags / universal-ctags**：Zephyr 代码量大，生成 tags 后在 Vim/Neovim 中 `Ctrl-]` 跳转非常高效；
- **clangd + LSP**：比 ctags 更准（能解析宏展开后的类型），但 Zephyr 是 Kconfig 驱动的，需要先用 `west build` 生成 `compile_commands.json` 才能正确索引；
- **`git log --oneline -20 -- <path>`**：AGENTS.md 明确推荐——**一个路径的最近历史是理解其局部约定最好的指南**；
- **`MAINTAINERS.yml`**：`./scripts/get_maintainer.py path <files>` 查某文件归哪个区、谁评审。

### 4.2 配置追踪

- **`west build -t pm_map`**：看内存布局；
- **`west build -t report`**：生成构建报告；
- **`.config` / `zephyr/.config`**：每次构建后生成，是 Kconfig 的最终结果，排查"为什么这段代码被编译进来"直接搜它；
- **`Kconfig` 文件中的 `help` 文本**：如 `kernel/Kconfig:280-321` 对三种调度算法的取舍说明写得非常清楚，比任何博客都权威。

### 4.3 调试与实验

- **`native_sim` 板**：`west build -b native_sim` 后在主机上跑，配合 GDB 单步内核，**不需要任何硬件**；
- **`CONFIG_THREAD_MONITOR`**：开启后内核维护所有线程链表，调试时能看到线程全貌；
- **`tests/` 目录**：每个内核特性都有对应测试（如 `tests/kernel/threads/`），读实现前先读测试，能建立"正确行为"的锚点。

### 4.4 文档

- 在线文档：https://docs.zephyrproject.org（源码在 `doc/`）；
- 内核专项：`doc/kernel/`（services、memory_management、timing_functions、usermode 等）；
- 项目 MCP 服务器：`https://zephyrproject.mcp.kapa.ai` 可搜索文档、源码树、近 6 个月 issue/PR（注意其答案是生成的，须对照源码验证）。

## 五、常见陷阱

### 5.1 把 `kernel/include/` 当公共 API

`kernel/include/` 是内核内部头文件（`z_` 前缀、无 Doxygen 承诺），应用代码只能包含 `include/zephyr/`。读源码时若按公共 API 的稳定性预期去理解内部接口，会误判其演化方式。

### 5.2 忽略 Kconfig 条件编译

同一份源码在不同配置下形态差异巨大。例如 `kernel/sched.c` 的 `next_up()`（`kernel/sched.c:57`）在 `CONFIG_SMP` 下走完全不同的分支（约 80 行 vs 单核 8 行）。**读任何函数前先问：它被哪些 `#ifdef` 包裹？** 建议养成习惯：读代码时把 `CONFIG_` 符号顺手记下来，回头查 Kconfig 的 help 文本。

### 5.3 混淆 `sched.c` 与 `scheduler.c`

`kernel/sched.c`（994 行）是单核调度核心；`kernel/scheduler.c`（139 行）是 SMP 入口与 IPI 相关逻辑。名字太像，grep 时容易拿错文件。

### 5.4 在 ISR 中阻塞

`z_pend_curr()`（`kernel/sched.c:522`）开头就断言"ISR 上下文阻塞 pend 是编程错误"并 `k_panic()`。读同步原语代码时，凡是 `arch_is_in_isr()` 检查出现的地方，都是作者踩过的坑。

### 5.5 直接 `cat` 大文件

`kernel.h` 7348 行、`CMakeLists.txt` 99KB——先 `grep` 定位函数，再按行段读。Zephyr 函数普遍 20-80 行，按函数读完全可行。

### 5.6 用旧版认知读新版

4.4 相比早期版本变化显著：就绪队列从单一实现变为**三选一可配置**（`kernel/Kconfig:271-321`），超时后端有四种，线程状态用位掩码而非枚举。网上很多教程基于 2.x/3.x，结构已对不上。

### 5.7 忘记版本是开发版

`VERSION` 显示 `4.4.99`——这是 4.4 发布后的开发主干。读到的代码可能包含未发布特性；引用行为时以 `doc/releases/` 下的 release notes 为准。

## 六、下一步

1. **精读 `include/zephyr/kernel_structs.h` 全文**（387 行，约 30 分钟）——这是整个内核的"骨架图"，看完它，后面所有文件都有了坐标；
2. **跑通 `native_sim`**：`west build -b native_sim samples/hello_world`，用 GDB 断在 `k_thread_create` 上单步一遍；
3. **进入指南 02（内核架构）**：系统走读 `kernel/` 目录与 `kernel/include/` 关键头文件；
4. 有精力再看 `kernel/idle.c` 全文（107 行），理解空闲路径与电源管理的耦合。

> 心法：读 RTOS 源码不是"读完"，而是**沿一条线程的一生**（创建→就绪→运行→阻塞→唤醒→终止）反复走 3-5 遍，每遍加深一层。本篇给你的是地图，指南 02 给你的是街道。
