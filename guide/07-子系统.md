# 指南 07：子系统（难度 ★★）

**主题**：`subsys/` 目录导读——子系统组织方式，以及网络、文件系统、电源管理等关键子系统。

`subsys/` 是 Zephyr 的"中间件层"：位于内核（`kernel/`）与驱动（`drivers/`）之上，提供协议栈、文件系统、电源管理、日志等跨驱动能力。当前版本包含 **56 个子系统目录**，从成熟的 networking 到实验性的 RTK（GNSS 实时动态定位）不等。理解子系统的组织模式（Kconfig 总开关 + CMake 按开关选源 + 公共 API 头文件），就能快速定位任何子系统。

---

## 一、目录结构说明

每个子系统目录遵循统一骨架：

```
subsys/<name>/
├── CMakeLists.txt      # zephyr_library() + target_sources_ifdef()
├── Kconfig             # menuconfig 总开关 + 子选项
├── *.c / *.h           # 实现与私有头
└── <submodule>/        # 可选：子模块（如 net/ip、pm/device_runtime）
```

公共 API 头文件**不在** `subsys/` 内，而在 `include/zephyr/<name>/`（如 `include/zephyr/net/`、`include/zephyr/fs/`、`include/zephyr/pm/`）——这是 Zephyr 的 API 生命周期约定：`include/zephyr/` 下的头文件是对外承诺的稳定 API。

`subsys/Kconfig` 用 `zephyr-keep-sorted` 块按字母序 source 所有子系统（`subsys/Kconfig:8` 起）；`subsys/CMakeLists.txt` 同样按字母序 `add_subdirectory`，并用 `add_subdirectory_ifdef(CONFIG_X ...)` 按 Kconfig 开关条件加入（`subsys/CMakeLists.txt:14-30` 节选）：

```cmake
# subsys/CMakeLists.txt:14
# zephyr-keep-sorted-start
add_subdirectory(authentication)
add_subdirectory(canbus)
add_subdirectory(debug)
add_subdirectory(fs)
...
add_subdirectory(usb)
# zephyr-keep-sorted-stop
add_subdirectory_ifdef(CONFIG_ARM_SIP_SVC_SUBSYS sip_svc)
add_subdirectory_ifdef(CONFIG_BINDESC bindesc)
add_subdirectory_ifdef(CONFIG_BT bluetooth)
add_subdirectory_ifdef(CONFIG_CHARACTER_FRAMEBUFFER fb)
```

注意两种加入方式的区别：`add_subdirectory` 无条件加入（子系统内部自己用 `ifdef` 选源），`add_subdirectory_ifdef` 整个目录按开关加入（适合"全有或全无"的子系统，如 bluetooth）。

## 三、核心代码走读

### 3.1 网络子系统：分层与 `net_if`

`subsys/net/` 是 Zephyr 最大的子系统（`subsys/net/ip/` 下约 69 个文件）。其 Kconfig 入口（`subsys/net/Kconfig:7`）：

```
# subsys/net/Kconfig:7
config NETWORKING
	bool "Link layer and networking (including IP)"
	select NET_BUF
	select POLL
	select ENTROPY_GENERATOR
```

`select NET_BUF` 体现了子系统的典型依赖方式：网络栈依赖 `lib/net_buf`（网络缓冲区池，见指南 04 的内存章节）。

栈分层：`l2/`（以太网、802.154、PPP 等链路层）→ `ip/`（IPv4/IPv6、TCP/UDP、DHCP 等）→ 上层 socket API。所有接口统一抽象为 `struct net_if`（`include/zephyr/net/net_if.h:783`）：

```c
/* include/zephyr/net/net_if.h:783 */
struct net_if {
	struct net_if_dev *if_dev;     /* 关联的 L2 设备 */
	struct net_if_config config;   /* 接口配置（MTU、类型等） */
	int tx_pending;               /* 待发送包计数（PM 用） */
	struct k_mutex lock;          /* 接口锁 */
	struct k_mutex tx_lock;       /* 发送锁 */
	...
};
```

以太网 L2 驱动适配在 `subsys/net/l2/ethernet/ethernet.c`：它把 `drivers/ethernet/` 的驱动 API 包装成 `net_if` 的收发回调，应用层完全看不到具体网卡。IP 层各协议（`ipv4.c`、`ipv6.c`、`tcp/`、`udp/`、`dhcpv4/` 等）通过 `net_if` 的 hook 机制挂到收发路径上。

网络子系统的日志级别用**模板 Kconfig** 管理（`subsys/net/Kconfig.template.log_config.net`）：`$(module)_LOG_LEVEL_CHOICE` 等宏让每个网络组件（`net_ipv4`、`net_ethernet` 等）自动生成一致的日志级别选项——这是 Zephyr 子系统 Kconfig 的复用技巧。

### 3.2 文件系统：注册表 + 挂载点

`subsys/fs/` 提供 POSIX 风格文件 API（`fs_open`/`fs_read`/`fs_write`），核心是**文件系统类型注册表**（`subsys/fs/fs.c`）：

```c
/* subsys/fs/fs.c:24 */
static sys_dlist_t fs_mnt_list = SYS_DLIST_STATIC_INIT(&fs_mnt_list);
static K_MUTEX_DEFINE(mutex);

/* 挂载点标识 → 文件系统实现的映射 */
struct registry_entry {
	int type;
	const struct fs_file_system_t *fstp;
};
static struct registry_entry registry[CONFIG_FILE_SYSTEM_MAX_TYPES];
```

每种文件系统（FAT、littlefs、EXT2、virtiofs 等）实现 `struct fs_file_system_t` 接口（`include/zephyr/fs/fs_sys.h:28`）——一组函数指针：

```c
/* include/zephyr/fs/fs_sys.h:28 */
struct fs_file_system_t {
	int (*open)(struct fs_file_t *filp, const char *fs_path, fs_mode_t flags);
	ssize_t (*read)(struct fs_file_t *filp, void *dest, size_t nbytes);
	ssize_t (*write)(struct fs_file_t *filp, const void *src, size_t nbytes);
	int (*lseek)(struct fs_file_t *filp, off_t off, int whence);
	off_t (*tell)(struct fs_file_t *filp);
	int (*truncate)(struct fs_file_t *filp, off_t length);
	...
};
```

挂载流程：`fs_mount()` 把挂载点（`struct fs_mount_t`）加入 `fs_mnt_list`；打开文件时 `fs_get_mnt_point()`（`subsys/fs/fs.c:81`）按路径前缀找到挂载点，再由 `registry` 查到对应实现，调用其 `open`。`fs_impl.c` 负责路径前缀剥离（`fs_impl_strip_prefix`，`subsys/fs/fs_impl.c:9`）——把 `/mnt/littlefs/foo.txt` 变成 littlefs 内部的 `foo.txt`。

Kconfig 侧（`subsys/fs/Kconfig:7`）：`FILE_SYSTEM` 总开关 + `FILE_SYSTEM_MAX_TYPES`（注册表大小）+ 各文件系统子开关（`Kconfig.fatfs`、`Kconfig.littlefs`）。

### 3.3 电源管理：系统状态机 + 设备运行时 PM

`subsys/pm/` 分两层：**系统级**（CPU 休眠）与**设备级**（外设 suspend/resume）。

系统级在 `subsys/pm/pm.c`。状态指针数组 `z_cpus_pm_state[]`（`subsys/pm/pm.c:28`）指向当前电源状态（NULL 表示 ACTIVE）：

```c
/* subsys/pm/pm.c:28 */
static const struct pm_state_info *z_cpus_pm_state[CONFIG_MP_MAX_NUM_CPUS];
static const struct pm_state_info *z_cpus_pm_forced_state[CONFIG_MP_MAX_NUM_CPUS];
static struct k_spinlock pm_forced_state_lock;
static struct k_spinlock pm_notifier_lock;
```

`pm_system_suspend()`（`subsys/pm/pm.c:168` 起）在 idle 时被架构层调用：计算"距下一个事件还有多少 tick"（取内核定时器、`pm_policy_next_event_ticks()`、自定义 hook 三者最小值），然后按策略选择目标状态、调用 `pm_state_set()` 进入休眠，唤醒后执行 `pm_system_resume()`。`pm_notifier_register()`（`subsys/pm/pm.c:289`）允许子系统注册状态切换回调（进入/离开某电源状态时通知）。

设备级在 `subsys/pm/device.c` + `device_runtime.c`。设备电源状态机用两张查找表定义合法转换（`subsys/pm/device.c:14-23`）：

```c
/* subsys/pm/device.c:14 */
static const enum pm_device_state action_target_state[] = {
	[PM_DEVICE_ACTION_SUSPEND] = PM_DEVICE_STATE_SUSPENDED,
	[PM_DEVICE_ACTION_RESUME]   = PM_DEVICE_STATE_ACTIVE,
	[PM_DEVICE_ACTION_TURN_OFF] = PM_DEVICE_STATE_OFF,
	[PM_DEVICE_ACTION_TURN_ON]  = PM_DEVICE_STATE_SUSPENDED,
};
static const enum pm_device_state action_expected_state[] = {
	[PM_DEVICE_ACTION_SUSPEND] = PM_DEVICE_STATE_ACTIVE,
	[PM_DEVICE_ACTION_RESUME]   = PM_DEVICE_STATE_SUSPENDED,
	[PM_DEVICE_ACTION_TURN_OFF] = PM_DEVICE_STATE_SUSPENDED,
	[PM_DEVICE_ACTION_TURN_ON]  = PM_DEVICE_STATE_OFF,
};
```

`pm_device_action_run()`（`subsys/pm/device.c:47`）校验"当前状态 == 期望状态"后才执行 `action_cb`，失败时 TURN_ON/TURN_OFF 仍要更新状态（反映物理现实）。

运行时 PM 的核心是**引用计数**：`pm_device_runtime_enable()`（`subsys/pm/device_runtime.c:552`）把设备切到 SUSPENDED 并置 `RUNTIME_ENABLED` 标志；之后每次 `pm_device_runtime_get()` 递增 `usage` 计数，`pm_device_runtime_put()` 递减到 0 时（可选经延迟 work）才真正 resume。设备初始化成功时内核自动调用 `pm_device_runtime_auto_enable()`（见指南 05 的 `kernel/device.c:54`）。

### 3.4 RTIO：Zephyr 的异步 I/O 框架

`subsys/rtio/` 是仿 Linux io_uring 的异步 I/O 框架（`subsys/rtio/Kconfig`），由 Intel 贡献，被 sensing 等子系统用作底层。核心组件：

- **SQE/CQE 池**：`rtio_init()`（`subsys/rtio/rtio_init.c:18`）遍历 `rtio_sqe_pool`/`rtio_cqe_pool` 可迭代段，把空闲项压入 MPSC 无锁队列；
- **工作队列**：`rtio_workq.c` 定义固定线程池 + 请求 slab（`K_MEM_SLAB_DEFINE_STATIC_TYPE`，`subsys/rtio/rtio_workq.c:15`），工作线程从 `k_queue` 取请求并执行 `req->handler`（`subsys/rtio/rtio_workq.c:63-74`）：

```c
/* subsys/rtio/rtio_workq.c:63 */
static void rtio_workq_thread_fn(void *arg1, void *arg2, void *arg3)
{
	while (true) {
		struct rtio_work_req *req = k_queue_get(&rtio_workq, K_FOREVER);
		if (req != NULL) {
			req->handler(req->iodev_sqe);
			k_mem_slab_free(&rtio_work_items_slab, req);
		}
	}
}
```

- **执行器**：`rtio_executor.c` 处理 `RTIO_OP_CALLBACK` 等不需要设备参与的提交（`subsys/rtio/rtio_executor.c:25`）。

### 3.5 其他代表性子系统速览

- **`logging`**：`LOG` 总开关（`subsys/logging/Kconfig:7`），支持运行时过滤（`LOG_RUNTIME_FILTERING`）、多后端（UART、RTT 等）。各子系统通过 `Kconfig.template.log_config` 模板自动获得 `<MODULE>_LOG_LEVEL` 选项；
- **`bluetooth`**：`BT` 总开关（`subsys/bluetooth/Kconfig:7`，`depends on !SMP`——蓝牙主机栈尚不支持 SMP），`host/` 下按协议分层（`att.c` 属性协议、`adv.c` 广播、`gatt`、`l2cap` 等），基于 `net_buf` 传递 HCI 包；
- **`storage`**：`flash_map`（flash 分区表抽象，`flash_area_foreach` 遍历，`subsys/storage/flash_map/flash_map.c:23`）+ `stream_flash`（按页对齐的流式写入，`subsys/storage/stream/stream_flash.c`）；
- **`settings`**：把子系统状态序列化到非易失存储（`subsys/settings/Kconfig:7`），支持多后端、原子保存；
- **`mgmt`**：设备远程管理——`mcumgr`（SMP 协议，`subsys/mgmt/mcumgr/Kconfig:7`，依赖 `NET_BUF` + `ZCBOR`）与 `hawkbit`（Eclipse hawkBit OTA，`subsys/mgmt/hawkbit/Kconfig:7`，依赖一长串：`SETTINGS` + `FLASH` + `NET_TCP` + `IMG_MANAGER` + `MCUBOOT` 等）；
- **`sensing`**：传感器子系统（`subsys/sensing/Kconfig:5`，`select RTIO`），`sensor_mgmt.c` 用 `RTIO_DEFINE_WITH_MEMPOOL` 建 RTIO 上下文（`subsys/sensing/sensor_mgmt.c:31`），`open_sensor()`（`subsys/sensing/sensor_mgmt.c:351`）为每个客户端建 `sensing_connection`；
- **`emul`**：仿真驱动框架（`subsys/emul/Kconfig:7`），让"假硬件"以真实驱动 API 形态出现，用于子系统测试；
- **`gnss`**：GNSS RTK 客户端（`subsys/gnss/rtk/Kconfig:7`，实验性），`gnss_rtk_publish_data()`（`subsys/gnss/rtk/rtk.c:13`）用可迭代段 `gnss_rtk_data_callback` 广播 RTK 数据给所有注册的回调。

### 3.6 子系统接入模式（通用）

新增一个子系统要做的三件事，与指南 06 的构建系统直接对应：

1. **`subsys/<name>/Kconfig`**：`menuconfig` 总开关 + 依赖（`select`/`depends on`）+ 插入 `subsys/Kconfig` 的 keep-sorted 块；
2. **`subsys/<name>/CMakeLists.txt`**：`zephyr_library()` + `target_sources_ifdef()` + 插入 `subsys/CMakeLists.txt` 的 keep-sorted 块（或用 `add_subdirectory_ifdef`）；
3. **`include/zephyr/<name>/`**：公共 API 头文件（带 Doxygen，遵循 API 生命周期）。

## 四、扩展阅读建议

1. **`doc/subsystems/`**：各子系统官方文档（networking、filesystem、power management、logging 等章节），比源码注释更系统地解释设计动机；
2. **`include/zephyr/net/` 全部头文件**：网络 API 面很大，建议按 `net_if.h` → `net_pkt.h` → `socket.h` 的顺序读；
3. **`subsys/fs/` 的 littlefs 集成**（`littlefs_fs.c`）：看一个文件系统如何实现 `fs_file_system_t` 全接口；
4. **`doc/reference/pm/`**：电源管理 API 参考（系统/设备/域三层）；
5. **`subsys/rtio/` 全部文件**（总共不到 2000 行）：小而完整的异步框架实现，适合通读；
6. **`MAINTAINERS.yml`**：查各子系统的维护者，读代码时遇到问题知道找谁。
