# 指南 05：设备驱动模型（难度 ★★★）

**主题**：Zephyr 驱动框架导读——设备树（devicetree）、`struct device` 驱动模型、设备生命周期、关键 API。

Zephyr 的驱动模型建立在一个核心思想之上：**硬件描述与驱动代码分离**。硬件"长什么样"（寄存器地址、引脚、中断）写在设备树里，驱动"怎么操作"（初始化、读写、API）写在 C 代码里，两者通过 `compatible` 属性在编译期匹配。运行时，内核把每个驱动实例表示为一个 `struct device` 对象，统一负责初始化、就绪状态查询与电源管理。这套机制让同一个驱动代码可以适配任意厂商的任意芯片——只要设备树按 binding 规范描述硬件。

## 三、核心代码走读

### 3.1 `struct device`：ROM 描述符 + RAM 状态分离

Zephyr 把设备对象拆成两半：**不可变的描述符**（`struct device`，放 ROM）和**可变的状态**（`struct device_state`，放 RAM）。这个分离让设备描述符可以整体 `const`，在用户空间（CONFIG_USERSPACE）下天然只读：

```c
/* include/zephyr/device.h:543 */
struct device {
	const char *name;           /* 设备名（DT 的 label 或节点全名） */
	const void *config;         /* 驱动私有只读配置（通常指向 DT 生成的结构） */
	const void *api;            /* 驱动 API 函数指针表（如 uart_driver_api） */
	struct device_state *state; /* 运行时状态（RAM） */
	void *data;                 /* 驱动私有可变数据 */
	struct device_ops ops;      /* init/deinit 函数指针 */
	device_flags_t flags;       /* 如 DEVICE_FLAG_INIT_DEFERRED */
};

/* include/zephyr/device.h:488 */
struct device_state {
	uint8_t init_res;      /* init 返回码（取正值的 errno） */
	bool initialized : 1;  /* init 是否已被调用过 */
};
```

`api` 字段是驱动向应用暴露能力的通道：例如 UART 驱动的 `api` 指向 `struct uart_driver_api`（`uart_api.h`），应用拿到 `struct device *` 后通过 `DEVICE_API_GET(uart, dev)` 取到函数指针表。API 类还有**继承机制**（`DEVICE_API_EXTENDS`，`include/zephyr/device.h:1451-1455`）：子 API 结构体必须以父 API 作为第一个成员，`DEVICE_API_IS()` 就能通过段地址比较判断设备是否属于某个 API 类。

### 3.2 `DEVICE_DT_DEFINE`：从设备树节点生成设备对象

驱动不手工填 `struct device`，而是用宏从 DT 节点生成。以 `DEVICE_DT_DEFINE` 为例（`include/zephyr/device.h:265`），它层层展开到 `Z_DEVICE_DEFINE`（`include/zephyr/device.h:1378-1397`），一次生成四样东西：

```c
/* include/zephyr/device.h:1378 */
#define Z_DEVICE_DEFINE(node_id, dev_id, name, init_fn, deinit_fn, flags, pm,   \
			data, config, level, prio, api, state, ...)             \
	Z_DEVICE_NAME_CHECK(name);                                              \
	/* 1. 设备依赖表（CONFIG_DEVICE_DEPS 时） */                              \
	IF_ENABLED(CONFIG_DEVICE_DEPS,                                          \
		   (Z_DEVICE_DEPS_DEFINE(node_id, dev_id, __VA_ARGS__);))       \
	/* 2. DT 元数据（shell 按 DT 节点标签查设备用） */                        \
	IF_ENABLED(CONFIG_DEVICE_DT_METADATA,                                   \
		   (IF_ENABLED(DT_NODE_EXISTS(node_id),                         \
			      (Z_DEVICE_DT_METADATA_DEFINE(node_id, dev_id);))))\
	/* 3. 设备对象本体（放入可迭代的 device 段） */                           \
	Z_DEVICE_BASE_DEFINE(node_id, dev_id, name, init_fn, deinit_fn, flags,  \
			     pm, data, config, level, prio, api, state, ...);   \
	/* 4. 初始化入口（按 level/prio 排序执行） */                             \
	Z_DEVICE_INIT_ENTRY_DEFINE(node_id, dev_id, level, prio);
```

其中 `name` 来自 `DEVICE_DT_NAME(node_id)`（`include/zephyr/device.h:210`）：优先取节点的 `label` 属性，否则用节点全名。`level` 通常是 `PRE_KERNEL_1`（时钟/定时器）、`PRE_KERNEL_2`（串口/内存控制器）或 `POST_KERNEL`（其余外设）。

驱动里最常见的写法是配合 `DT_DRV_COMPAT`：

```c
/* 典型驱动骨架（示意） */
#define DT_DRV_COMPAT vendor_uart

static int my_uart_init(const struct device *dev) { ... }

DEVICE_DT_INST_DEFINE(0, my_uart_init, NULL, NULL, &cfg,
		      PRE_KERNEL_2, 0, &my_uart_api);
```

`DT_DRV_COMPAT` 是 `DT_DRV_INST(0)` 的别名，即"该 compatible 的第 0 个 status=okay 节点"。`DT_FOREACH_STATUS_OKAY_NODE()`（`include/zephyr/device.h:1413`）还会为每个 okay 节点预声明 `extern struct device`，保证"声明了节点却没写驱动"时链接期就能暴露问题。

### 3.3 设备初始化生命周期

内核启动时按 level/prio 顺序执行所有 init entry，最终落到 `kernel/device.c` 的 `do_device_init()`（`kernel/device.c:18-61`）：

```c
/* kernel/device.c:18 */
int do_device_init(const struct device *dev)
{
	int rc = 0;

	if (dev->ops.init != NULL) {
		rc = dev->ops.init(dev);
		/* 失败时把正值的 errno 存入 state->init_res */
		if (rc != 0) {
			__ASSERT(rc >= -UINT8_MAX && rc < 0, ...);
			if (rc < 0) {
				rc = -rc;
			}
			if (rc > UINT8_MAX) {
				rc = UINT8_MAX;   /* 截断防溢出 */
			}
			dev->state->init_res = rc;
		}
	}

	dev->state->initialized = true;   /* 无论成败都标记"已调用过" */

	if (rc == 0) {
		/* 初始化成功后自动启用 runtime PM */
		(void)pm_device_runtime_auto_enable(dev);
	}

	return -rc;
}
```

三个要点：

1. **`initialized` 与 `init_res` 是两回事**——init 被调用过但失败时，`initialized == true` 而 `init_res != 0`；
2. **`device_is_ready()`**（`kernel/device.c:186-197`）的判定是 `initialized && init_res == 0`，且对 NULL 指针返回 false（"无效设备视为未就绪"）；
3. 初始化成功后自动调用 `pm_device_runtime_auto_enable()`（`kernel/device.c:54`），把设备交给运行时电源管理（见指南 07 的 PM 子系统）。

应用侧的标准用法：

```c
const struct device *dev = DEVICE_DT_GET(DT_NODELABEL(uart0));
if (!device_is_ready(dev)) {
	LOG_ERR("uart0 not ready");
	return;
}
```

按名查找用 `device_get_binding()`（`kernel/device.c:83-100`），它遍历 `device` 段做字符串匹配，**未就绪的设备返回 NULL**——注意这与 `DEVICE_DT_GET`（直接取地址）语义不同。

### 3.4 设备依赖（CONFIG_DEVICE_DEPS）

设备之间存在依赖（如某外设依赖某个时钟）。`Z_DEVICE_DEPS_DEFINE` 在编译期把 DT 的 `zephyr,requires`/`zephyr,supported-by` 属性固化成依赖表；构建期 `scripts/build/gen_device_deps.py` 从链接中间产物生成 `device_deps.c`（`CMakeLists.txt:1138-1154`，属于多阶段链接的第二阶段输入）。运行时遍历 API 在 `kernel/device.c:236-275`：

```c
/* kernel/device.c:257 */
int device_required_foreach(const struct device *dev,
			    device_visitor_callback_t visitor_cb,
			    void *context)
{
	size_t handle_count = 0;
	const device_handle_t *handles =
		device_required_handles_get(dev, &handle_count);
	return device_visitor(handles, handle_count, visitor_cb, context);
}
```

### 3.5 设备树：binding 与属性

DT 源文件是 C 预处理语法（`.dts`/`.dtsi`），最小骨架见 `dts/common/skeleton.dtsi`：

```dts
/* dts/common/skeleton.dtsi:1 */
/ {
	#address-cells = <1>;
	#size-cells = <1>;
	chosen {};
	aliases {};
};
```

各架构 dtsi（如 `dts/arm/armv8-m.dtsi`）在此骨架上补 `soc`、NVIC、SysTick 等节点。板级 overlay 通过 `&node { ... }` 语法覆盖 SoC 默认值。

**binding** 是属性的"类型定义"。每个 compatible 对应 `dts/bindings/` 下的一个 YAML。基类 `dts/bindings/base/base.yaml` 定义了所有设备公共属性：

```yaml
# dts/bindings/base/base.yaml（节选）
include: [pm.yaml]
properties:
  status:
    type: string
    enum: ["okay", "disabled", "reserved", "fail", "fail-sss"]
  compatible:
    type: string-array
    required: true
  reg:
    type: array          # (地址, 长度) 对
  reg-names:
    type: string-array
```

具体 binding 在此基础上扩展，例如 `dts/bindings/clock/clock-controller.yaml` 要求 `#clock-cells`（时钟 spec 的项数）。compatible 的命名规范是 `<vendor>,<device>`（vendor 需在 `dts/bindings/vendor-prefixes.txt` 登记）；通用硬件（如 `gpio-leds`）不加虚构前缀。

驱动读属性全部走 `DT_*` 宏（`include/zephyr/devicetree.h`）：`DT_PROP(node_id, prop)` 读标量、`DT_REG_ADDR(node_id)` 读寄存器地址、`DT_IRQ_BY_IDX(node_id, idx, ...)` 读中断、`DT_Nodelabel_GET` 等。这些宏在构建期由 `scripts/dts/` 工具链展开成 C 字面量——**DT 是编译期信息，不占运行时内存**（只有驱动 `config`/`data` 结构体引用到的部分进 ROM）。

### 3.6 设备电源管理钩子

`struct device` 携带 `pm`（`struct pm_device`）字段，驱动通过 `PM_DEVICE_RUNTIME_DEFINE` 等宏声明自己支持 suspend/resume。`kernel/device.c` 的 `z_impl_device_deinit()`（`kernel/device.c:199-224`）在 `CONFIG_DEVICE_DEINIT_SUPPORT` 下调用 `ops.deinit()` 并清除 `initialized` 标志——设备可以"去初始化"后重新 `device_init()`（注意 `z_impl_device_init` 对已初始化设备返回 `-EALREADY`，`kernel/device.c:63-70`）。

## 五、扩展阅读建议

1. **`include/zephyr/devicetree.h` 全文**：`DT_*` 宏家族是驱动开发的日常工具，重点看 `DT_FOREACH_STATUS_OKAY_NODE` 与 `DT_INST_FOREACH_STATUS_OKAY` 的展开机制；
2. **`doc/build/dts/`**：设备树编写指南、binding 上游流程（`bindings-upstream.rst`）、compatible 命名规范；
3. **`scripts/dts/`**：DT 预处理（`soc` 树如何与板级 overlay 合并）与 `zephyr.dts` 生成逻辑；
4. **一个完整驱动**：建议选 `drivers/uart/` 下的某个简单 UART 驱动（如 `uart_nrfx.c`），对照 `dts/bindings/serial/` 的 binding 通读，把"DT 节点 → config 结构 → init 函数"的链路走一遍；
5. **`doc/reference/drivers/`**：各驱动类的 API 参考（UART、GPIO、Flash 等）；
6. **`kernel/Kconfig.device`**：`CONFIG_DEVICE_DEINIT_SUPPORT`、`CONFIG_DEVICE_DEPS`、`CONFIG_DEVICE_DT_METADATA` 等开关的取舍。
