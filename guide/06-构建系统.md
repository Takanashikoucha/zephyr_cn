# 指南 06：构建系统（难度 ★★）

**主题**：Zephyr 构建系统导读——CMake 构建流程、Kconfig 配置系统、west 工具链。

Zephyr 的构建系统由三个协作的组件构成：**west**（仓库管理 + 命令入口）、**CMake**（构建图与链接流程）、**Kconfig**（配置系统）。理解它们的分工：west 负责"把代码拉齐"和"调用 cmake"，CMake 负责"编译什么、怎么链接"，Kconfig 负责"哪些功能被启用"。三者通过 `build/` 目录下的 `CMakeCache.txt` 与 `.config` 文件交换信息。

---

## 一、目录结构说明

| 位置 | 内容 | 说明 |
|---|---|---|
| `CMakeLists.txt`（仓库根，2462 行） | **不是**顶层 CMakeLists——真正的顶层在应用目录 | Zephyr 自身的构建逻辑，被应用的 CMakeLists `include()` |
| `Kconfig.zephyr` | 根 Kconfig | 按序 source 各子系统的 Kconfig |
| `Kconfig.constants` | 常量定义（如 `VERSION_CODE`） | 被根 Kconfig 首先 source |
| `west.yml` | west 仓库清单 | 声明所有依赖仓库（HAL、模块、工具） |
| `cmake/` | CMake 辅助文件 | `linker/`（链接脚本生成）、`toolchain/`、`flash/`、`usage/` 等 |
| `scripts/` | 构建期 Python 工具 | `build/`（生成代码）、`west_commands/`（west 命令实现）、`dts/`（DT 处理） |
| `scripts/west_commands/` | west 命令实现 | `build.py`（`west build`）、`zcmake.py`（cmake 封装）、`flash.py`、`twister_cmd.py` 等 |
| `boards/` `soc/` `arch/` | 板级/SoC/架构构建定义 | 各自的 `CMakeLists.txt` + `Kconfig` + defconfig |
| `subsys/` `drivers/` `lib/` `kernel/` | 各组件构建定义 | 每个组件一个 `CMakeLists.txt` + `Kconfig` |

## 三、核心代码走读

### 3.1 west：从命令到 cmake

`west build` 的实现入口是 `scripts/west_commands/build.py`。其核心流程（`scripts/west_commands/build.py:286-294`）：

```python
# scripts/west_commands/build.py:286
        self._run_cmake(board, origin)
        ...
        self._run_build(args.target, args.domain)
```

`_run_cmake()`（`scripts/west_commands/build.py:668-750`）组装 cmake 参数：`-DBOARD=`、`-DSOC=`、`-DZEPHYR_BASE=` 等，然后调用 `run_cmake()`；`_run_build()`（`scripts/west_commands/build.py:752-779`）调用 `run_build()`。两者都委托给 `zcmake.py`：

```python
# scripts/west_commands/zcmake.py:32
def run_cmake(args, cwd=None, capture_output=False, dry_run=False, env=None):
    cmake = shutil.which('cmake')
    if cmake is None and not dry_run:
        sys.exit('CMake is not installed or cannot be found; cannot build.')
    _ensure_min_version(cmake, dry_run)
    cmd = [cmake] + args
    ...
    p = subprocess.Popen(cmd, env=env, **kwargs)
    out, _ = p.communicate()
    ...
    if p.returncode == 0:
        return out.splitlines() if out else None
    else:
        raise subprocess.CalledProcessError(p.returncode, p.args)
```

`run_build()`（`scripts/west_commands/zcmake.py:82-114`）执行 `cmake --build <build_dir>`，并解析 `-- -j N` / `-v` 等构建选项（通过 `CMAKE_BUILD_PARALLEL_LEVEL` 环境变量传递并行度）。默认生成器是 **Ninja**（`scripts/west_commands/zcmake.py:28`）。

west 的另一个职责是**仓库管理**。`west.yml` 声明所有依赖（`west.yml:20-40` 节选）：

```yaml
# west.yml:20
manifest:
  defaults:
    remote: upstream
  remotes:
    - name: upstream
      url-base: https://github.com/zephyrproject-rtos
    - name: babblesim
      url-base: https://github.com/BabbleSim
  group-filter: [-babblesim, -optional, -testing]
  projects:
    - name: acpica
      revision: 8d24867bc9c9d81c81eeac59391cda59333affd4
      path: modules/lib/acpica
    ...
```

`west init -l <zephyr-dir> && west update` 按此清单拉取 HAL 与模块仓库到 `modules/` 与 `tools/` 下。每个 project 的 `path` 字段决定落盘位置，`revision` 锁定版本。`groups` 机制允许按功能组选择性拉取（如 `babblesim` 组只在需要蓝牙仿真时拉取）。

### 3.2 CMake：Zephyr 的构建图

应用目录的 `CMakeLists.txt`（真正的顶层）会 `include()` 仓库根的 `CMakeLists.txt`。后者开头就声明了它**不是**顶层（`CMakeLists.txt:3-12`），并校验 `ZEPHYR_BINARY_DIR` 已定义（`CMakeLists.txt:14-22`）。

**多阶段链接**是 Zephyr CMake 流程中最特殊的部分（`CMakeLists.txt:39-92`）：

```cmake
# CMakeLists.txt:44
# 目前最多三个阶段：
# zephyr_pre0:  第一遍链接（段大小/地址可能变化）
# zephyr_pre1:  第二遍链接（段大小固定，地址不可再变）
# zephyr_final: 最终镜像
#
# 需要多阶段的场景：
# - CONFIG_DEVICE_DEPS（设备依赖表生成）
# - CONFIG_GEN_ISR_TABLES（ISR 表生成）
# - CONFIG_USERSPACE（内核对象哈希表、应用内存分区）

set(ZEPHYR_CURRENT_LINKER_PASS 0)
set(ZEPHYR_CURRENT_LINKER_CMD    linker_zephyr_pre${ZEPHYR_CURRENT_LINKER_PASS}.cmd)
set(ZEPHYR_LINK_STAGE_EXECUTABLE zephyr_pre${ZEPHYR_CURRENT_LINKER_PASS})
...
if(CONFIG_USERSPACE OR CONFIG_DEVICE_DEPS)
  set(ZEPHYR_PREBUILT_EXECUTABLE zephyr_pre1)
else()
  set(ZEPHYR_PREBUILT_EXECUTABLE zephyr_pre0)
endif()
```

为什么需要"先链接一遍再链接"？因为 `gen_device_deps.py`、`gen_isr_tables.py` 等工具需要**从第一遍链接的 ELF 中读取符号地址**，生成 C 源码（`device_deps.c` 等），再参与第二遍链接。`CMakeLists.txt:1138-1154` 用 `add_custom_command` 把 `gen_device_deps.py` 挂到 `zephyr_pre0` 之后：

```cmake
# CMakeLists.txt:1140
  add_custom_command(
    OUTPUT device_deps.c
    COMMAND
    ${PYTHON_EXECUTABLE}
    ${ZEPHYR_BASE}/scripts/build/gen_device_deps.py
    --output-source device_deps.c
    --output-graphviz dev_graph.dot
    ${dynamic_deps}
    --num-dynamic-devices ${number_of_dynamic_devices}
    --kernel $<TARGET_FILE:${ZEPHYR_LINK_STAGE_EXECUTABLE}>
    ...
    DEPENDS ${ZEPHYR_LINK_STAGE_EXECUTABLE}
    )
```

**子目录加入顺序**有讲究（`CMakeLists.txt:736-771`）：

```cmake
# CMakeLists.txt:758
# arch 放在最前，因为它定义重要的编译器标志，
# 必须导出给 subsys/ 等定义的外部构建系统。
add_subdirectory(arch)
add_subdirectory(lib)
include(misc/generated/CMakeLists.txt)   # 用 include 而非 add_subdirectory
add_subdirectory(soc)
add_subdirectory(boards)
add_subdirectory(subsys)
add_subdirectory(drivers)
# 然后是 west 拉取的 modules（CMakeLists.txt:774-787）
```

每个组件（`kernel/`、`subsys/*`、`drivers/*`）的 `CMakeLists.txt` 遵循统一模式：`zephyr_library()` 声明 + `target_sources_ifdef(CONFIG_X ...)` 按 Kconfig 开关选源文件 + `zephyr_include_directories()`。例如 `kernel/CMakeLists.txt:144-177` 还负责**计算系统堆大小**：汇总所有 `CONFIG_HEAP_MEM_POOL_ADD_SIZE_*` 需求，与 `CONFIG_HEAP_MEM_POOL_SIZE` 取最大值，生成 `K_HEAP_MEM_POOL_SIZE` 编译定义。

### 3.3 Kconfig：配置系统

Zephyr 使用 Kconfig（与 Linux 内核同源）管理配置。根文件 `Kconfig.zephyr` 的结构（`Kconfig.zephyr:1-40` 节选）：

```
# Kconfig.zephyr:5
source "Kconfig.constants"
osource "$(APPLICATION_SOURCE_DIR)/VERSION"
# 尽早加载 DT 生成的 Kconfig（autogen Kconfig.dts 的选项和宏
# 可能被 shield/board/SoC defconfig 或模块引用）
source "dts/Kconfig"
# 先加载 defconfig 文件，使其能覆盖默认值：
# shield 默认 > board 默认 > SoC 默认 > 工具链默认
osource "$(KCONFIG_BINARY_DIR)/Kconfig.shield.defconfig"
source "boards/shields/*/Kconfig.defconfig"
osource "$(KCONFIG_BOARD_DIR)/Kconfig.defconfig"
source "$(KCONFIG_BINARY_DIR)/soc/Kconfig.defconfig"
osource "$(TOOLCHAIN_KCONFIG_DIR)/Kconfig.defconfig"
...
source "boards/Kconfig"
source "soc/Kconfig"
source "arch/Kconfig"
source "kernel/Kconfig"
source "drivers/Kconfig"
source "lib/Kconfig"
source "subsys/Kconfig"
```

注意 `osource`（optional source）：文件不存在时静默跳过——defconfig 就是这样"可选注入"的。

`subsys/Kconfig` 用 `zephyr-keep-sorted` 标记维护有序 source 列表（`subsys/Kconfig:8` 起）：

```
# subsys/Kconfig:8
# zephyr-keep-sorted-start
source "subsys/authentication/Kconfig"
source "subsys/bindesc/Kconfig"
source "subsys/bluetooth/Kconfig"
...
# zephyr-keep-sorted-stop
```

CI 的 KeepSorted 检查会强制该块保持字母序——新增子系统时插入位置必须正确。

每个子系统的 Kconfig 遵循统一模式：`menuconfig` 总开关 + `select`/`depends on` 依赖 + 可选的日志级别模板。例如 `subsys/net/Kconfig`（节选）：

```
# subsys/net/Kconfig:7
config NETWORKING
	bool "Link layer and networking (including IP)"
	select NET_BUF
	select POLL
	select ENTROPY_GENERATOR
```

`select` 与 `depends on` 的区别是 Kconfig 新手最常混淆的：`select` 是**无条件强制启用**（被选者不感知选择者），`depends on` 是**条件约束**（条件不满足时该选项不可见）。选型原则见 `doc/build/kconfig/tips.rst`。

`west build -o CONFIG_X=y` 或 `pristine` 目录下的 `menuconfig`（ncurses 界面）修改配置后，west 会重新运行 Kconfig 生成 `.config` 与 `autoconf.h`（`CONFIG_*` 宏），CMake 再据此决定编译哪些源文件。

### 3.4 构建期代码生成

`scripts/build/` 下约 30 个 Python 工具在构建期生成 C 代码，典型如：

- `gen_device_deps.py`：设备依赖表（见 3.2）；
- `gen_isr_tables.py`：ISR 表（`CONFIG_GEN_ISR_TABLES`）；
- `gen_syscalls.py` / `parse_syscalls.py`：syscall 列表与用户空间校验代码；
- `gen_iter_sections.py`：可迭代段的 C 数组；
- `gen_offset_header.py`：内核结构体偏移（用户空间用）；
- `gen_version_h.cmake`（`cmake/`）：从 `VERSION` 文件生成 `version.h`。

这些生成物统一放在 `build/include/generated/zephyr/` 下，`zephyr_generated_headers` 接口库（`CMakeLists.txt:755-756`）负责保证"生成先于编译"的依赖顺序。

## 四、一次 `west build` 的完整链路

```
west build -b <board> <app>
  │
  ├─ west 解析参数（build.py:200-290）
  ├─ 确定 build 目录（默认 <app>/build）
  ├─ run_cmake()：cmake -DBOARD=... -DSOC=... <app>
  │    ├─ 应用 CMakeLists.txt → include(Zephyr 根 CMakeLists.txt)
  │    ├─ 运行 Kconfig（.config 生成 + autoconf.h）
  │    ├─ 处理设备树（scripts/dts/ → zephyr.dts → devicetree.h）
  │    ├─ add_subdirectory(arch/lib/soc/boards/subsys/drivers/modules)
  │    ├─ 生成链接脚本（cmake/linker/）
  │    └─ 生成构建图（Ninja）
  └─ run_build()：cmake --build <build_dir>
       ├─ 编译各组件源文件
       ├─ 第一遍链接（zephyr_pre0）
       ├─ 运行 gen_device_deps.py 等（基于 pre0 ELF）
       ├─ 第二遍链接（zephyr_pre1，如需要）
       └─ 最终链接（zephyr_final）→ zephyr.elf
```

后续 `west flash`（`scripts/west_commands/flash.py`）调用 `cmake/flash/` 下的工具链把镜像烧录；`west twister`（`scripts/west_commands/twister_cmd.py`）批量跑测试。
